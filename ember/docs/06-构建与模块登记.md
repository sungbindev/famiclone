# 构建与模块登记

Ember 的构建命令、由 Schema 生成的代码、模块的登记方式与依赖检查。目录分层与依赖规则见 [01-软件架构设计.md](01-软件架构设计.md) 第 4、5 节。

## 1. 命令

在 `ember/` 目录下运行；先 `npm install`。

| 命令 | 用途 |
| --- | --- |
| `npm run schema` | 由 `schema/` 生成 TypeScript 与 C++ 代码 |
| `npm run core:build` | 生成 Schema 代码、打包官方插件并编译原生模块，输出 `core/build/Release/ember_core.node` |
| `npm run core:test` | 生成 Schema 代码、打包官方插件，构建并运行 C++ 测试（GoogleTest） |
| `npm run plugins:pack` | 把 `plugins/<插件>/` 打成 `build/plugins/<id>.emap`，见第 7 节 |
| `npm start` | 生成代码、打包插件、编译原生模块，再启动开发版 |
| `.\debug.ps1` | 在任意目录下启动开发版（切到项目目录后执行 `npm start`） |
| `npm run typecheck` | 生成代码后做 TypeScript 类型检查 |
| `npm run lint` | oxlint 检查（有警告即失败） |
| `npm run boundaries` | 分层、模块依赖与模块登记检查 |
| `npm test` | 生成代码后运行 TypeScript 测试（Vitest） |
| `npm run check` | 类型检查、lint、依赖检查、TypeScript 测试与 C++ 测试 |
| `npm run package` | 打包当前平台的应用 |
| `npm run package:win` | 打包 Windows x64 版 |
| `npm run make:win` | 生成 Windows x64 安装程序 |
| `npm run package:mac` | 打包 macOS arm64 版（只在苹果电脑上运行） |
| `node tools/dev/smoke-run.mjs` | Electron 冒烟，见第 8 节 |
| `node tools/dev/latency-run.mjs` | 画面延迟与丢帧测量，见第 9 节 |

- Windows 上编译 C++ 使用 Visual Studio 自带的 CMake（用 `vswhere` 查找）；PATH 里的 `cmake` 可能是 MinGW 的，不被使用。环境变量 `EMBER_CMAKE` 可指定 `cmake` 可执行文件。
- 界面组件库默认取 `../../rujian-ui-kit`（与 `famiclone` 并列），环境变量 `EMBER_UI_KIT_SOURCE` 可指定其他位置。
- 核心版本取自 `package.json` 的 `version`，编译时经 `EMBER_CORE_VERSION` 传入；应用版本由主进程在启动核心时传入。

## 2. Schema 与生成代码

请求、事件与数据类型只在 `schema/<模块>.schema.json` 中定义。`npm run schema` 生成：

| 生成位置 | 内容 |
| --- | --- |
| `src/contracts/<模块>/generated/<模块>.ts` | 请求名、事件名、数据类型、请求名到类型的对照，以及入口校验用的 Schema |
| `src/contracts/core-gateway/generated/core-api.ts` | 汇总全部模块：请求名单、事件名单、`CoreApi` 与全部 Schema |
| `core/src/contracts/<模块>/generated/<模块>.hpp`、`.cpp` | C++ 数据结构、请求名常量、JSON 转换与结构校验 |
| `docs/api/openrpc.json`、`core/src/contracts/debug/generated/openrpc.hpp`、`.cpp` | 调试服务的 OpenRPC 接口描述文档（全部模块的请求与事件，`debugOnly` 与 `mainOnly` 带 `x-` 标记）；核心里的是同一份文档的 C++ 常量，`rpc.discover` 返回它；由 `tools/schema-gen/openrpc.mjs` 生成，见 04 第 2.2 节 |

- 生成目录不提交，不手写、不手改；内容没变的文件不改写；删除模块后，它的生成目录一并删除。`docs/api/openrpc.json` 在文档目录里，随代码一起提交，同样不手改。
- Schema 是 JSON Schema 的子集：类型 `string`、`integer`、`number`、`boolean`、`array`、`object`；可空写成 `["string", "null"]`；枚举只支持字符串；`minLength`、`maxLength`、`minimum`、`maximum`、`minItems`、`maxItems`；类型引用写成 `#/types/名称` 或 `模块#/types/名称`。属性名与操作名用 camelCase，类型名用 PascalCase，错误码以模块名开头。
- 请求的使用范围：默认界面与调试服务都能用；标 `mainOnly` 的只能由主进程发起；标 `debugOnly` 的只经调试服务开放，界面的预加载脚本不暴露。两者都不进入界面请求名单与 `CoreApi`，不能同时标记。
- `mainRequests` 是主进程自己处理、不进入核心的请求，只生成 TypeScript。
- 入口层按 Schema 校验界面发来的参数，核心再按生成的 C++ 代码校验一次；未登记的请求直接拒绝。

## 3. 模块登记

新增模块时，在各层建立同名目录，并在三份模块清单里各登记一项；摘除模块时删除目录并取消登记。

| 清单 | 位置 | 登记方式 |
| --- | --- | --- |
| C++ | `core/src/bootstrap/module-list.cpp` | 一项 `{"模块名", 登记函数}`，登记函数写在 `bootstrap/modules/<模块>.cpp`，在其中创建实现并登记请求 |
| 主进程 | `src/bootstrap/main/module-list.ts` | 引用 `main/modules/<模块>.ts` 里的登记项（模块的 Schema） |
| 渲染进程 | `src/bootstrap/renderer/module-list.ts` | 只登记有界面的模块，引用 `renderer/modules/<模块>.ts` 里的登记项（页面） |

- 取用其他模块共享服务的模块排在提供方之后登记。目前的 C++ 清单是 `system`、`preferences`、`mappers`、`output`、`runtime`、`cartridges`、`debug`：`preferences` 提供 `PreferenceService`（其他模块取用它登记自己的设置项、读取取值、订阅变化）并登记 `preferences.*` 请求，登记自己的外观与画面两组设置项，取值保存在 `config/preferences.json`；`mappers` 提供 `MapperService` 与 `MapperFactory`；`output` 取用 `PreferenceService`（登记“声音”分组的设置项、启动时读取缓冲档位与音量、订阅变化），打开系统声音输出（失败时降级为空输出并写错误日志），提供 `platform::AudioOutput`（共享给 `runtime`）与 `OutputService`，并登记 `output.*` 请求；`runtime` 取用 `MapperFactory`（按匹配结果创建卡带）与 `AudioOutput`，提供 `RuntimeService`，并登记 `runtime.*` 请求、在核心停止时结束模拟线程；`cartridges` 取用 `MapperFactory` 与 `RuntimeService`，提供 `CartridgeLoader` 与 `CartridgeService`，并登记 `cartridges.*` 请求；`debug` 取用 `PreferenceService`（登记“调试服务”分组的设置项）、请求路由与事件订阅源，创建调试服务宿主并登记 `debug.*` 请求，排在最后，所以核心停止时最先停下（先停调试服务，再停被它调用的模块）。`runtime` 只依赖 `mappers` 的契约（`MapperFactory`、卡带映像与匹配结果）和硬件契约，不依赖 `cartridges`，避免模块之间循环。主进程的模块清单是 `system`、`preferences`、`mappers`、`output`、`runtime`、`cartridges`、`debug`，渲染进程的清单目前是 `runtime` 与 `preferences`（`runtime`：运行页：画面、边栏、画面提示、键盘采集，以及文件与机器菜单、命令、状态栏项和常驻组件；`preferences`：首选项页、“设置”菜单的“首选项”命令；登记的内容见下面的“界面登记”）。核心启动参数里可选的 `bundledPluginsPath` 给出预装插件目录，由 `mappers` 模块读取；帧输出由核心入口经 `ModuleRegistry.frames` 给 `runtime` 模块，按键输入经 `Core::sendInput` 进入 `RuntimeService`。
- 主进程模块登记项 `MainModule` 除 `schema` 外，有主进程自己处理的请求（`mainRequests`）时提供 `createMainHandlers`（目前只有 `cartridges` 的 `open`、`recent`、`openRecent`；创建时可用的能力 `MainHandlerContext` 有文件选择窗口、以主进程身份请求核心的依赖，以及最近打开的卡带服务），组装根把它们汇总后交给 `entry/ipc/core/main-request-ipc.ts`；预加载脚本按 `MAIN_REQUEST_NAMES` 暴露 `window.ember.main`。最近打开的卡带由主进程保存（`config/recent-cartridges.json`，格式 `{ version, items: [{ path }] }`，最多 10 个，读不到、不是合法 JSON 或某项不合格时用空清单或跳过那一项，不报错弹窗），路径只在主进程里，界面只拿到编号与显示名；`cartridges.open`、`cartridges.openRecent` 与启动参数 `--cartridge=` 都经 `entry/ipc/cartridges/load-cartridge.ts` 加载：先把路径记入清单再请核心加载，失败时移出清单。
- 硬件不是业务模块，没有请求，不在清单里登记；硬件的装配见 02。
- 硬件目录：契约在 `core/src/contracts/hardware/`，一个契约一个头文件，错误码在 `hardware-error.hpp`；实现在 `core/src/logic/hardware/<模块>/`（命名空间 `ember::logic::hardware`），目前有 `scheduler`、`bus`、`lines`、`cpu-6502`、`ppu-2c02`、`apu-2a03`、`dma-2a03`、`pad-2a03`、`joypad`、`ram`、`cartridge-slot`、`nametable-ram`、`null-device`，说明见 02 第 3.4、6 节；主机型号的装配在 `core/src/bootstrap/machines/<主机型号>.cpp`（目前有 `fc`，`$4016-$4017` 的转接设备 `pad-apu-port.hpp` 也在这里）；测试在 `core/test/hardware/`，公共辅助是 `test-support.hpp`（CPU 测试台）、`fc-test-support.hpp`（手写 6502 程序的小汇编器、构造 iNES 文件、用 nrom 插件装好卡带的 `FcRig`）与 `rom-test-support.hpp`（测试 ROM 的清单项、运行到出结果、两种结果读法、要求复位时的软复位，PPU 与 APU 的 ROM 测试共用）；新增硬件模块只需在 `logic/hardware/` 下建目录，不登记。

### 界面登记

渲染进程的模块登记项 `ShellModule`（`src/ui/shell/shell-registry.ts`）由各模块在 `src/bootstrap/renderer/modules/<模块>.ts` 里写出，汇总在 `src/bootstrap/renderer/module-list.ts`；外壳（`ui/shell`）只渲染登记表，不写死任何入口。外壳自己的登记项（`ui/shell/shell-module.ts`，名称 `shell`）排在最前面，也走同一套检查。

| 登记项 | 内容 |
| --- | --- |
| `name` | 模块名，与 Schema 与目录名一致；其余登记项的标识都以“`<模块名>.`”开头 |
| `pages` | 页面：标识、标题、图标、页面组件 `Component`、`singleton`（默认 true：重复打开聚焦已有标签；false：每次新开一个标签）、`openOnStart`（启动时自动打开）、`closable`（默认 true：false 时标签上没有关闭按钮，也不能被“关闭当前标签”关掉）、`sideBar`（页面声明的边栏 `{ title?, Component }`，没有声明时边栏自动关闭、折叠按钮置灰；切换页面时边栏换成该页面的） |
| `commands` | 命令：标识、名称（字符串，或每次渲染菜单时重新取值的函数，如“上电”与“断电”的切换）、默认快捷键 `defaultShortcut`、动作 `run(shell)`、`enabled(view)`（菜单项是否可用）、`checked(view)`（菜单项是否勾选） |
| `menuItems` | 菜单项：所属菜单（`file` 文件、`machine` 机器、`view` 视图、`settings` 设置、`help` 帮助）、本模块的命令或一个子菜单（二选一）、助记字母、是否在前面加分隔线；没有任何菜单项的菜单不显示；外壳自己的菜单项排在各模块之后（如“文件”菜单的“退出”在最后） |
| `menuItems[].submenu` | 子菜单：标识（以模块名开头）、名称、`entries()`（每次渲染菜单时取当前的项：`id`、`label`、`hint` 右侧提示文字、`disabled`、`separatorBefore`、`run(shell)`）；子菜单项不登记成命令（没有快捷键，项随数据变化，如最近打开的卡带），没有项时这一项置灰 |
| `activityItems` | 活动栏按钮：标识、名称、图标、要打开的页面；每个按钮自动在“视图”菜单最前面生成同名入口（命令 `shell.showActivity.<按钮标识>`） |
| `bottomPanels` | 底部面板页签：标识、标题、内容组件、可选的标题行操作组件 `Actions`（只在选中本页签时显示） |
| `statusItems` | 状态栏项：标识、`align`（`start` 左侧或 `end` 右侧）、组件；右侧最后一项固定是外壳的通知按钮 |
| `Host` | 常驻组件：外壳启动后一直挂载（全屏时也在），没有界面，用来订阅事件、维护模块自己的状态；模块状态变化影响命令的名称与可用状态时调用 `shell.refreshCommands()`，外壳随即重新计算菜单 |

- 汇总与检查在 `ui/shell/build-registry.ts`：模块名合格且不重复；标识（含子菜单）以“模块名.”开头且不重复；菜单项只能使用本模块的命令或子菜单且命令存在，不能两者都是也不能两者都不是；活动栏按钮引用的页面存在；默认快捷键写法合格（修饰键按 Ctrl、Shift、Alt 排列）、不占用保留组合（`Esc`、`Alt+F4`、`Ctrl+A/C/V/X/Z/Y` 与菜单的 `Alt+F/M/V/S/H`）、必须带 Ctrl 或 Alt（`F1` 至 `F24` 除外）、全部命令之间不重复。有误属于程序错误，整个登记表不用，界面只显示一句说明，开发者工具的控制台列出全部问题。与如见不同：快捷键允许 `Ctrl` 与 `Alt` 同时使用（组件库的 `checkShortcut` 禁止，所以这里自己检查），因为 05 第 5 节规定右边栏的默认快捷键是 `Ctrl+Alt+B`。
- 页面和边栏组件收到 `bridge`（预加载脚本暴露的 `window.ember`）；页面、面板与状态项经 `useShell()`（`ui/shell/shell-context.tsx`）取得外壳接口：打开页面、关闭当前标签、切换边栏与底部面板与右边栏与全屏、退出、展开底部面板的某个页签、追加消息（`addMessage({ level, text, time? })`，级别为 `info`、`warning`、`error`，显示在底部面板的“消息”页签，最多保留 1000 条，不写盘）、执行命令、通知外壳刷新命令状态（`refreshCommands()`）。模块之间不互相引用界面代码，只经外壳接口协作；界面层的模块之间也不能引用对方的契约（`ui/runtime` 里最近打开清单的类型取自预加载脚本接口 `EmberBridge` 的返回值，不直接引用 `contracts/cartridges`，否则 `cartridges` 与 `runtime` 的契约会循环依赖）。
- 外壳登记的命令与默认快捷键：文件→退出（无快捷键）；视图→边栏 `Ctrl+B`（当前页面没有边栏时置灰）、底部面板 `Ctrl+J`、右边栏 `Ctrl+Alt+B`（目前置灰，见 05 第 4.6 节）、全屏 `F11`；这几项是勾选项，勾选状态与外壳当前状态一致。快捷键由外壳在 `window` 的 `keydown` 里处理：已经被处理过的按键（`defaultPrevented`，如画面区采集的手柄键）不再响应，所以画面获得焦点时键盘先给画面（F 键与 Ctrl 组合不被画面占用，照常生效）；焦点在文本输入框、多行文字框、下拉框与可编辑区域里时，不带 Ctrl 或 Alt 的快捷键（如 `F7`）留给控件、不触发（按钮、复选框、滑块不算）；置灰的命令快捷键不起作用；用户修改快捷键本阶段没有做。
- 阶段 3a-2：`runtime` 模块在 `ui/runtime/runtime-module.tsx` 里登记（`bootstrap/renderer/modules/runtime.ts` 只创建整个界面唯一的控制器 `RuntimeController` 并传入）：页面 `runtime.run`（标题“运行”，单例，启动时打开，边栏是 `RuntimeSideBar`）与活动栏按钮 `runtime.run`；命令 `runtime.openCartridge`（`Ctrl+O`）、`runtime.ejectCartridge`、`runtime.powerToggle`（`F9`）、`runtime.pauseToggle`（`F8`）、`runtime.softReset`（`F7`）、`runtime.hardReset`（`Ctrl+F7`）、`runtime.muteToggle`（勾选项）；“文件”菜单的子菜单 `runtime.boot`（开机…）与 `runtime.recent`（最近打开）；状态栏项 `runtime.power`、`runtime.host`、`runtime.cartridge`、`runtime.plugin`（左侧）与 `runtime.volume`（右侧）；常驻组件 `RuntimeHost`（把预加载脚本的接口、外壳的消息与命令刷新、组件库的通知接到控制器上）。控制器（`runtime-controller.ts`，不依赖 React）保存机器状态、最近打开的清单与音量，订阅核心事件（`runtime.stateChanged`、`cartridges.loaded`）与核心运行状态（`onCoreStatusChange`：核心进入启动中时状态清成“还没读到”，就绪后重新读取状态、清单与音量并写一条“核心进程已重启”的消息），边栏、状态栏、画面提示与菜单都从它取数据，所以边栏没有打开时状态也是最新的。卡库、设备、mapper 插件、关于对话框、机器菜单的“截图”与整机机型开机仍是后面阶段的事，不占位。
- 阶段 3c：`preferences` 模块在 `ui/preferences/preferences-module.tsx` 里登记（`bootstrap/renderer/modules/preferences.ts` 只引用它）：页面 `preferences.preferences`（标题“首选项”，单例，没有边栏，没有活动栏按钮）、命令 `preferences.open`（`Ctrl+,`）与“设置”菜单里的同名菜单项；主进程一侧的 `bootstrap/main/modules/preferences.ts` 只登记 Schema，并在组装根（`main.ts`）里启动主题同步（`entry/preferences/theme-sync.ts`，把 `appearance.theme` 设成系统主题来源，并让窗口等第一次读到主题再显示）；运行页的画面设置（`ui/runtime/use-display-settings.ts`）自己读取首选项，界面层的模块之间不互相引用。

## 4. 依赖检查

`npm run boundaries` 运行 `tools/check/check-modules.mjs`，规则同 01 第 5 节：

- TypeScript：各层的 `import` 规则、`electron`、Node 内置模块与第三方包的使用范围、文件之间的循环引用；`ui` 层引用 `contracts` 只能用 `import type`。渲染 Worker（`ui` 层里以 `-worker.ts` 结尾的入口）与 `ui` 层同属渲染侧，不能引用 `electron` 与 Node 内置模块（同 `ui` 层）；入口与它经 `import` 依赖的全部文件还不能引用 `react`、`react-dom`、`@rujianjs/ui-kit`、`.tsx` 与样式文件，入口也不能放在 `ui` 层之外。
- C++：各层的 `#include` 规则；`logic` 只能包含 `platform` 的五个抽象（`events/event-sink.hpp`、`requests/cancellation.hpp`、`logging/error-log.hpp`、`streams/frame-output.hpp`、`audio/audio-output.hpp`），硬件模块只能包含前两个；`binding` 只能包含 `bootstrap/core.hpp`；第三方头文件只能出现在指定位置。
- 框架目录不属于任何业务模块，不要求登记：契约目录 `core-gateway`、`shell`、`logging`、`stream-ports`，入口目录 `entry/ipc/core`、`entry/ipc/shell`、`entry/ipc/streams`，界面目录 `ui/shell`。TypeScript 的 `platform` 不能引用 `contracts`，它的实现用自己声明的结构类型。
- 模块：一个模块只能引用另一个模块的契约，模块之间（含 Schema 的 `$ref`）不能循环依赖。
- 硬件：`contracts/hardware` 是硬件契约；`logic/hardware/<模块>` 的每个目录按一个模块计，模块之间（含同族型号）互不引用，业务模块也不能引用硬件模块的实现，都只经 `contracts/hardware`。具体规则：
  - `contracts/hardware` 只能包含 `contracts/hardware`、`shared` 与标准库头文件（没有扩展名的头文件，如 `<cstdint>`），不能包含 `logic`、`platform`、其他模块的契约与任何第三方库（含 `<stdint.h>` 这类带扩展名的头文件）。
  - `logic/hardware/<模块>` 里的文件只能包含自己目录的文件、`contracts/hardware`、`shared` 与 `platform` 的抽象（`platform/events/event-sink.hpp`、`platform/requests/cancellation.hpp`），不能包含其他模块的契约与第三方库；文件必须放在 `logic/hardware/<模块>/` 目录里，不能直接放在 `logic/hardware/` 下。
- 登记：有 Schema 或模块目录的模块都登记在清单里，清单里的项都有对应的文件。
- 官方插件目录：`plugins/<id>/` 的目录名必须等于 `manifest.json` 里的 `id`，目录里只能有 `manifest.json`、`main.js`、`icon.png`。
- 第三方头文件的位置：`quickjs.h` 只能出现在 `infra/mappers/`，`miniz.h` 只能出现在 `infra` 层，`miniaudio.h` 只能出现在 `platform/audio/`，`nlohmann/` 不能出现在 `logic` 层，`sqlite3.h` 只能出现在 `platform/database/`。

`node tools/check/check-modules.mjs --dependents <模块>` 列出直接与间接依赖该模块的全部模块。

## 5. 第三方库

- C++ 第三方库源码放在 `core/third_party/`，随代码提交，编译时不联网；每个目录有 `third-party.json`，清单见 01 第 10 节。QuickJS-ng（只编译引擎核心，不编译提供文件与进程访问的 quickjs-libc）、miniz 与 miniaudio 已由核心库链接（mapper 插件宿主用前两个，QuickJS 的头文件不对外暴露，miniz 的头文件对测试可见；miniaudio 只在 `platform/audio/` 里使用，`core/third_party/miniaudio/miniaudio-impl.c` 单独一个编译单元，只编译播放设备部分——`MA_NO_ENCODING`、`MA_NO_DECODING`、`MA_NO_GENERATION`、`MA_NO_ENGINE`、`MA_NO_NODE_GRAPH`、`MA_NO_RESOURCE_MANAGER` 由 CMake 目标 `ember_miniaudio` 公开定义，第三方代码关闭警告；Windows 用 WASAPI，不需要额外安装；macOS 链接 CoreFoundation、CoreAudio、AudioToolbox 三个系统框架，Linux 链接 dl、pthread、m，这两个平台不在 Windows 上测试）；SQLite 已登记构建目标（`EXCLUDE_FROM_ALL`），核心库链接它时才编译。
- `tools/third-party/third-party.mjs` 汇总 `third-party.json` 与源码引入的 npm 包，生成“关于”对话框用的清单和打包时随应用分发的许可全文（`build/third-party/THIRD_PARTY_NOTICES.txt`）；声明或许可缺失时构建、测试与打包失败。

## 7. 官方插件与打包

- 官方 mapper 插件的源码在 `plugins/<插件>/`（目前只有 `nrom`），目录里是 `manifest.json`，有脚本时还有 `main.js`，可选 `icon.png`；规则见 03 第 3、4 节。
- `npm run plugins:pack`（`tools/build/pack-plugins.mjs`）把每个插件目录打成 `build/plugins/<id>.emap`：只用 Node 自带的 `zlib`，不引入依赖；条目按文件名排序、时间戳固定，同样的输入得到字节相同的包；打包时只检查目录名等于 `id`、清单是 JSON、没有多余的文件，完整的清单与脚本检查在核心安装时做。
- `npm run core:build`、`npm run core:test`（以及经它们的 `npm start`、`npm run package*`）会先打包，所以 `build/plugins` 总是最新；开发版把 `build/plugins` 当作预装目录，正式包把它作为额外资源整个目录复制到应用的 `resources/plugins`（`forge.config.mts` 的 `extraResource`）；主进程启动核心时把这个路径经启动参数 `bundledPluginsPath` 传给 `mappers` 模块，所以开发版与正式包启动后都会自动加载预装的 `nrom`。
- 打包脚本有自己的测试（`test/pack-plugins.test.ts`）：解析生成的 zip、输出可重现、错误用例。

## 8. Electron 冒烟

| 核心重启 | 结束 forge 进程树下命令行含 `node.mojom.NodeService` 的进程（即核心的 utilityProcess，Windows 上按 PID 结束），主进程重新给页面端口，新核心可以响应请求（新核心里没有卡带，电源为 off）；边栏与状态栏重新读取（显示“未开机”，不再显示旧的“运行中”），“消息”里有“核心进程已重启” |

| 退出 | 经浏览器端点关闭全部窗口，应用在 4.5 秒内自行退出（网关等待核心停止的超时是 5 秒，快于它说明模拟线程和帧通道干净停止，没有靠超时强杀；用 `--skip-core-kill` 运行时停止的是正在运行卡带的原核心） |

- 冒烟、延迟测量共用 `tools/dev/dev-support.mjs`：启动开发版（临时用户数据目录、`--cartridge=`、CDP 端口）、等页面、CDP 连接、截图、发按键、按 PID 结束进程树。诊断入口 `window.emberRuntimeDiagnostics` 只在开发版（`import.meta.env.DEV`）里有，正式包没有，所以这两个脚本只用于开发版。

## 9. 延迟与丢帧测量

`node tools/dev/latency-run.mjs`（可选参数：`--rom=`，默认 `nestest/nestest.nes`；`--port=` CDP 端口，默认 9303；`--seconds=` 测量时长，默认 30；`--warmup=` 预热秒数，默认 3；`--no-build`；`--screenshots=目录`）：启动开发版，等卡带运行起来，预热后把渲染 Worker 的统计清零，测量指定时长，读出并打印报告（核心帧率、收到帧率、渲染帧率、画面节拍、各类丢帧、两段延迟的平均、p95、最大、最小）与三条结论（渲染帧率不低于核心帧率的 98%、丢帧合计不超过 1%、两段 p95 之和不超过两帧的时间），结束后只结束自己启动的进程树。统计口径与实测结果见 01 第 7 节“延迟与丢帧测量”。
