# 构建与模块登记

Ember 的构建命令、由 Schema 生成的代码、模块的登记方式与依赖检查。目录分层与依赖规则见 [01-软件架构设计.md](01-软件架构设计.md) 第 4、5 节。

## 1. 命令

在 `ember/` 目录下运行；先 `npm install`。

| 命令 | 用途 |
| --- | --- |
| `npm run schema` | 由 `schema/` 生成核心的 C++ 契约代码、外壳的请求目录（`win32/app/src/contracts/core-gateway/generated/request-catalog.hpp`）、调试服务的 OpenRPC 文档，以及 FC Dev 扩展里调试客户端用的接口文档与类型（见第 2 节） |
| `npm run core:test` | 生成 Schema 代码、打包官方插件，构建并运行 C++ 测试（GoogleTest）；`--` 之后的参数原样交给 CTest，如 `npm run core:test -- -R DebugInspector` 只跑匹配的用例，`-- -E ^Roms/` 排除测试 ROM 用例（它们单个耗时可达数秒、数量最多） |
| `npm run plugins:pack` | 把 `plugins/<插件>/` 打成 `build/ember/plugins/<id>.emap`，见第 7 节 |
| `npm run win32:build` | Win32 原生外壳（计划与目录见 08）：生成 Schema 代码，用 `win32/CMakePresets.json` 的预设 `win7-x64`（MSVC v143 14.44、x64、静态运行库、目标 Windows 7）配置并构建 Release 版，输出在 `build/ember/win32`；`-- --target <名称>` 只构建指定目标 |
| `npm run win32:test` | 用同一套工具链构建 Debug 版核心测试、控件库测试与原生应用测试（`ember_app_tests`）并运行，输出在 `build/ember/win32-test`；`--` 之后的参数交给 CTest（如 `-- -R ^Root\.`） |
| `npm run win32:start` | 以开发方式启动原生外壳：生成 Schema 代码、打包预装插件、帮助站点还没构建过（`build/ember/help/index.html` 不存在）时先构建一次（让“帮助”菜单能打开；已有的不重建，要更新运行 `npm run help:build`）、构建 Release 版的 `ember-win32.exe` 再运行，窗口关闭后返回；`--` 之后的参数交给应用（`--cartridge=路径`、`--user-data-dir=目录`、`--debug-port=端口`、`--debug-token=令牌`） |
| `npm run win32:check` | 控件库结构检查（`tools/check/check-win32-ui-kit.mjs`：`#include` 依赖方向、公共头文件不暴露系统图形头、控件之间不互相引用、源文件登记到 CMake、生成的令牌与图标文件与生成结果一致），再做 Windows 7 兼容检查：列出原生应用、探针、导出表转储工具与控件库画廊导入的全部系统函数，对照 `win32/baseline/win7-sp1-exports.json`；`-- --list-only` 只输出导入清单（该参数只对后一项有效，要单独运行） |
| `npm run win32:reference` | 原生控件库与网页版对照：构建网页版参考页（`win32/ui-kit/tools/reference`）、用 Electron 截图、画廊离屏绘制同样的页面并比较，输出在 `build/ember/win32-reference`；先用 `win32:test` 构建画廊 |
| `npm run win32:shaders` | 由 `win32/app/src/platform/display/screen.hlsl` 重新生成画面着色器的字节码（Windows SDK 的 `fxc`，`vs_4_0_level_9_1` 与 `ps_4_0_level_9_1`）；只在改动着色器时运行，生成的 `screen-shaders.generated.cpp` 提交进仓库 |
| `npm run win32:probe-package` | 生成拿到 Windows 7 上运行的验证包（`ember-probe.exe`、`ember-export-dump.exe`、DLL 清单、`run-on-win7.cmd` 与说明），输出在 `build/ember/win32/win7-package`；在干净的 Windows 7 SP1 上运行后，把 `win7-sp1-exports.json` 放进 `win32/baseline/` |
| `npm run help:build` | 构建帮助文档站点到 `build/ember/help`，见第 10 节；要先运行过 `npm run schema`，并在 `vscode/` 里运行过 `npm run build` |
| `.\debug-win32.ps1` | 在任意目录下启动 Win32 原生外壳的开发版（执行 `npm run win32:start`），脚本后面的参数原样交给应用，如 `--debug-port=5688`、`--user-data-dir=目录` |
| `.\build-win32.ps1` | Win32 原生外壳的构建脚本：安装依赖，编译 Release 版（`npm run win32:build`），再运行依赖边界检查（`npm run boundaries`）与 Win32 检查（`npm run win32:check`），输出 `build\ember\win32\app\Release\ember-win32.exe`；`-SkipCheck` 跳过检查；C++ 测试与网页版对照不在其中；发布包用 `npm run package:win` |
| `npm run lint` | oxlint 检查（`tools`、`test`、`win32/ui-kit/tools`，有警告即失败） |
| `npm run boundaries` | 分层、模块依赖与模块登记检查 |
| `npm test` | 生成代码后运行脚本与代码生成工具的测试（Vitest） |
| `npm run check` | lint、依赖检查、帮助文档构建、Vitest 测试、C++ 核心测试、FC Dev 扩展的检查与 `win32:check` |
| `npm run vscode:check` | 运行 FC Dev 扩展（`vscode/`）的全部检查（类型检查、lint、测试、构建、工具测试，即 `vscode/` 里的 `npm run check`），首次使用前要在 `vscode/` 里 `npm install`，见 07 |
| `npm run package:win` | 发布打包：打预装插件包、构建帮助文档、写出许可全文，用开启升级的 Release 配置构建 `ember-win32.exe`（资源嵌进去，是单个文件），检查导入表在 Windows 7 SP1 基线内，在 `build/ember/release/` 下生成 `Ember-<版本>.exe`（升级用）、`Ember-<版本>.zip`（下载用）与 `Ember-<版本>-学习机开发模拟器.zip`（发给用户），发布见第 11 节 |
| `npm run update:keygen` | 生成升级签名密钥并导出编进程序的公钥（`-- --export-public` 只从已有私钥重新导出公钥），见第 11 节 |
| `npm run update:publish` | 用私钥给 `Ember-<版本>.exe` 签名生成 `latest.json`，并把程序文件、下载用的 `Ember-<版本>.zip` 与清单复制到仓库的升级目录 `updates/ember/windows/`，`-- --dry-run` 只检查并生成，见第 11 节 |
| `npm run resources:pack` | 把预装插件、帮助文档与许可全文打成资源包 `build/ember/resources/resources.zip`（配置构建时自动运行，缺的部分跳过） |
| `node tools/dev/smoke-win32.mjs` | Win32 原生外壳冒烟（46 项）：启动 `ember-win32.exe` 加载测试卡带，用系统输入驱动窗口，检查画面、F8 快捷键、菜单盖在画面上、菜单暂停与继续、运行面板、键盘独占、窗口始终置顶、全屏与正常退出、学习机开机、调试模式项、真实拖放与设备面板、首选项、手柄设置、mapper 插件与“关于”对话框、帮助菜单（要先构建 FC Dev 扩展：在 `vscode/` 里运行 `npm run build`）；`--rom=`、`--no-build`，见 08 第 6 节 |
| `node tools/dev/latency-win32.mjs` | Win32 原生外壳的画面延迟与丢帧测量（`--seconds=`，默认 30；统计由环境变量 `EMBER_WIN_DIAGNOSTICS` 指定的文件在退出时写出），见 08 第 5.5 节 |

构建产物都在仓库根目录的 `build/ember/` 下（不在 `ember/` 里，不入库）：`win32/`（Release 构建，含 `app/Release/ember-win32.exe`）、`win32-test/`（测试用的 Debug 构建）、`win32-reference/`（控件对照的输出）、`core-test/`（核心测试的构建）、`plugins/`（打好的官方插件包）、`resources/`（资源包 `resources.zip`）、`help/`（帮助文档站点）、`third-party/`（第三方开源代码的许可全文）、`release/`（发布包与升级清单）。这些路径统一写在 `tools/build/build-paths.mjs`。

- Windows 上编译 C++ 使用 Visual Studio 自带的 CMake（用 `vswhere` 查找）；PATH 里的 `cmake` 可能是 MinGW 的，不被使用。环境变量 `EMBER_CMAKE` 可指定 `cmake` 可执行文件。
- 编译速度：核心库、应用库与控件库的 MSVC 编译参数带 `/MP`（一个工程内的源文件并行编译），并用预编译头（`core/pch/`、`win32/app/pch/`、`win32/ui-kit/pch/`，只放标准库头文件，不放第三方与系统头文件）。“关于”对话框的编译时间宏（`EMBER_APP_BUILD_DATE`、`EMBER_APP_BUILD_CLOCK`）只加在 `application.cpp` 上（该文件不用预编译头），不加在整个目标上，否则每次配置都会让应用库的全部文件重新编译；生成第三方清单的脚本在内容没变时不写文件，原因相同。
- 界面组件库默认取 `../../rujian-ui-kit`（与 `famiclone` 并列），环境变量 `EMBER_UI_KIT_SOURCE` 可指定其他位置。
- 核心版本取自 `package.json` 的 `version`，编译时经 `EMBER_CORE_VERSION` 传入；应用版本由外壳在启动核心时传入。
- 应用图标：标志图的原件在文档仓库的 `02-设计/Ember/logo.png`（蓝色卡带，相邻的 `logo.xcf` 是源文件）；`resources/icon.ico`（可执行文件的图标，由 `win32/app/resources/ember-win.rc.in` 引用）与 `resources/ember-logo.png`（帮助站点标题栏用的标志）是已经生成的文件，提交进仓库。

## 2. Schema 与生成代码

请求、事件与数据类型只在 `schema/<模块>.schema.json` 中定义。`npm run schema` 生成：

| 生成位置 | 内容 |
| --- | --- |
| `win32/app/src/contracts/core-gateway/generated/request-catalog.hpp` | 外壳用的请求目录：全部请求名、参数与结果类型，外壳自己处理的请求（`mainRequests`）与各请求的使用范围；界面与 `entry` 只经目录引用请求名 |
| `core/src/contracts/<模块>/generated/<模块>.hpp`、`.cpp` | C++ 数据结构、请求名常量、JSON 转换与结构校验 |
| `core/src/contracts/debug/generated/openrpc.hpp`、`.cpp` | 调试服务的 OpenRPC 接口描述文档（全部模块的请求与事件，`debugOnly` 与 `mainOnly` 带 `x-` 标记）的 C++ 常量，`rpc.discover` 返回它；由 `tools/schema-gen/openrpc.mjs` 生成，见 04 第 2.2 节 |
| `vscode/debug/openrpc.json`、`vscode/src/contracts/debug-client/generated/api.ts` | 同一份 OpenRPC 文档与 TypeScript 类型（请求、事件、`EmberApi`），给 FC Dev 扩展的调试客户端用，也是帮助文档里“调试接口手册”的来源（见第 10 节）；由 `tools/schema-gen/sdk-ts.mjs` 生成，见 04 第 8 节与 07 |

- 生成目录不提交，不手写、不手改；内容没变的文件不改写；删除模块后，它的生成目录一并删除。
- Schema 是 JSON Schema 的子集：类型 `string`、`integer`、`number`、`boolean`、`array`、`object`；可空写成 `["string", "null"]`；枚举只支持字符串；`minLength`、`maxLength`、`minimum`、`maximum`、`minItems`、`maxItems`；类型引用写成 `#/types/名称` 或 `模块#/types/名称`。属性名与操作名用 camelCase，类型名用 PascalCase，错误码以模块名开头。
- 请求的使用范围：默认界面与调试服务都能用；标 `mainOnly` 的只能由外壳自己发起；标 `debugOnly` 的只经调试服务开放，外壳不发。两者都不进入界面请求目录，不能同时标记。
- `mainRequests` 是外壳自己处理、不进入核心的请求，只进入外壳的请求目录，由外壳的 `entry` 层登记处理函数（见 08 第 5.4 节）。
- 入口层按 Schema 校验界面发来的参数，核心再按生成的 C++ 代码校验一次；未登记的请求直接拒绝。

## 3. 模块登记

新增模块时，在各层建立同名目录，并在模块清单里登记；摘除模块时删除目录并取消登记。

| 清单 | 位置 | 登记方式 |
| --- | --- | --- |
| C++ | `core/src/bootstrap/module-list.cpp` | 一项 `{"模块名", 登记函数}`，登记函数写在 `bootstrap/modules/<模块>.cpp`，在其中创建实现并登记请求 |
| 外壳 | `win32/app/src/bootstrap/application.cpp` | 在组装根里创建模块并向外壳登记表登记（有界面的模块提供登记项：对话框、命令、菜单项、面板、状态项等），顺序见 08 第 5.8 节 |

- 取用其他模块共享服务的模块排在提供方之后登记。目前的 C++ 清单是 `system`、`preferences`、`mappers`、`output`、`runtime`、`input`、`inspector`、`cartridges`、`machines`、`media`、`filemanager`、`debug`（`filemanager` 取用 `RuntimeService`（经 `runOnSimulation` 访问软驱）与 `FloppyDrive`（与 `media` 共用的软驱 A），创建目录的磁盘存取（`infra/filemanager/file-manager-storage`）、位流格式解码器适配器（`bootstrap/apple-bitstream-decoder`，调用 `disk2-codec`，业务模块不能引用硬件实现，所以由组装根注入）与媒体库服务，登记 `filemanager.*` 请求，核心停止时停下目录监视与后台刷新线程）：`preferences` 提供 `PreferenceService`（其他模块取用它登记自己的设置项、读取取值、订阅变化）并登记 `preferences.*` 请求，登记自己的外观与画面两组设置项，取值保存在 `config/preferences.json`；`mappers` 提供 `MapperService` 与 `MapperFactory`；`output` 取用 `PreferenceService`（登记“声音”分组的设置项、启动时读取缓冲档位与音量、订阅变化），打开系统声音输出（失败时降级为空输出并写错误日志），提供 `platform::AudioOutput`（共享给 `runtime`）与 `OutputService`，并登记 `output.*` 请求（`output.screenshot` 的截图服务需要 `runtime` 提供的 `RuntimeService`，而 `runtime` 排在 `output` 之后，所以截图服务登记一个“启动后”处理（`ModuleRegistry.startHandlers`），全部模块登记完、开始处理请求之前再绑定；截图保存目录读首选项 `debug.outputDirectory`），并提供 `DebugFileWriter`（把文本写进同一个调试输出目录，供 `inspector` 保存跟踪与调用记录）；`runtime` 取用 `MapperFactory`（按匹配结果创建卡带）与 `AudioOutput`，提供 `RuntimeService`，并登记 `runtime.*` 请求、在核心停止时结束模拟线程；`cartridges` 取用 `MapperFactory` 与 `RuntimeService`，提供 `CartridgeLoader` 与 `CartridgeService`，并登记 `cartridges.*` 请求；`machines` 取用 `RuntimeService`（整机机型开机经它的 `bootMachine`），创建 ROM 目录的存储（`<用户数据目录>/roms/<机型>/<文件>`）与机型管理，登记 `machines.*` 请求；`media` 取用 `PreferenceService`（登记“打印机”分组与 `printer.outputDirectory`）、`RuntimeService`（经它的 `useMachine` 在模拟线程里访问打印机，经 `runOnSimulation` 访问软驱与磁带机）、`TapeControl` 与 `FloppyDrive`（主机型号目录创建、`runtime` 模块提供的磁带机与软驱 A，独立于主机，目录把它们交给需要的主机）与事件出口，创建盘片镜像存储、磁带存取（`infra/media/disk-tape-store`：用静态链接的 libav 解码（`libavformat`、`libavcodec`、`libswresample`、`libavutil`，只含音频解码））、打印页存储（1 位灰度 PNG）与介质管理（磁带载入后用一个后台线程独立打开声音文件读一遍，由 `logic/media/tape-analysis` 算出数据线上的声音大小与空白段，结果只存在内存里，经 `media.tapeTimeline` 读取，结束后发 `media.tapeAnalyzed`），登记 `media.*` 请求，并把 `runtime` 模块创建的打印机输出中转（`PrinterOutputRelay`）绑定到打印页存储；`input` 取用 `RuntimeService`（转发按键、鼠标、游戏手柄事件，设置手柄口）、`PreferenceService`（登记“输入”分组的设置项）与事件出口，创建输入注入服务（`logic/input/local-input-service`，同时保存 Family BASIC 键盘的接入状态：不写文件，每次启动都是未接入，经 `RuntimeService::setFamilyKeyboard` 生效并发 `input.familyKeyboardChanged`）、手柄绑定服务（`infra/input/input-binding-registry`，保存到 `<用户数据目录>/config/input-bindings.json`）与手柄输入路由器（`logic/input/pad-input-router`），把路由器经 `RuntimeService::setInputHook` 挂到运行服务上（钩子接口 `InputHook` 在 `contracts/runtime`，所以 `runtime` 不认识 `input`，模块之间没有循环），登记 `input.getBindings`、`input.setBindings`、`input.resetBindings`（界面与调试服务都能用）与注入输入的 `input.key`、`input.mouse`、`input.gamepad`、`input.pad`、`input.releaseAll`（这五个 `debugOnly`）；`inspector` 取用 `RuntimeService`（经它的 `inspect` 在模拟线程读写主机与卡带，把卡带上的存储区合成 `cart.<标识>` 空间，经 `setObserver` 检查监视项）与 `DebugFileWriter`，登记 `inspector.*` 请求（全部 `debugOnly`）；`debug` 取用 `PreferenceService`（登记“调试服务”分组的设置项）、请求路由与事件订阅源，创建调试服务宿主并登记 `debug.*` 请求，排在最后，所以核心停止时最先停下（先停调试服务，再停被它调用的模块）。`runtime` 只依赖 `mappers` 的契约（`MapperFactory`、卡带映像与匹配结果）和硬件契约，不依赖 `cartridges`，避免模块之间循环。外壳的模块（在 `win32/app/src/bootstrap/application.cpp` 里登记）目前是 `shell`、`runtime`、`media`、`debug`、`preferences`、`input`、`machines`、`mappers` 与 `system`，登记的内容见下面的“界面登记”与 08 第 5 节。核心启动参数里可选的 `bundledPluginsPath` 给出预装插件目录（外壳解压出来的 `bundled-plugins/`），由 `mappers` 模块读取；帧输出由核心入口经 `ModuleRegistry.frames` 给 `runtime` 模块，按键输入经 `Core::sendInput` 进入 `RuntimeService`。

## 4. 依赖检查

`npm run boundaries` 运行 `tools/check/check-modules.mjs`，规则同 01 第 5 节：

- C++：各层的 `#include` 规则；`logic` 只能包含 `platform` 的六个抽象（`events/event-sink.hpp`、`requests/cancellation.hpp`、`logging/error-log.hpp`、`streams/frame-output.hpp`、`audio/audio-output.hpp`、`files/file-watcher.hpp`），硬件模块只能包含前两个；第三方头文件只能出现在指定位置。
- 外壳（`win32/app/src`）：目录只能是 `contracts`、`logic`、`infra`、`entry`、`ui`、`platform`、`shared`、`bootstrap` 八层之一；前五层的文件必须放在 `<层>/<模块>/` 目录下（`entry/main-requests` 是请求路由，不属于任何业务模块）；各层可以包含的层：`contracts`（`contracts`、`shared`）、`logic`（`logic`、`contracts`、`shared`）、`infra`（`infra`、`contracts`、`shared`、`platform`）、`entry`（`entry`、`contracts`、`shared`）、`ui`（`ui`、`contracts`）、`platform`（`platform`、`shared`）、`shared`（`shared`），`bootstrap` 可以包含全部；核心的头文件只有 `bootstrap/core.hpp` 与 `platform/streams/frame-output.hpp` 可以被包含，且只在 `infra` 与 `bootstrap`；控件库的头文件（`rujian/`）只在 `ui`、`platform`、`bootstrap`；Windows 系统头文件与 Direct2D、Direct3D 等只在 `platform` 与 `bootstrap`。
- 模块：一个模块只能引用另一个模块的契约，模块之间（含 Schema 的 `$ref`）不能循环依赖。
- 硬件：`contracts/hardware` 是硬件契约；`logic/hardware/<模块>`（主板与主机上的芯片）与 `logic/hardware/mapper-chips/<芯片>`（mapper 电路，如 `mmc3`，可装在卡带上，也可在学习机主板上）的每个目录都按一个模块计，模块之间（含同族型号）互不引用，业务模块也不能引用它们的实现，都只经 `contracts/hardware`。具体规则：
  - `contracts/hardware` 只能包含 `contracts/hardware`、`shared` 与标准库头文件（没有扩展名的头文件，如 `<cstdint>`），不能包含 `logic`、`platform`、其他模块的契约与任何第三方库（含 `<stdint.h>` 这类带扩展名的头文件）。
  - `logic/hardware/<模块>` 与 `logic/hardware/mapper-chips/<芯片>` 里的文件只能包含自己目录的文件、`contracts/hardware`、`shared` 与 `platform` 的抽象（`platform/events/event-sink.hpp`、`platform/requests/cancellation.hpp`），不能包含其他模块的契约与第三方库；文件必须放在 `logic/hardware/<模块>/` 或 `logic/hardware/mapper-chips/<芯片>/` 目录里，不能直接放在 `logic/hardware/`、`logic/hardware/mapper-chips/` 下。
  - `bootstrap/machines/<机型>/` 与 `bootstrap/machines/common/` 里的文件只能包含 `contracts/hardware`、`logic/hardware`、`shared`、`platform` 的两个抽象头文件（同上）与自己目录和 `common` 里的文件，不能包含其他机型、`machine-catalog` 与业务模块，`common` 也不能包含任何机型；机型的文件必须放在 `bootstrap/machines/<机型>/` 或 `bootstrap/machines/common/` 目录里，只有 `machine-catalog` 可以直接放在 `bootstrap/machines/` 下。
- 登记：有 Schema 或模块目录的模块都登记在清单里，清单里的项都有对应的文件。
- 官方插件目录：`plugins/<id>/` 的目录名必须等于 `manifest.json` 里的 `id`，目录里只能有 `manifest.json`、`main.js`、`icon.png`。
- 第三方头文件的位置：`quickjs.h` 只能出现在 `infra/mappers/`，`miniz.h` 只能出现在 `infra` 层，`miniaudio.h` 只能出现在 `platform/audio/`，`nlohmann/` 不能出现在 `logic` 层，`libavcodec/`、`libavformat/`、`libavutil/`、`libswresample/` 的头文件只能出现在 `infra/media/`。

`node tools/check/check-modules.mjs --dependents <模块>` 列出直接与间接依赖该模块的全部模块。

## 5. 第三方库

- C++ 第三方库源码放在 `core/third_party/`，随代码提交，编译时不联网；每个目录有 `third-party.json`，清单见 01 第 10 节。`mesen-ce` 目录只有 `third-party.json` 与许可全文 `LICENSE`（官方 mapper 插件与 MMC2、MMC3 电路的逻辑是重新编写的，来源与许可只登记在这里）。QuickJS-ng（只编译引擎核心，不编译提供文件与进程访问的 quickjs-libc）、miniz 与 miniaudio 已由核心库链接（mapper 插件宿主用前两个，QuickJS 的头文件不对外暴露，miniz 的头文件对测试可见；miniaudio 只在 `platform/audio/` 里使用，`core/third_party/miniaudio/miniaudio-impl.c` 单独一个编译单元，只编译播放设备部分——`MA_NO_ENCODING`、`MA_NO_DECODING`、`MA_NO_GENERATION`、`MA_NO_ENGINE`、`MA_NO_NODE_GRAPH`、`MA_NO_RESOURCE_MANAGER` 由 CMake 目标 `ember_miniaudio` 公开定义，第三方代码关闭警告；Windows 用 WASAPI，不需要额外安装；macOS 链接 CoreFoundation、CoreAudio、AudioToolbox 三个系统框架，Linux 链接 dl、pthread、m，这两个平台不在 Windows 上测试）；FFmpeg 的 libavformat、libavcodec、libswresample、libavutil 以只含音频解码的静态库链接进核心（源码子集在 `core/third_party/ffmpeg/source`，编译好的库与头文件在 `core/third_party/ffmpeg/lib/win32-x64` 与 `include`，`third-party.json` 与许可全文在同一目录，LGPL）：`npm run ffmpeg:build` 用 `tools/ffmpeg` 的脚本重新编译（目标是 Windows 7 基线，只在升级或改编译配置时手动运行，先 `npm run ffmpeg:tools` 安装编译工具），`npm run ffmpeg:check` 核对仓库里编译好的库与源码、编译配置一致；只用于磁带的解码，头文件只在 `infra/media/` 里出现。
- `tools/third-party/third-party.mjs` 汇总 `third-party.json` 与源码引入的 npm 包，生成“关于”对话框用的清单和打包时随应用分发的许可全文（`build/ember/third-party/THIRD_PARTY_NOTICES.txt`）；声明或许可缺失时构建、测试与打包失败。

## 7. 官方插件与打包

- 官方 mapper 插件的源码在 `plugins/<插件>/`（目前有 232 个，覆盖的 mapper 号见 03 第 9 节的台账），目录里是 `manifest.json`，有脚本时还有 `main.js`，可选 `icon.png`；规则见 03 第 3、4 节。每个插件在 `core/test/data/mapper-vectors/<id>.json`（同一插件的多个向量用 `<id>.<后缀>.json`）有测试向量，由 `core/test/mappers/mapper-vectors-test.cpp` 用打好的包逐步验证；步骤有 `cycles`、`reset`、`write`（可带 `bus`、`after`）、`read`（带 `expect`）、`a12`（让 A12 出现指定次数的上升沿）、`video`（让 PPU 依次访问给定的显存地址）、`expectMap`、`expectState`、`expectNametable`、`expectIrq`。向量文件的增减要重新链接测试程序才能被发现。插件包在注册表读取预装目录时都要试创建一次（每个向量用例包含读取全部预装包在内，调试构建下约 0.04 秒），所以插件数量对启动时间的影响很小。
- `npm run plugins:pack`（`tools/build/pack-plugins.mjs`）把每个插件目录打成 `build/ember/plugins/<id>.emap`：只用 Node 自带的 `zlib`，不引入依赖；条目按文件名排序、时间戳固定，同样的输入得到字节相同的包；包末尾附一段 256 字节的可压缩注释（zip 的注释字段，读取时被忽略），保证包总能被压缩得更小（测试会检查每个官方插件包都能压得更小）；打包时只检查目录名等于 `id`、清单是 JSON、没有多余的文件，完整的清单与脚本检查在核心安装时做。
- `npm run core:test`、`npm run win32:start`、`npm run win32:test` 与 `npm run package:win` 会先打包插件，所以 `build/ember/plugins` 总是最新；`npm run resources:pack`（配置构建时自动运行）把 `build/ember/plugins/*.emap`、帮助文档站点与第三方许可全文打成资源包，嵌进 `ember-win32.exe`；外壳启动时把预装插件解压到用户数据目录的 `bundled-plugins/`（资源包的指纹变化时重新解压），经核心启动参数 `bundledPluginsPath` 交给 `mappers` 模块，所以开发版与发布版启动后都会自动加载预装的 `nrom`。
- 打包脚本有自己的测试（`test/pack-plugins.test.ts`）：解析生成的 zip、输出可重现、错误用例。
- 仓库的 `ember/roms/`（`sb97.rom`、`sb2000_bios.rom`、`bbg1_bios.rom`、`bbg98_bios.rom`、`pec9588.rom`、`pec586.rom`、`pec686f.rom`、`yuxing_v8.0-c.rom`、`yuxing_v8.2-d.rom`、`yuxing_v8.3-d.rom`、`yuxing_v9.0-98.rom`、`cec1_v1.1a.rom`、`cec1_v1.21.rom`，都是不带文件头的纯 ROM 文件，按机型命名（真正的 BIOS 文件名里带 `bios`，其余机型的 ROM 不叫 BIOS），也是仓库里各处测试与工具使用的 ROM）只供开发与测试使用；发给用户的压缩包也包含 `roms/` 目录下的文件（见第 11 节），核心也不会自动装载它们：程序没有默认 ROM，用户在首选项里自己添加（见 01 第 9 节）；外壳冒烟把其中一个复制进实例的用户数据目录，FC Dev 的测试经 `machines.setRom` 添加。

## 8. Win32 冒烟

`node tools/dev/smoke-win32.mjs`（可选参数：`--rom=` 相对 `core/test/data` 或绝对路径，默认 `nestest/nestest.nes`；`--no-build` 跳过构建；环境变量 `EMBER_WIN_EXE` 指定要测的 `ember-win32.exe`，默认是 `build/ember/win32/app/Release/ember-win32.exe`）启动原生外壳，用系统的鼠标与键盘输入驱动窗口，全部通过时退出码为 0（目前 45 项）。每个场景启动一个新实例，用临时的 `--user-data-dir`（不影响已打开的 Ember，也避开单实例锁）；FC Dev 扩展要先构建（在 `vscode/` 里运行 `npm run build`）：

| 场景 | 检查内容 |
| --- | --- |
| 一：卡带与外壳 | 启动后出现窗口；卡带的画面显示出来；没有开启调试服务时系统栏没有“调试模式”；F8 暂停并显示“已暂停”提示；“机器”菜单盖在画面上，Esc 关闭；菜单里选“继续”撤掉提示、选“暂停”显示提示；点系统栏的运行按钮展开运行面板，点画面后自动收起；经典 FC 不独占键盘，画面持有焦点时 F8 仍触发外壳的暂停；“窗口始终置顶”勾选后置顶、再点一次取消；关闭窗口后进程正常退出 |
| 二：全屏 | F11 进入全屏，窗口比原来大；正常退出 |
| 三：学习机开机 | 先把 `rom/sb2000_bios.rom` 复制进实例的 ROM 目录，经菜单选小霸王 2000 后开机，画面铺满显示区；正常退出 |
| 四：调试服务与设备 | 启动参数开启调试服务后系统栏出现“调试模式”，调试服务在监听（经调试服务核对）；经调试服务让小霸王 2000 开机；学习机独占键盘，画面持有焦点时 F8 不触发外壳的暂停；真实地把软盘镜像拖进窗口，载入了软驱 A；点设备按钮展开设备面板，软驱 A 一行显示盘片名；写保护按钮与取出按钮生效，取出后盘片名变成“空” |
| 五：首选项与手柄设置 | Ctrl+, 打开首选项，把主题选成“浅色”并经调试服务核对已保存，Esc 关闭；“设置”菜单里打开手柄设置，点手柄图上的键再按 Q，玩家 1 的绑定里有 Q（经调试服务核对） |
| 六：mapper 插件、帮助与关于 | 核心里有预装的 mapper 插件；“设置”菜单里打开 mapper 插件对话框，Esc 关闭；“帮助”菜单里打开“关于 Ember”，Esc 关闭；正常退出（“帮助文档”与“更新记录”会启动用户的默认浏览器，冒烟里不点） |

- 只结束本脚本启动的进程（按 PID），不按进程名结束任何进程，不影响用户已经打开的 Ember；结束后删除临时的用户数据目录。
- 窗口里的操作用系统的鼠标与键盘输入完成（坐标按窗口的逻辑像素），运行期间会抢前台窗口，不要同时操作键盘与鼠标；驱动脚本在 `tools/dev/win32-dev-support.mjs`，步骤写法见该文件的说明。
- 核心启动时会打开系统声音设备；没有声卡或设备被独占时降级为无声并写错误日志，冒烟照常通过，冒烟本身不检查声音。

## 9. 延迟与丢帧测量

`node tools/dev/latency-win32.mjs`（可选参数 `--seconds=` 测量时长，默认 30）：启动原生外壳（脚本自己设置环境变量 `EMBER_WIN_DIAGNOSTICS`，让程序退出时写出诊断文件），运行指定时长，读出诊断文件，打印帧计数与每一帧从核心发布到画出的延迟（平均、p95、最大），并检查“画出不少于 98%、丢帧不超过 1%、p95 不超过两帧的时间”，结束后只结束自己启动的进程。统计口径与实测结果见 08 第 5.5 节。

| `help/.vitepress/theme/` | 站点主题：引入组件库源码的令牌、主题与标题栏样式（经 `config.mts` 里的 `@ember-ui-kit` 别名，位置同界面打包，见第 1 节的 `EMBER_UI_KIT_SOURCE`），`style.css` 把 VitePress 的颜色与字体变量指到令牌，`HelpTitleBar.ts` 是与主窗口一致的标题栏，`PageScrollbar.ts` 是标题栏与导航栏下面的覆盖式页面滚动条；`config.mts` 的 head 脚本给 html 写 `theme-dark`、`theme-light`（与 VitePress 的 `dark` 同步）；`help/.vitepress/tsconfig.json` 与 `theme/env.d.ts` 让编辑器检查主题的 ts 文件（引入 VitePress 客户端类型，CSS 与图片导入才有类型声明），不参与构建与 `npm run typecheck` |

- `npm run help:build`（`tools/build/build-help.mjs`）先运行 `vscode/tools/gen/gen-debug-api-docs.mjs`，把 `vscode/debug/openrpc.json` 生成成 `help/api/`，再用 VitePress 把 `help/` 构建到 `build/ember/help`（路径写在 `tools/build/build-paths.mjs`）；存在死链接时构建失败。要先运行过 `npm run schema`，并在 `vscode/` 里运行过 `npm run build`（生成脚本用扩展的编译产物）。
- FC Dev 手册的导入也在 `npm run help:build` 里完成，顺序在生成 `help/api/` 之后、VitePress 构建之前：先运行仓库根目录 `vscode/tools/gen/gen-sb2000-api-doc.mjs`、`vscode/tools/gen/gen-sb2000-symbols-doc.mjs` 与 `vscode/tools/gen/gen-sb2000-examples-doc.mjs`（从头文件注释、`sb2000.inc` 与 `apps/sb2000/examples` 的示例源码重新生成 `vscode/targets/sb2000/` 下的三份参考文档，没有变化时文件不变），再由 `tools/build/import-fcdev-docs.mjs` 按 `vscode/docs/topics.json` 的登记把全部使用文档导入 `help/fcdev/`：每个主题一页（页名就是主题名）加一个由登表生成的概述页，每页开头有“由导入生成、不要手改”的标记。导入时文档之间的相对链接改成站内页面，指向文档目录之外（头文件、链接配置、目录）的链接改成普通文字，正文中代码之外的尖括号与双花括号转义（否则 VitePress 会当成 Vue 模板），文档里单独成节的“## 目录”去掉（帮助页右边有自动生成的页内大纲，源文件里的目录是给单独阅读用的），已不再登记的页面删除；侧边栏的分组（通用、NES、SB2000、SB97、裕兴、步步高、中华学习机）与导入用同一份规则，在 `import-fcdev-docs.mjs` 的 `sidebarGroups` 里，`config.mts` 直接引用。新增或改名 FC Dev 的使用文档只改 `vscode/docs`（登记到 `topics.json`），帮助站点下次构建自动跟上。
- `npm run package:win` 与 `npm run check` 会先构建帮助文档；`npm run resources:pack`（配置构建时自动运行）把 `build/ember/help` 打进资源包，嵌进 `ember-win32.exe`（帮助文档还没构建时跳过并提示）。
- 站点内的链接一律用 `.html` 结尾（不开 `cleanUrls`），因为外壳在本机回环地址上提供的只读服务（见 08 第 5.6 节）按文件路径提供页面。
- 站点使用的 VitePress、Vue 等运行时代码与字体登记在第三方清单里（`tools/third-party/third-party.mjs` 的 `HELP_SITE_PACKAGES`，只登记分发的包本身，构建工具不进安装包）。
- 修改界面或用户可见的行为时，同步 `help/manual/` 的对应页；修改调试协议的规则时同步 04 文档与 `help/debug/`；修改 mapper 插件规范或插件宿主的行为（清单字段、`ctx` 接口、限制、安装规则）时同步 03 文档与 `help/plugin/`；修改 FC Dev 的使用文档、头文件注释或 `sb2000.inc` 时不用改 `help/`（`help/fcdev/` 是导入的），重新运行 `npm run help:build` 即可。

## 11. 发布升级

正式版的升级文件放在仓库根目录的 `updates/ember/windows/`，提交并推送后由 GitHub Pages 经自有域名 `fcdev.cn` 对外（程序里的升级地址是 `https://fcdev.cn/updates/ember/windows`，客户端的检查、签名校验与替换见 01 第 11 节）；0.3.18 及更早的版本从阿里云 OSS 取升级，0.3.19 是最后一次上传到 OSS，之后不再更新那里。

| 步骤 | 做法 |
| --- | --- |
| 1 | 把 `package.json` 的 `version` 升到新版本（升级按版本号比较，新版本必须大于已发布的版本），并在 `help/manual/changelog.md` 最上面加该版本一节（只写用户可见的功能变化）：用户升级后第一次启动时会自动看到这一页（见 01 第 11 节） |
| 2 | 第一次发布前运行 `npm run update:keygen` 生成签名密钥：私钥写到文档仓库的 `01-文档/密钥/ember-update-signing-key.pem`（与 famiclone 并列，不进 Ember 仓库，生成后记得提交文档仓库；`EMBER_UPDATE_KEY` 可指定别的文件），公钥导出到 `win32/app/src/shared/update/update-public-key.hpp`（提交进仓库）；以后不要重新生成，换了密钥，已经发布的程序就不再接受新的升级 |
| 3 | `npm run package:win`：打预装插件包、构建帮助文档、写出许可全文，用开启升级的 Release 配置构建 `ember-win32.exe`，检查导入表，生成 `build/ember/release/Ember-<版本>.exe`（升级用）、`Ember-<版本>.zip`（下载用）与 `Ember-<版本>-学习机开发模拟器.zip`（发给用户） |
| 4 | `npm run update:publish -- --dry-run`：核对程序里编译进去的公钥就是这把私钥的公钥，生成并校验签名清单 `build/ember/release/latest.json`，打印要复制的文件；不写仓库 |
| 5 | `npm run update:publish`：先把 `Ember-<版本>.exe` 与 `Ember-<版本>.zip`、最后把 `latest.json` 复制到仓库的 `updates/ember/windows/`（客户端按 `latest.json` 找新版本，必须在程序文件复制好之后才对外可见；程序文件名带版本号，新版本不会覆盖以前发布的） |
| 6 | 发给用户的 `Ember-<版本>-学习机开发模拟器.zip` 不随上传复制，留在 `build/ember/release/`，由维护者手动发出，不进仓库 |
| 7 | 在 `site/` 目录运行 `npm run build`，更新首页与帮助页（读取 `latest.json` 与压缩包名，见 `site/scripts/build.mjs`） |
| 8 | 提交并推送仓库：`index.html`、`site/`，以及 `updates/ember/windows/` 下新增的文件（exe、zip、`latest.json`）进入提交，推送后由 GitHub Pages 对外（有几分钟的缓存延迟，`latest.json` 晚一点才会让新版本可见）；每个版本的 exe 都留在仓库里，仓库会随版本增长 |

- 脚本只做检查、签名与复制，不改动 `package.json`，也不执行 git 提交；公钥与私钥对不上、签名生成后校验不过时不写仓库。
- 分发给用户的是 `Ember-<版本>-学习机开发模拟器.zip`（里面是 `Ember.exe`、`LICENSE.txt`、`THIRD_PARTY_NOTICES.txt`，以及 `roms/` 目录下的文件），解压即用，没有安装步骤。
- 纯函数部分（清单生成与签名、复制计划、公钥核对、资源打包）有单元测试（`test/update-signing.test.ts`、`test/pack-resources.test.ts`）。升级流程的端到端演练：把用 `npm run package:win` 的配置构建出的 `ember-win32.exe` 复制到临时目录，另做一个文件内容不同的“新版本”，用 `tools/release/update-signing.mjs` 的 `buildManifest` 签名，在本机起一个只服务 `latest.json` 与这个文件的 HTTP 服务，设置环境变量 `EMBER_UPDATE_FEED_URL=http://127.0.0.1:<端口>`（只接受 https 或指向 `127.0.0.1` 的 http）并用 `--user-data-dir` 启动，等自动检查、下载暂存后点标题栏的“更新”：旧进程退出、程序文件被替换、新进程启动即为通过；在线地址的访问不在自动测试里。
