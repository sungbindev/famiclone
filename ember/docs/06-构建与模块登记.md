# 构建与模块登记

Ember 的构建命令、由 Schema 生成的代码、模块的登记方式与依赖检查。目录分层与依赖规则见 [01-软件架构设计.md](01-软件架构设计.md) 第 4、5 节。

## 1. 命令

在 `ember/` 目录下运行；先 `npm install`。

| 命令 | 用途 |
| --- | --- |
| `npm run schema` | 由 `schema/` 生成 TypeScript 与 C++ 代码 |
| `npm run core:build` | 生成 Schema 代码、打包官方插件并编译原生模块，输出 `core/build/Release/ember_core.node` |
| `npm run core:test` | 生成 Schema 代码、打包官方插件，构建并运行 C++ 测试（GoogleTest） |
| `npm run plugins:pack` | 把 `plugins/<插件>/` 打成 `build/plugins/<id>.emap`，见第 7 节 |
| `npm start` | 生成代码、打包插件、编译原生模块，再启动开发版 |
| `.\debug.ps1` | 在任意目录下启动开发版（切到项目目录后执行 `npm start`） |
| `npm run typecheck` | 生成代码后做 TypeScript 类型检查 |
| `npm run lint` | oxlint 检查（有警告即失败） |
| `npm run boundaries` | 分层、模块依赖与模块登记检查 |
| `npm test` | 生成代码后运行 TypeScript 测试（Vitest） |
| `npm run check` | 类型检查、lint、依赖检查、TypeScript 测试与 C++ 测试 |
| `npm run package` | 打包当前平台的应用 |
| `npm run package:win` | 打包 Windows x64 版 |
| `npm run make:win` | 生成 Windows x64 安装程序 |
| `npm run package:mac` | 打包 macOS arm64 版（只在苹果电脑上运行） |
| `node tools/dev/smoke-run.mjs` | Electron 冒烟，见第 8 节 |

- Windows 上编译 C++ 使用 Visual Studio 自带的 CMake（用 `vswhere` 查找）；PATH 里的 `cmake` 可能是 MinGW 的，不被使用。环境变量 `EMBER_CMAKE` 可指定 `cmake` 可执行文件。
- 界面组件库默认取 `../../rujian-ui-kit`（与 `famiclone` 并列），环境变量 `EMBER_UI_KIT_SOURCE` 可指定其他位置。
- 核心版本取自 `package.json` 的 `version`，编译时经 `EMBER_CORE_VERSION` 传入；应用版本由主进程在启动核心时传入。

## 2. Schema 与生成代码

请求、事件与数据类型只在 `schema/<模块>.schema.json` 中定义。`npm run schema` 生成：

| 生成位置 | 内容 |
| --- | --- |
| `src/contracts/<模块>/generated/<模块>.ts` | 请求名、事件名、数据类型、请求名到类型的对照，以及入口校验用的 Schema |
| `src/contracts/core-gateway/generated/core-api.ts` | 汇总全部模块：请求名单、事件名单、`CoreApi` 与全部 Schema |
| `core/src/contracts/<模块>/generated/<模块>.hpp`、`.cpp` | C++ 数据结构、请求名常量、JSON 转换与结构校验 |

- 生成目录不提交，不手写、不手改；内容没变的文件不改写；删除模块后，它的生成目录一并删除。
- Schema 是 JSON Schema 的子集：类型 `string`、`integer`、`number`、`boolean`、`array`、`object`；可空写成 `["string", "null"]`；枚举只支持字符串；`minLength`、`maxLength`、`minimum`、`maximum`、`minItems`、`maxItems`；类型引用写成 `#/types/名称` 或 `模块#/types/名称`。属性名与操作名用 camelCase，类型名用 PascalCase，错误码以模块名开头。
- 请求的使用范围：默认界面与调试服务都能用；标 `mainOnly` 的只能由主进程发起；标 `debugOnly` 的只经调试服务开放，界面的预加载脚本不暴露。两者都不进入界面请求名单与 `CoreApi`，不能同时标记。
- `mainRequests` 是主进程自己处理、不进入核心的请求，只生成 TypeScript。
- 入口层按 Schema 校验界面发来的参数，核心再按生成的 C++ 代码校验一次；未登记的请求直接拒绝。

## 3. 模块登记

新增模块时，在各层建立同名目录，并在三份模块清单里各登记一项；摘除模块时删除目录并取消登记。

| 清单 | 位置 | 登记方式 |
| --- | --- | --- |
| C++ | `core/src/bootstrap/module-list.cpp` | 一项 `{"模块名", 登记函数}`，登记函数写在 `bootstrap/modules/<模块>.cpp`，在其中创建实现并登记请求 |
| 主进程 | `src/bootstrap/main/module-list.ts` | 引用 `main/modules/<模块>.ts` 里的登记项（模块的 Schema） |
| 渲染进程 | `src/bootstrap/renderer/module-list.ts` | 只登记有界面的模块，引用 `renderer/modules/<模块>.ts` 里的登记项（页面） |

- 取用其他模块共享服务的模块排在提供方之后登记。目前的 C++ 清单是 `system`、`mappers`、`runtime`、`cartridges`：`mappers` 提供 `MapperService` 与 `MapperFactory`；`runtime` 取用 `MapperFactory`（按匹配结果创建卡带），提供 `RuntimeService`，并登记 `runtime.*` 请求、在核心停止时结束模拟线程；`cartridges` 取用 `MapperFactory` 与 `RuntimeService`，提供 `CartridgeLoader` 与 `CartridgeService`，并登记 `cartridges.*` 请求。`runtime` 只依赖 `mappers` 的契约（`MapperFactory`、卡带映像与匹配结果）和硬件契约，不依赖 `cartridges`，避免模块之间循环。主进程的模块清单是 `system`、`mappers`、`runtime`、`cartridges`，渲染进程的清单目前只有系统页面。核心启动参数里可选的 `bundledPluginsPath` 给出预装插件目录，由 `mappers` 模块读取；帧输出由核心入口经 `ModuleRegistry.frames` 给 `runtime` 模块，按键输入经 `Core::setButtons` 进入 `RuntimeService`。
- 主进程模块登记项 `MainModule` 除 `schema` 外，有主进程自己处理的请求（`mainRequests`）时提供 `createMainHandlers`（目前只有 `cartridges` 的 `open`），组装根把它们汇总后交给 `entry/ipc/core/main-request-ipc.ts`；预加载脚本按 `MAIN_REQUEST_NAMES` 暴露 `window.ember.main`。
- 硬件不是业务模块，没有请求，不在清单里登记；硬件的装配见 02。
- 硬件目录：契约在 `core/src/contracts/hardware/`，一个契约一个头文件，错误码在 `hardware-error.hpp`；实现在 `core/src/logic/hardware/<模块>/`（命名空间 `ember::logic::hardware`），目前有 `scheduler`、`bus`、`lines`、`cpu-6502`、`ppu-2c02`、`dma-2a03`、`pad-2a03`、`joypad`、`ram`、`cartridge-slot`、`nametable-ram`、`null-device`，说明见 02 第 3.4、6 节；主机型号的装配在 `core/src/bootstrap/machines/<主机型号>.cpp`（目前有 `fc`）；测试在 `core/test/hardware/`，公共辅助是 `test-support.hpp`（CPU 测试台）与 `fc-test-support.hpp`（手写 6502 程序的小汇编器、构造 iNES 文件、用 nrom 插件装好卡带的 `FcRig`）；新增硬件模块只需在 `logic/hardware/` 下建目录，不登记。

## 4. 依赖检查

`npm run boundaries` 运行 `tools/check/check-modules.mjs`，规则同 01 第 5 节：

- TypeScript：各层的 `import` 规则、`electron`、Node 内置模块与第三方包的使用范围、文件之间的循环引用；`ui` 层引用 `contracts` 只能用 `import type`。
- C++：各层的 `#include` 规则；`logic` 只能包含 `platform` 的四个抽象（`events/event-sink.hpp`、`requests/cancellation.hpp`、`logging/error-log.hpp`、`streams/frame-output.hpp`），硬件模块只能包含前两个；`binding` 只能包含 `bootstrap/core.hpp`；第三方头文件只能出现在指定位置。
- 框架目录不属于任何业务模块，不要求登记：契约目录 `core-gateway`、`shell`、`logging`、`stream-ports`，入口目录 `entry/ipc/core`、`entry/ipc/shell`、`entry/ipc/streams`，界面目录 `ui/shell`。TypeScript 的 `platform` 不能引用 `contracts`，它的实现用自己声明的结构类型。
- 模块：一个模块只能引用另一个模块的契约，模块之间（含 Schema 的 `$ref`）不能循环依赖。
- 硬件：`contracts/hardware` 是硬件契约；`logic/hardware/<模块>` 的每个目录按一个模块计，模块之间（含同族型号）互不引用，业务模块也不能引用硬件模块的实现，都只经 `contracts/hardware`。具体规则：
  - `contracts/hardware` 只能包含 `contracts/hardware`、`shared` 与标准库头文件（没有扩展名的头文件，如 `<cstdint>`），不能包含 `logic`、`platform`、其他模块的契约与任何第三方库（含 `<stdint.h>` 这类带扩展名的头文件）。
  - `logic/hardware/<模块>` 里的文件只能包含自己目录的文件、`contracts/hardware`、`shared` 与 `platform` 的抽象（`platform/events/event-sink.hpp`、`platform/requests/cancellation.hpp`），不能包含其他模块的契约与第三方库；文件必须放在 `logic/hardware/<模块>/` 目录里，不能直接放在 `logic/hardware/` 下。
- 登记：有 Schema 或模块目录的模块都登记在清单里，清单里的项都有对应的文件。
- 官方插件目录：`plugins/<id>/` 的目录名必须等于 `manifest.json` 里的 `id`，目录里只能有 `manifest.json`、`main.js`、`icon.png`。
- 第三方头文件的位置：`quickjs.h` 只能出现在 `infra/mappers/`，`miniz.h` 只能出现在 `infra` 层，`nlohmann/` 不能出现在 `logic` 层，`sqlite3.h` 只能出现在 `platform/database/`。

`node tools/check/check-modules.mjs --dependents <模块>` 列出直接与间接依赖该模块的全部模块。

## 5. 第三方库

- C++ 第三方库源码放在 `core/third_party/`，随代码提交，编译时不联网；每个目录有 `third-party.json`，清单见 01 第 10 节。QuickJS-ng（只编译引擎核心，不编译提供文件与进程访问的 quickjs-libc）与 miniz 已由核心库链接（mapper 插件宿主用它们，QuickJS 的头文件不对外暴露，miniz 的头文件对测试可见）；SQLite 已登记构建目标（`EXCLUDE_FROM_ALL`），核心库链接它时才编译。
- `tools/third-party/third-party.mjs` 汇总 `third-party.json` 与源码引入的 npm 包，生成“关于”对话框用的清单和打包时随应用分发的许可全文（`build/third-party/THIRD_PARTY_NOTICES.txt`）；声明或许可缺失时构建、测试与打包失败。

## 6. 测试数据

- C++ 测试放在 `core/test/`，按层与模块分目录（硬件测试在 `core/test/hardware/`）；测试数据放在 `core/test/data/<名称>/`，每个目录有 `README.md` 说明来源与用途；目前有 `nestest`（CPU）与 PPU 的 9 组测试 ROM：`blargg-ppu-tests`、`sprite-hit-tests`、`sprite-overflow-tests`、`vbl-nmi-timing`、`ppu-vbl-nmi`、`oam-read`、`oam-stress`、`ppu-open-bus`、`ppu-read-buffer`，由 `core/test/hardware/ppu-rom-test.cpp` 运行（结果的读法见各目录的 README）；另有 `test-plugins`（只用于测试的 mapper 插件源文件，不是 ROM）。
- 测试用的卡带经 iNES 解析加真实的 mapper 插件装配：经典 FC 的 ROM 用官方的 nrom 插件（带测试 ROM 需要的 `$6000-$7FFF` 8K RAM），ppu_read_buffer 用的 mapper 3 用 `core/test/data/test-plugins/cnrom/` 的测试插件（测试时现场打包）；核心程序和测试代码里都没有 mapper 的替身实现。
- 插件与卡带的测试在 `core/test/mappers/`（插件包、清单、沙箱、卡带、插件登记）与 `core/test/cartridges/`（iNES 解析、卡带装载、卡带服务），运行服务的测试在 `core/test/runtime/`（真实的 nrom 插件、不限速的模拟线程，覆盖连续运行与帧输出、暂停与继续、断电与上电、软硬复位、运行中换卡带、装配失败保持原状、脚本出错暂停、按键、帧节拍、停止时无死锁），公共辅助是 `core/test/support/plugin-test-support.hpp`（用 miniz 现场生成 `.emap` 包、读取官方插件包、临时目录、记录型错误日志与事件发布）与 `core/test/support/runtime-test-support.hpp`（线程安全的事件与帧记录、轮询等待、按 mapper 号构造 iNES 文件、用 RAM 标记区分冷热启动的小程序）。官方插件包的位置经编译参数 `EMBER_PLUGIN_DIR`（指向 `build/plugins`）传入，`npm run core:test` 会先打包；直接用 CMake 构建测试时要先运行 `npm run plugins:pack`。
- 测试在 Debug 配置下构建；ROM 测试要模拟上万帧画面，所以 `core/CMakeLists.txt` 在测试构建里对 MSVC 改用 `/O2`、去掉 `/RTC1` 并关闭标准库的迭代器检查（`_ITERATOR_DEBUG_LEVEL=0`），全部 C++ 测试约十几秒；发布构建不受影响。
- 测试经编译参数 `EMBER_TEST_DATA_DIR`（CMake 传入，指向 `core/test/data`）定位数据，不依赖运行时的工作目录。
- `.gitignore` 对 `core/test/data` 里的 `.log` 放行，`.gitattributes` 把 `.nes` 当二进制、`core/test/data` 里的 `.log` 不做换行转换。

## 7. 官方插件与打包

- 官方 mapper 插件的源码在 `plugins/<插件>/`（目前只有 `nrom`），目录里是 `manifest.json`，有脚本时还有 `main.js`，可选 `icon.png`；规则见 03 第 3、4 节。
- `npm run plugins:pack`（`tools/build/pack-plugins.mjs`）把每个插件目录打成 `build/plugins/<id>.emap`：只用 Node 自带的 `zlib`，不引入依赖；条目按文件名排序、时间戳固定，同样的输入得到字节相同的包；打包时只检查目录名等于 `id`、清单是 JSON、没有多余的文件，完整的清单与脚本检查在核心安装时做。
- `npm run core:build`、`npm run core:test`（以及经它们的 `npm start`、`npm run package*`）会先打包，所以 `build/plugins` 总是最新；开发版把 `build/plugins` 当作预装目录，正式包把它作为额外资源整个目录复制到应用的 `resources/plugins`（`forge.config.mts` 的 `extraResource`）；主进程启动核心时把这个路径经启动参数 `bundledPluginsPath` 传给 `mappers` 模块，所以开发版与正式包启动后都会自动加载预装的 `nrom`。
- 打包脚本有自己的测试（`test/pack-plugins.test.ts`）：解析生成的 zip、输出可重现、错误用例。

## 8. Electron 冒烟

`node tools/dev/smoke-run.mjs`（可选参数：`--rom=` 相对 `core/test/data` 或绝对路径，默认 `nestest/nestest.nes`；`--port=` CDP 调试端口，默认 9302；`--seconds=` 每段观察的秒数，默认 3；`--no-build` 跳过 `npm run schema` 与 `npm run core:build`；`--skip-core-kill` 跳过结束核心进程的检查）启动开发版并经 CDP 检查整条链路，全部通过时退出码为 0：

| 检查 | 内容 |
| --- | --- |
| 启动 | 用 `--remote-debugging-port`、临时的 `--user-data-dir`（不影响已打开的 Ember，也避开单实例锁）与 `--cartridge=<ROM>` 启动 `electron-forge start`；主进程在核心启动后以主进程的身份调用 `cartridges.load` |
| 暴露的接口 | 渲染进程没有 `require`、`process`、`ipcRenderer`；`cartridges.load` 不暴露，`main.cartridges.open` 与 `streams.requestPorts` 已暴露 |
| 运行 | `runtime.status` 通电并运行，卡带是 `nrom`、主机是 `fc`；帧号与周期数在增长，帧率约 60 帧/秒 |
| 画面 | 在页面里经 CDP 临时注册 `message` 监听（只存在于这次会话，不写进界面代码）、调用 `requestPorts()`，收到端口与画面帧：256x240、`rgba8`、245760 字节、帧号递增、每秒约 60 帧 |
| 输入 | 经输入端口发开始键，nestest 的选单画面改变（证明按键经核心宿主与命令队列送达模拟线程）；非法输入被丢弃，画面继续 |
| 重载 | `Page.reload` 后重新请求端口，画面帧继续到达 |
| 核心重启 | 结束 forge 进程树下命令行含 `node.mojom.NodeService` 的进程（即核心的 utilityProcess，Windows 上按 PID 结束），主进程重新给页面端口，新核心可以响应请求（新核心里没有卡带，电源为 off） |
| 退出 | 经浏览器端点关闭全部窗口，应用在 4.5 秒内自行退出（网关等待核心停止的超时是 5 秒，快于它说明模拟线程和帧通道干净停止，没有靠超时强杀；用 `--skip-core-kill` 运行时停止的是正在运行卡带的原核心） |

- 只结束本脚本启动的 forge 进程树与它下面的核心进程（按 PID），不按进程名结束任何进程；结束后删除临时的用户数据目录。
- 首次运行要先构建主进程、预加载脚本与界面，等待页面出现的上限是 3 分钟；Vite 的端口被占用时会自动换一个，`--port` 只影响 CDP。
- 核心重启的检查只在 Windows 上做；macOS 的脚本路径与冒烟不在 Windows 上测试。
