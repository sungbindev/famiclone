# 构建与模块登记

Ember 的构建命令、由 Schema 生成的代码、模块的登记方式与依赖检查。目录分层与依赖规则见 [01-软件架构设计.md](01-软件架构设计.md) 第 4、5 节。

## 1. 命令

在 `ember/` 目录下运行；先 `npm install`。

| 命令 | 用途 |
| --- | --- |
| `npm run schema` | 由 `schema/` 生成 TypeScript 与 C++ 代码 |
| `npm run core:build` | 生成 Schema 代码、打包官方插件并编译原生模块，输出 `build/ember/core/Release/ember_core.node`（Windows 另有键盘独占模块 `ember_keyboard.node`，随安装包一起分发） |
| `npm run core:test` | 生成 Schema 代码、打包官方插件，构建并运行 C++ 测试（GoogleTest）；`--` 之后的参数原样交给 CTest，如 `npm run core:test -- -R DebugInspector` 只跑匹配的用例，`-- -E ^Roms/` 排除测试 ROM 用例（它们单个耗时可达数秒、数量最多） |
| `npm run plugins:pack` | 把 `plugins/<插件>/` 打成 `build/ember/plugins/<id>.emap`，见第 7 节 |
| `npm run help:build` | 构建帮助文档站点到 `build/ember/help`，见第 10 节；要先运行过 `npm run schema`，并在仓库根目录 `npm install` |
| `npm start` | 生成代码、构建帮助文档、打包插件、编译原生模块，再启动开发版 |
| `.\debug.ps1` | 在任意目录下启动开发版（切到项目目录后执行 `npm start`） |
| `.\build.ps1` | 安装依赖（`ember/` 与仓库根目录各一次），运行类型检查、lint、依赖检查与 TypeScript 测试（不含 C++ 测试与调试 SDK 的检查），再编译并生成 Windows x64 安装程序 `build\ember\make\squirrel.windows\x64\Ember-学习机模拟器.exe`（仓库根目录下）；`-SkipCheck` 跳过检查，`-PackageOnly` 只打包成 `build\ember\Ember-win32-x64` 目录、不生成安装程序 |
| `npm run typecheck` | 生成代码后做 TypeScript 类型检查 |
| `npm run lint` | oxlint 检查（有警告即失败） |
| `npm run boundaries` | 分层、模块依赖与模块登记检查 |
| `npm test` | 生成代码后运行 TypeScript 测试（Vitest） |
| `npm run check` | 类型检查、lint、依赖检查、帮助文档构建、TypeScript 测试、C++ 测试与调试 SDK 的检查 |
| `npm run debug-sdk:check` | 运行 `packages/ember-debug-sdk/` 的全部检查（生成、类型检查、lint、构建、测试），首次使用前要在仓库根目录 `npm install`（SDK 是 npm 工作区的一员），见 07 |
| `npm run package` | 打包当前平台的应用 |
| `npm run package:win` | 打包 Windows x64 版 |
| `npm run make:win` | 生成 Windows x64 安装程序；同一输出目录里还有升级文件 `RELEASES` 与 `.nupkg`，发布见第 11 节 |
| `npm run update:publish` | 检查并把升级文件上传到阿里云 OSS 的升级目录（先传 `.nupkg`，最后传 `RELEASES`），`-- --dry-run` 只检查不上传，见第 11 节 |
| `npm run package:mac` | 打包 macOS arm64 版（只在苹果电脑上运行） |
| `node tools/dev/smoke-run.mjs` | Electron 冒烟，见第 8 节 |
| `node tools/dev/latency-run.mjs` | 画面延迟与丢帧测量，见第 9 节 |
| `npx electron tools/build/make-icons.cjs <标志图.png>` | 由标志图生成应用图标，见下面“应用图标” |

构建产物都在仓库根目录的 `build/ember/` 下（不在 `ember/` 里，不入库）：`core/`（原生模块，模块在 `core/Release/`）、`core-test/`（C++ 测试的构建）、`plugins/`（打好的官方插件包）、`help/`（帮助文档站点）、`third-party/`（第三方开源代码的许可全文），以及 Electron Forge 的打包输出 `Ember-win32-x64/`、`make/`、`make-results/`。这些路径统一写在 `tools/build/build-paths.mjs`（`forge.config.mts`、`main.ts`、`core/CMakeLists.txt`、`build.ps1`、`package-mac.sh` 各自写了同样的路径，改动时一并修改）。Forge 的 Vite 插件把输出固定在 `ember/.vite/`，不能移动。

- Windows 上编译 C++ 使用 Visual Studio 自带的 CMake（用 `vswhere` 查找）；PATH 里的 `cmake` 可能是 MinGW 的，不被使用。环境变量 `EMBER_CMAKE` 可指定 `cmake` 可执行文件。
- 界面组件库默认取 `../../rujian-ui-kit`（与 `famiclone` 并列），环境变量 `EMBER_UI_KIT_SOURCE` 可指定其他位置。
- 核心版本取自 `package.json` 的 `version`，编译时经 `EMBER_CORE_VERSION` 传入；应用版本由主进程在启动核心时传入。
- 应用图标：标志图的原件在文档仓库的 `02-设计/Ember/logo.png`（蓝色卡带，相邻的 `logo.xcf` 是源文件）；`tools/build/make-icons.cjs` 用 Electron 自带的画布把它居中放进正方形、逐级缩小，生成 `resources/icon.ico`（Windows，16、24、32、48、64、128、256 像素七种尺寸）与 `src/ui/shell/ember-logo.png`（128 像素，标题栏的标志），两个生成文件提交进仓库，换标志时重新运行脚本。命令行参数里有中文时 PowerShell 5.1 会丢字，先把原图复制到纯英文路径。`forge.config.mts` 的 `packagerConfig.icon`（可执行文件、与对话框窗口的图标）与安装程序的 `setupIcon` 都用 `icon.ico`；开发版由主进程把 `resources/icon.ico` 传给主窗口与对话框窗口；macOS 的 `.icns`（`resources/icon.icns`，已在 `.gitignore`）与安装包以后再定。

## 2. Schema 与生成代码

请求、事件与数据类型只在 `schema/<模块>.schema.json` 中定义。`npm run schema` 生成：

| 生成位置 | 内容 |
| --- | --- |
| `src/contracts/<模块>/generated/<模块>.ts` | 请求名、事件名、数据类型、请求名到类型的对照，以及入口校验用的 Schema |
| `src/contracts/core-gateway/generated/core-api.ts` | 汇总全部模块：请求名单、事件名单、`CoreApi` 与全部 Schema |
| `core/src/contracts/<模块>/generated/<模块>.hpp`、`.cpp` | C++ 数据结构、请求名常量、JSON 转换与结构校验 |
| `core/src/contracts/debug/generated/openrpc.hpp`、`.cpp` | 调试服务的 OpenRPC 接口描述文档（全部模块的请求与事件，`debugOnly` 与 `mainOnly` 带 `x-` 标记）的 C++ 常量，`rpc.discover` 返回它；由 `tools/schema-gen/openrpc.mjs` 生成，见 04 第 2.2 节 |
| `packages/ember-debug-sdk/generated/openrpc.json`、`api.ts` | 同一份 OpenRPC 文档与 TypeScript 类型（请求、事件、`EmberApi`），给调试 SDK 用，也是帮助文档里“调试接口手册”的来源（见第 10 节）；由 `tools/schema-gen/sdk-ts.mjs` 生成，见 04 第 8 节与 07 |

- 生成目录不提交，不手写、不手改；内容没变的文件不改写；删除模块后，它的生成目录一并删除。
- Schema 是 JSON Schema 的子集：类型 `string`、`integer`、`number`、`boolean`、`array`、`object`；可空写成 `["string", "null"]`；枚举只支持字符串；`minLength`、`maxLength`、`minimum`、`maximum`、`minItems`、`maxItems`；类型引用写成 `#/types/名称` 或 `模块#/types/名称`。属性名与操作名用 camelCase，类型名用 PascalCase，错误码以模块名开头。
- 请求的使用范围：默认界面与调试服务都能用；标 `mainOnly` 的只能由主进程发起；标 `debugOnly` 的只经调试服务开放，界面的预加载脚本不暴露。两者都不进入界面请求名单与 `CoreApi`，不能同时标记。
- `mainRequests` 是主进程自己处理、不进入核心的请求，只生成 TypeScript。
- 入口层按 Schema 校验界面发来的参数，核心再按生成的 C++ 代码校验一次；未登记的请求直接拒绝。

## 3. 模块登记

新增模块时，在各层建立同名目录，并在三份模块清单里各登记一项；摘除模块时删除目录并取消登记。

| 清单 | 位置 | 登记方式 |
| --- | --- | --- |
| C++ | `core/src/bootstrap/module-list.cpp` | 一项 `{"模块名", 登记函数}`，登记函数写在 `bootstrap/modules/<模块>.cpp`，在其中创建实现并登记请求 |
| 主进程 | `src/bootstrap/main/module-list.ts` | 引用 `main/modules/<模块>.ts` 里的登记项（模块的 Schema） |
| 渲染进程 | `src/bootstrap/renderer/module-list.ts` | 只登记有界面的模块，引用 `renderer/modules/<模块>.ts` 里的登记项（页面） |

- 取用其他模块共享服务的模块排在提供方之后登记。目前的 C++ 清单是 `system`、`preferences`、`mappers`、`output`、`runtime`、`input`、`inspector`、`cartridges`、`machines`、`media`、`debug`：`preferences` 提供 `PreferenceService`（其他模块取用它登记自己的设置项、读取取值、订阅变化）并登记 `preferences.*` 请求，登记自己的外观与画面两组设置项，取值保存在 `config/preferences.json`；`mappers` 提供 `MapperService` 与 `MapperFactory`；`output` 取用 `PreferenceService`（登记“声音”分组的设置项、启动时读取缓冲档位与音量、订阅变化），打开系统声音输出（失败时降级为空输出并写错误日志），提供 `platform::AudioOutput`（共享给 `runtime`）与 `OutputService`，并登记 `output.*` 请求（`output.screenshot` 的截图服务需要 `runtime` 提供的 `RuntimeService`，而 `runtime` 排在 `output` 之后，所以截图服务登记一个“启动后”处理（`ModuleRegistry.startHandlers`），全部模块登记完、开始处理请求之前再绑定；截图保存目录读首选项 `debug.outputDirectory`），并提供 `DebugFileWriter`（把文本写进同一个调试输出目录，供 `inspector` 保存跟踪与调用记录）；`runtime` 取用 `MapperFactory`（按匹配结果创建卡带）与 `AudioOutput`，提供 `RuntimeService`，并登记 `runtime.*` 请求、在核心停止时结束模拟线程；`cartridges` 取用 `MapperFactory` 与 `RuntimeService`，提供 `CartridgeLoader` 与 `CartridgeService`，并登记 `cartridges.*` 请求；`machines` 取用 `RuntimeService`（整机机型开机经它的 `bootMachine`），创建 BIOS 目录的存储（`<用户数据目录>/bios/<机型>/<文件>`）与机型管理，登记 `machines.*` 请求；`media` 取用 `PreferenceService`（登记“打印机”分组与 `printer.outputDirectory`）、`RuntimeService`（经它的 `useMachine` 在模拟线程里访问打印机，经 `runOnSimulation` 访问软驱与磁带机）、`TapeControl` 与 `FloppyDrive`（主机型号目录创建、`runtime` 模块提供的磁带机与软驱 A，独立于主机，目录把它们交给需要的主机）与事件出口，创建盘片镜像存储、磁带存取（`infra/media/disk-tape-store`：经 `platform/process` 运行随应用附带的 ffmpeg 解码，程序路径由核心启动参数 `ffmpegPath` 经 `ModuleRegistry.ffmpegPath` 传入，没有时打开磁带报 `media.decoderMissing`）、打印页存储（1 位灰度 PNG）与介质管理，登记 `media.*` 请求，并把 `runtime` 模块创建的打印机输出中转（`PrinterOutputRelay`）绑定到打印页存储；`input` 取用 `RuntimeService`（转发按键、鼠标、游戏手柄事件，设置手柄口）、`PreferenceService`（登记“输入”分组的设置项，启动时读取“接入 Family BASIC 键盘”并交给 `RuntimeService::setFamilyKeyboard`，订阅变化）与事件出口，创建手柄绑定服务（`infra/input/input-binding-registry`，保存到 `<用户数据目录>/config/input-bindings.json`）与手柄输入路由器（`logic/input/pad-input-router`），把路由器经 `RuntimeService::setInputHook` 挂到运行服务上（钩子接口 `InputHook` 在 `contracts/runtime`，所以 `runtime` 不认识 `input`，模块之间没有循环），登记 `input.getBindings`、`input.setBindings`、`input.resetBindings`（界面与调试服务都能用）与注入输入的 `input.key`、`input.mouse`、`input.gamepad`、`input.pad`、`input.releaseAll`（这五个 `debugOnly`）；`inspector` 取用 `RuntimeService`（经它的 `inspect` 在模拟线程读写主机与卡带，把卡带上的存储区合成 `cart.<标识>` 空间，经 `setObserver` 检查监视项）与 `DebugFileWriter`，登记 `inspector.*` 请求（全部 `debugOnly`）；`debug` 取用 `PreferenceService`（登记“调试服务”分组的设置项）、请求路由与事件订阅源，创建调试服务宿主并登记 `debug.*` 请求，排在最后，所以核心停止时最先停下（先停调试服务，再停被它调用的模块）。`runtime` 只依赖 `mappers` 的契约（`MapperFactory`、卡带映像与匹配结果）和硬件契约，不依赖 `cartridges`，避免模块之间循环。主进程的模块清单是 `system`、`preferences`、`mappers`、`output`、`runtime`、`input`、`inspector`、`cartridges`、`machines`、`media`、`debug`，渲染进程的清单目前是 `runtime`、`media`、`debug`、`input`、`mappers`、`preferences` 与 `system`（`runtime`：显示区的画面、画面提示、键盘采集，底部面板的“运行”页签，以及文件与机器菜单、命令、系统栏项和常驻组件；`media`：底部面板的“设备”页签（系统栏左侧的软盘图标按钮，带读写灯）、系统栏左侧的已载入软盘名与常驻组件；`debug`：系统栏右侧的调试模式项与常驻组件；`input`：“手柄设置”对话框、“设置”菜单的“手柄设置”命令；`mappers`：“mapper 插件”对话框、“设置”菜单的“mapper 插件”命令；`preferences`：首选项页、“设置”菜单的“首选项”命令；`system`：“帮助”菜单的“打开日志目录”“关于 Ember”命令、“关于 Ember”对话框与取得预加载接口的常驻组件；登记的内容见下面的“界面登记”）。核心启动参数里可选的 `bundledPluginsPath` 给出预装插件目录，由 `mappers` 模块读取；帧输出由核心入口经 `ModuleRegistry.frames` 给 `runtime` 模块，按键输入经 `Core::sendInput` 进入 `RuntimeService`。
- 主进程模块登记项 `MainModule` 除 `schema` 外，有主进程自己处理的请求（`mainRequests`）时提供 `createMainHandlers`（目前有 `cartridges` 的 `open`、`recent`、`openRecent`，`machines` 的 `openBios`，`media` 的 `openFloppy`、`openTape`、`openTapeRecording`，`mappers` 的 `openPackage`，`preferences` 的 `pickDirectory`，`system` 的 `openLogDirectory`、`openHelp`、`updateStatus`、`checkUpdate`、`installUpdate`；创建时可用的能力 `MainHandlerContext` 有文件选择窗口（`FileDialog`：选文件 `pickFile`、选文件夹 `pickDirectory`，每次调用都要给 `purpose` 用途标识，同一用途的窗口记住上次的目录）、以主进程身份请求核心的依赖、最近打开的卡带服务、应用升级服务（`AppUpdater`，见 01 第 11 节），以及日志目录（`LogDirectory`，用系统的文件管理器打开用户数据目录下的 `logs`）），组装根把它们汇总后交给 `entry/ipc/core/main-request-ipc.ts`；预加载脚本按 `MAIN_REQUEST_NAMES` 暴露 `window.ember.main`。最近打开的卡带由主进程保存（`config/recent-cartridges.json`，格式 `{ version, items: [{ path }] }`，最多 10 个，读不到、不是合法 JSON 或某项不合格时用空清单或跳过那一项，不报错弹窗），路径只在主进程里，界面只拿到编号与显示名；`cartridges.open`、`cartridges.openRecent` 与启动参数 `--cartridge=` 都经 `entry/ipc/cartridges/load-cartridge.ts` 加载：先把路径记入清单再请核心加载，失败时移出清单。
- 硬件不是业务模块，没有请求，不在清单里登记；硬件的装配见 02。
- 硬件目录：契约在 `core/src/contracts/hardware/`，一个契约一个头文件，错误码在 `hardware-error.hpp`；实现在 `core/src/logic/hardware/<模块>/`（命名空间 `ember::logic::hardware`），目前有 `scheduler`、`bus`、`lines`、`cpu-6502`、`ppu-2c02`、`apu-2a03`、`dma-2a03`、`pad-2a03`、`joypad`、`ram`、`cartridge-slot`、`nametable-ram`、`null-device`，以及 6576 学习机的 `ppu-um6576`、`psg-um6576`、`sysinit-um6576`、`irq-um6576`、`timer-um6576`、`rtc-um6576`、`paging-um6576`、`dma-um6576`、`pad-um6576`、`keyboard-um6576`、`mouse-um6576`、`printer-um6576`、`expio-um6576`、`dac-um6576`，学习机外设 `keyboard-sb2000`、`mouse-sb2000`、`fdc-upd765`、`floppy-drive`、`printer-escp`（`debug` 是调试辅助，不是硬件），说明见 02 第 3.4、6 节；主机型号的装配在 `core/src/bootstrap/machines/<主机型号>/`（目前有 `fc` 与 `sb2000`；学习机的板级译码 `sb2000-board.hpp`、学习机 FC 兼容模式的 MMC3 接线与模式切换 `sb2000-fc-board.hpp` 在 `sb2000/`，`$4016-$4017` 的转接设备 `pad-apu-port.hpp`、打印机输出中转 `printer-output-relay.hpp`、软驱活动中转 `floppy-activity-relay.hpp`、mapper 电路目录 `mapper-circuit-catalog.*`、调试辅助 `cpu-debug-kit` 在 `common/`，机型清单 `machine-catalog` 在 `machines/` 下）；测试在 `core/test/hardware/`，公共辅助是 `test-support.hpp`（CPU 测试台）、`fc-test-support.hpp`（手写 6502 程序的小汇编器、构造 iNES 文件、用 nrom 插件装好卡带的 `FcRig`）与 `rom-test-support.hpp`（测试 ROM 的清单项、运行到出结果、两种结果读法、要求复位时的软复位，PPU 与 APU 的 ROM 测试共用）；新增硬件模块只需在 `logic/hardware/` 下建目录，不登记。

### 界面登记

渲染进程的模块登记项 `ShellModule`（`src/ui/shell/shell-registry.ts`）由各模块在 `src/bootstrap/renderer/modules/<模块>.ts` 里写出，汇总在 `src/bootstrap/renderer/module-list.ts`；外壳（`ui/shell`）只渲染登记表，不写死任何入口。外壳自己的登记项（`ui/shell/shell-module.ts`，名称 `shell`）排在最前面，也走同一套检查。

| 登记项 | 内容 |
| --- | --- |
| `name` | 模块名，与 Schema 与目录名一致；其余登记项的标识都以“`<模块名>.`”开头 |
| `screen` | 显示区的内容组件：整个应用只能有一个模块登记，固定显示在窗口中间，没有标签页 |
| `dialogs` | 对话框：标识、标题、内容组件 `Component`、初始宽度 `width`、可选的高度与最小宽高；对话框是组件库的独立窗口对话框，同一个对话框同时只开一个，再次打开时聚焦已有的 |
| `commands` | 命令：标识、名称（字符串，或每次渲染菜单时重新取值的函数，如“开机”与“断电”的切换）、默认快捷键 `defaultShortcut`、动作 `run(shell)`、`enabled(view)`（菜单项是否可用）、`checked(view)`（菜单项是否勾选） |
| `menuItems` | 菜单项：所属菜单（`file` 文件、`machine` 机器、`settings` 设置、`help` 帮助，没有视图菜单）、本模块的命令或一个子菜单（二选一）、助记字母、是否在前面加分隔线；没有任何菜单项的菜单不显示；外壳自己的菜单项排在各模块之后（如“文件”菜单的“退出”在最后） |
| `menuItems[].submenu` | 子菜单：标识（以模块名开头）、名称、`entries()`（每次渲染菜单时取当前的项：`id`、`label`、`hint` 右侧提示文字、`disabled`、`checked`（给出时是单选项，选中的一项前面打对勾）、`separatorBefore`、`run(shell)`）；子菜单项不登记成命令（没有快捷键，项随数据变化，如最近打开的卡带、可选的机型），没有项时这一项置灰 |
| `bottomPanels` | 底部面板：标识、标题（也是系统栏按钮的悬停提示与可访问名称）、图标、内容组件 `Component`（面板收起时卸载，没有属性）、可选的 `autoCollapse`（为 true 时标题栏有“自动收缩”开关，开关开着时点面板之外的地方就收起面板（例外见 05 第 2 节），开关状态由外壳按面板标识保存到界面状态的 `autoCollapsePanels`；运行与设备面板登记了）、可选的 `look()`（按钮当前的图标、颜色与悬停提示，随模块状态变化）与 `lamp()`（按钮上的指示灯，`inIcon` 给出时画在图标里）；每个面板在系统栏左侧自动有一个只有图标的按钮，按钮、面板标题行与内容由外壳生成 |
| `statusItems` | 系统栏项：标识、`align`（`start` 左侧或 `end` 右侧）、组件；左侧的项排在面板按钮之后，右侧最后一项固定是外壳的通知按钮 |
| `titleBarItems` | 标题栏项：标识、组件；按登记顺序排在标题栏右侧、系统窗口按钮左边（组件库 `TitleBar` 的 `actions`），组件自己用组件库的按钮渲染，没有内容要显示时返回 `null`（所有项都不显示时操作区不占位），状态变化后模块调用 `refreshCommands()` 让外壳重新渲染（系统模块的蓝色“更新”按钮用它） |
| `fileHandlers` | 拖入主窗口的文件的处理项：标识、认领的扩展名 `extensions`（小写字母与数字、不带点，全部处理项之间不能重复）、`open(file)`（`file` 是主进程登记的编号 `id` 与显示名 `name`，没有路径，处理项经主进程请求的 `droppedId` 参数打开，失败自己用通知提示）；外壳接住窗口的拖放，按扩展名交给认领它的处理项，没人认领的用通知说明，规则见 05 第 2 节 |
| `Host` | 常驻组件：外壳启动后一直挂载（全屏时也在），没有界面，用来订阅事件、维护模块自己的状态；模块状态变化影响命令的名称与可用状态时调用 `shell.refreshCommands()`，外壳随即重新计算菜单 |

## 4. 依赖检查

`npm run boundaries` 运行 `tools/check/check-modules.mjs`，规则同 01 第 5 节：

- TypeScript：各层的 `import` 规则、`electron`、Node 内置模块与第三方包的使用范围、文件之间的循环引用；`ui` 层引用 `contracts` 只能用 `import type`。渲染 Worker（`ui` 层里以 `-worker.ts` 结尾的入口）与 `ui` 层同属渲染侧，不能引用 `electron` 与 Node 内置模块（同 `ui` 层）；入口与它经 `import` 依赖的全部文件还不能引用 `react`、`react-dom`、`@rujianjs/ui-kit`、`.tsx` 与样式文件，入口也不能放在 `ui` 层之外。
- C++：各层的 `#include` 规则；`logic` 只能包含 `platform` 的六个抽象（`events/event-sink.hpp`、`requests/cancellation.hpp`、`logging/error-log.hpp`、`streams/frame-output.hpp`、`audio/audio-output.hpp`、`files/file-watcher.hpp`），硬件模块只能包含前两个；`binding` 只能包含 `bootstrap/core.hpp`；第三方头文件只能出现在指定位置。
- 框架目录不属于任何业务模块，不要求登记：契约目录 `core-gateway`、`shell`、`logging`、`stream-ports`，入口目录 `entry/ipc/core`、`entry/ipc/shell`、`entry/ipc/streams`，界面目录 `ui/shell`。TypeScript 的 `platform` 不能引用 `contracts`，它的实现用自己声明的结构类型。
- 模块：一个模块只能引用另一个模块的契约，模块之间（含 Schema 的 `$ref`）不能循环依赖。
- 硬件：`contracts/hardware` 是硬件契约；`logic/hardware/<模块>`（主板与主机上的芯片）与 `logic/hardware/mapper-chips/<芯片>`（mapper 电路，如 `mmc3`，可装在卡带上，也可在学习机主板上）的每个目录都按一个模块计，模块之间（含同族型号）互不引用，业务模块也不能引用它们的实现，都只经 `contracts/hardware`。具体规则：
  - `contracts/hardware` 只能包含 `contracts/hardware`、`shared` 与标准库头文件（没有扩展名的头文件，如 `<cstdint>`），不能包含 `logic`、`platform`、其他模块的契约与任何第三方库（含 `<stdint.h>` 这类带扩展名的头文件）。
  - `logic/hardware/<模块>` 与 `logic/hardware/mapper-chips/<芯片>` 里的文件只能包含自己目录的文件、`contracts/hardware`、`shared` 与 `platform` 的抽象（`platform/events/event-sink.hpp`、`platform/requests/cancellation.hpp`），不能包含其他模块的契约与第三方库；文件必须放在 `logic/hardware/<模块>/` 或 `logic/hardware/mapper-chips/<芯片>/` 目录里，不能直接放在 `logic/hardware/`、`logic/hardware/mapper-chips/` 下。
  - `bootstrap/machines/<机型>/` 与 `bootstrap/machines/common/` 里的文件只能包含 `contracts/hardware`、`logic/hardware`、`shared`、`platform` 的两个抽象头文件（同上）与自己目录和 `common` 里的文件，不能包含其他机型、`machine-catalog` 与业务模块，`common` 也不能包含任何机型；机型的文件必须放在 `bootstrap/machines/<机型>/` 或 `bootstrap/machines/common/` 目录里，只有 `machine-catalog` 可以直接放在 `bootstrap/machines/` 下。
- 登记：有 Schema 或模块目录的模块都登记在清单里，清单里的项都有对应的文件。
- 官方插件目录：`plugins/<id>/` 的目录名必须等于 `manifest.json` 里的 `id`，目录里只能有 `manifest.json`、`main.js`、`icon.png`。
- 第三方头文件的位置：`quickjs.h` 只能出现在 `infra/mappers/`，`miniz.h` 只能出现在 `infra` 层，`miniaudio.h` 只能出现在 `platform/audio/`，`nlohmann/` 不能出现在 `logic` 层，`sqlite3.h` 只能出现在 `platform/database/`。

`node tools/check/check-modules.mjs --dependents <模块>` 列出直接与间接依赖该模块的全部模块。

## 5. 第三方库

- C++ 第三方库源码放在 `core/third_party/`，随代码提交，编译时不联网；每个目录有 `third-party.json`，清单见 01 第 10 节。`mesen-ce` 目录只有 `third-party.json` 与许可全文 `LICENSE`（官方 mapper 插件与 MMC2、MMC3 电路的逻辑是重新编写的，来源与许可只登记在这里）。QuickJS-ng（只编译引擎核心，不编译提供文件与进程访问的 quickjs-libc）、miniz 与 miniaudio 已由核心库链接（mapper 插件宿主用前两个，QuickJS 的头文件不对外暴露，miniz 的头文件对测试可见；miniaudio 只在 `platform/audio/` 里使用，`core/third_party/miniaudio/miniaudio-impl.c` 单独一个编译单元，只编译播放设备部分——`MA_NO_ENCODING`、`MA_NO_DECODING`、`MA_NO_GENERATION`、`MA_NO_ENGINE`、`MA_NO_NODE_GRAPH`、`MA_NO_RESOURCE_MANAGER` 由 CMake 目标 `ember_miniaudio` 公开定义，第三方代码关闭警告；Windows 用 WASAPI，不需要额外安装；macOS 链接 CoreFoundation、CoreAudio、AudioToolbox 三个系统框架，Linux 链接 dl、pthread、m，这两个平台不在 Windows 上测试）；SQLite 已登记构建目标（`EXCLUDE_FROM_ALL`），核心库链接它时才编译；ffmpeg 不是链接的库，是随应用附带的外部程序（`core/third_party/ffmpeg/bin/win32-x64/ffmpeg.exe`，精简编译版本，LGPL，许可文件与 `third-party.json` 在同一目录，只用于磁带的解码；打包时由 `forge.config.mts` 的 `extraResource` 放进应用的资源目录 `resources/<平台>-<架构>/`，主进程启动核心时把完整路径作为 `ffmpegPath` 传入，开发版指向仓库里的这份；核心里只有 `platform/process/`（运行外部程序并流式读取输出，Windows 实现在 `stream-process-win`）知道怎么启动它）。
- `tools/third-party/third-party.mjs` 汇总 `third-party.json` 与源码引入的 npm 包，生成“关于”对话框用的清单和打包时随应用分发的许可全文（`build/ember/third-party/THIRD_PARTY_NOTICES.txt`）；声明或许可缺失时构建、测试与打包失败。
- `tools/build/build-info.mjs` 提供虚拟模块 `virtual:ember-build-info`，导出编译时间（Vite 读取配置时取得的本机时间）；渲染进程的构建配置与测试配置都加载它。

## 7. 官方插件与打包

- 官方 mapper 插件的源码在 `plugins/<插件>/`（目前有 232 个，覆盖的 mapper 号见 03 第 9 节的台账），目录里是 `manifest.json`，有脚本时还有 `main.js`，可选 `icon.png`；规则见 03 第 3、4 节。每个插件在 `core/test/data/mapper-vectors/<id>.json`（同一插件的多个向量用 `<id>.<后缀>.json`）有测试向量，由 `core/test/mappers/mapper-vectors-test.cpp` 用打好的包逐步验证；步骤有 `cycles`、`reset`、`write`（可带 `bus`、`after`）、`read`（带 `expect`）、`a12`（让 A12 出现指定次数的上升沿）、`video`（让 PPU 依次访问给定的显存地址）、`expectMap`、`expectState`、`expectNametable`、`expectIrq`。向量文件的增减要重新链接测试程序才能被发现。插件包在注册表读取预装目录时都要试创建一次（每个向量用例包含读取全部预装包在内，调试构建下约 0.04 秒），所以插件数量对启动时间的影响很小。
- `npm run plugins:pack`（`tools/build/pack-plugins.mjs`）把每个插件目录打成 `build/ember/plugins/<id>.emap`：只用 Node 自带的 `zlib`，不引入依赖；条目按文件名排序、时间戳固定，同样的输入得到字节相同的包；包末尾附一段 256 字节的可压缩注释（zip 的注释字段，读取时被忽略）：Windows 安装包（Squirrel）里，压不小的小文件会被原样存放，原样存放的 `.emap` 本身就是 zip，安装程序解压到它之后会停止，后面的文件（V8 快照、显卡驱动 dll 等）全部缺少，应用无法启动；有这段注释包就总能压得更小，会被压缩存放（测试会检查每个官方插件包都能压得更小）；打包时只检查目录名等于 `id`、清单是 JSON、没有多余的文件，完整的清单与脚本检查在核心安装时做。
- `npm run core:build`、`npm run core:test`（以及经它们的 `npm start`、`npm run package*`）会先打包，所以 `build/ember/plugins` 总是最新；开发版把 `build/ember/plugins` 当作预装目录，正式包把它作为额外资源整个目录复制到应用的 `resources/plugins`（`forge.config.mts` 的 `extraResource`）；主进程启动核心时把这个路径经启动参数 `bundledPluginsPath` 传给 `mappers` 模块，所以开发版与正式包启动后都会自动加载预装的 `nrom`。
- 打包脚本有自己的测试（`test/pack-plugins.test.ts`）：解析生成的 zip、输出可重现、错误用例。
- 默认 BIOS 不经构建脚本：四个已支持机型的纯 BIOS 文件直接放在 `bios/<机型>/<文件>`（`sb97/SB97.bin`、`sb2000/SB2K_BIOS.bin`、`bbk10/bbk_bios10.bin`、`bbk20/bbk_bios20.bin`，由仓库的 `reference/rom` 里的 `.nes` 去掉 16 字节文件头得到），正式包把 `bios/` 作为额外资源整个目录复制到 `resources/bios`（`forge.config.mts` 的 `extraResource`），开发版直接读项目目录下的 `bios/`；主进程启动核心时经启动参数 `bundledBiosPath` 传给 `machines` 模块，核心启动时装进还没有 BIOS 的机型，规则见 01 第 9 节。`test/default-bios.test.ts` 检查四个机型各一个文件、大小等于 PRG 容量、没有文件头，并在原始资料存在时核对内容相同。

## 9. 延迟与丢帧测量

`node tools/dev/latency-run.mjs`（可选参数：`--rom=`，默认 `nestest/nestest.nes`；`--port=` CDP 端口，默认 9303；`--seconds=` 测量时长，默认 30；`--warmup=` 预热秒数，默认 3；`--no-build`；`--screenshots=目录`）：启动开发版，等卡带运行起来，预热后把渲染 Worker 的统计清零，测量指定时长，读出并打印报告（核心帧率、收到帧率、渲染帧率、画面节拍、各类丢帧、两段延迟的平均、p95、最大、最小）与三条结论（渲染帧率不低于核心帧率的 98%、丢帧合计不超过 1%、两段 p95 之和不超过两帧的时间），结束后只结束自己启动的进程树。统计口径与实测结果见 01 第 7 节“延迟与丢帧测量”。

- `npm run help:build`（`tools/build/build-help.mjs`）先运行调试 SDK 的 `npm run docs:protocol`（`packages/ember-debug-sdk/scripts/docs.mjs`），把 `generated/openrpc.json` 生成成 `help/api/`，再用 VitePress 把 `help/` 构建到 `build/ember/help`（路径写在 `tools/build/build-paths.mjs`）；存在死链接时构建失败。要先运行过 `npm run schema`，并在仓库根目录运行过 `npm install`（生成脚本用工作区里的 esbuild）。
- `npm start`、`npm run package*`、`npm run make:win`、`npm run check` 会先构建帮助文档；`build.ps1` 会在仓库根目录安装依赖，`package-mac.sh` 也会构建。开发版从 `build/ember/help` 读取；正式包由 `forge.config.mts` 的 `extraResource` 整个目录复制到 `resources/help`。
- 站点内的链接一律用 `.html` 结尾（不开 `cleanUrls`），因为由主进程的只读协议 `ember-help://app/` 提供（`src/platform/help/`）。
- 站点使用的 VitePress、Vue 等运行时代码与字体登记在第三方清单里（`tools/third-party/third-party.mjs` 的 `HELP_SITE_PACKAGES`，只登记分发的包本身，构建工具不进安装包）。
- 修改界面或用户可见的行为时，同步 `help/manual/` 的对应页；修改调试协议的规则时同步 04 文档与 `help/debug/`；修改 mapper 插件规范或插件宿主的行为（清单字段、`ctx` 接口、限制、安装规则）时同步 03 文档与 `help/plugin/`。

## 11. 发布升级

正式版的升级文件放在阿里云 OSS 的 `famiclone` Bucket 的 `updates/ember/windows/` 下（客户端的检查与重启见 01 第 11 节）；Bucket 对匿名只读（不含列举）、仅 HTTPS，写入只有持有访问密钥的发布者能做。

| 步骤 | 做法 |
| --- | --- |
| 1 | 把 `package.json` 的 `version` 升到新版本（升级按版本号比较，新版本必须大于已发布的版本），并在 `help/manual/changelog.md` 最上面加该版本一节（只写用户可见的功能变化）：用户升级后第一次启动时会自动看到这一页（见 01 第 11 节） |
| 2 | `npm run make:win`：生成 `build/ember/make/squirrel.windows/x64/` 下的 `Ember-学习机模拟器.exe`、`RELEASES` 与 `ember-<版本>-full.nupkg` |
| 3 | `npm run update:publish -- --dry-run`：检查 `RELEASES` 列出的文件都在、大小与 SHA1 一致、当前版本的完整包在其中，并打印要上传的文件；不上传 |
| 4 | `npm run update:publish`：用阿里云命令行工具 `ossutil` 先上传 `.nupkg`，最后上传 `RELEASES`（客户端按 `RELEASES` 找新版本，必须在 `.nupkg` 都传好之后才对外可见） |

- 上传前要先安装 `ossutil` 并运行 `ossutil config` 配好访问密钥与地域（华北 2 北京）；密钥只在本机的 `ossutil` 配置里，不放进仓库、不写进脚本，也不要交给界面或模拟器程序。
- 脚本只做检查与上传，不改动 `package.json`；检查失败（缺文件、大小或校验值不一致、缺当前版本的完整包）时不上传任何文件。
- 首次安装用 `Ember-学习机模拟器.exe`（安装程序，分发给用户的就是它）手动分发，不经升级目录；安装后程序目录里的可执行文件仍是 `ember.exe`（Squirrel 的包标识、启动器与升级都依赖它）。
- 脚本的纯函数部分（`RELEASES` 的解析与上传计划）有单元测试（`test/publish-update.test.ts`）；真实的升级过程（旧版本检查到新版本、下载、重启）需要两个版本的安装包与 OSS 目录，不在自动测试里。
