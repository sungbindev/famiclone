# Win32 原生外壳

Ember 的外壳：用 C++ 与 Win32 写成，面向 Windows 7 到 Windows 11 的 64 位系统，尤其是系统与硬件都较旧的电脑。它是 Ember 唯一的外壳：以前的 Electron 外壳已经停用并从仓库移除（存档在 `ember/electron-archive.zip`，只作历史参考），外壳与核心在同一个进程里，核心是静态库 `ember_core`。

本文档是设计与开发计划，已由用户确认，按本文执行；状态说明同 [01-软件架构设计.md](01-软件架构设计.md)。界面的布局、菜单、各页面内容与 [05-界面.md](05-界面.md) 完全一致，本文只写原生外壳特有的部分。

## 1. 决策

| 决策项 | 结论 | 状态 |
| --- | --- | --- |

| 网页版对照 | 文档里的“网页版”是 rujian-ui-kit 的网页组件库，只作为控件外观的对照基线（`win32:reference` 用 Electron 自带的浏览器渲染它，Electron 只作为开发依赖保留），不是 Ember 的外壳 | 已定 |
| 构建选择 | 构建脚本 `build-win32.ps1`、开发版启动脚本 `debug-win32.ps1`，见第 6 节 | 已定 |
| 支持的系统 | Windows 7 到 Windows 11 的 64 位系统，要能在刚装好的干净系统上直接运行；不支持 32 位系统 | 已定 |
| 对齐范围 | 外观、样式、布局、菜单位置、主题切换与全部功能都与 05 的描述一致；控件与网页版组件库对照，个别无法对齐的细节登记在第 10 节“已知差异”，差距不能过大 | 已定 |
| 样式令牌 | 全部取自 rujian-ui-kit 的令牌与主题（`src/styles`），原生外壳不自定义令牌；控件的尺寸、间距、状态底色取自各组件的样式文件 | 已定 |
| 控件库 | 不能使用 Web 组件库，另做一套 Win32 控件库，做成独立的 VC 项目，只依赖 Windows 系统与令牌，别的项目也能使用；性质与 rujian-ui-kit 相同，只是运行环境不同 | 已定 |
| 开发顺序 | 先做控件库，再做应用程序 | 已定 |
| 窗口外框 | 窗口的缩放、最大化、停靠、贴边与系统菜单交给 Windows（去掉标题栏样式、保留缩放边框样式，缩放区在窗口边框线的外面和边框线本身，见 5.2）；标题栏区域自绘（图标、名称、菜单、更新按钮与三个系统按钮），三个系统按钮的鼠标跟踪由外壳自己做；阴影与边框：Windows 11 用系统的（圆角、阴影、边框色），Windows 7、8、10 自绘，见 5.2 | 已定 |
| 核心 | 核心不改动功能，经 `Core` 类（`core/src/bootstrap/core.hpp`）在进程内直接链接使用，不经 Node-API、不经网络；确需兼容 Windows 7 的小改动放在核心的 `platform` 层，见 7 | 已定 |
| 控件绘制 | Direct2D 1.0 与 DirectWrite 1.0（Windows 7 自带），没有可用显卡时用它们自带的软件渲染；不用 GDI+ 画界面，见 4.1 | 已定 |
| 运行画面 | Direct3D 11，优先用硬件设备；创建不出（没有显卡、没有驱动、虚拟机没有 3D 加速）时回退到 WARP 软件设备（Windows 7 SP1 起系统自带），两者都创建不出时弹出提示并退出；不做 GDI 降级，见 5.5 | 已定 |
| 工具链 | MSVC v143 工具集 14.44（本机已装的 VS 2022 组件），静态链接运行库；不用 14.50 及以后的工具集，因为它们的标准库不再支持 Windows 7（见微软 STL 变更日志），见 7 | 已定 |
| 项目位置 | `ember/win32/`，下分 `ui-kit/`（控件库）与 `app/`（应用程序），见第 3 节 | 已定 |
| 用户数据 | 与 Mesen 一样二选一：可执行文件所在目录里有 `ember-data` 目录就用它，否则用 `%APPDATA%\Ember`，可在首选项里切换，见 5.7 | 已定 |
| 帮助文档 | 嵌在可执行文件里，由外壳在本机回环地址上提供只读服务，用系统默认浏览器打开，见 5.6 | 已定 |
| 分发与升级 | 单个可执行文件（帮助文档、预装插件、许可全文嵌在里面），放在 zip 里发布，不做安装程序；只做自动升级：清单带版本、文件大小、SHA-256 与 RSA 签名，升级就是替换可执行文件，见 5.6 与 01 第 11 节 | 已定 |
| 平台 | 只做 Windows | 已定 |

## 3. 目录与依赖

```text
ember/win32/
├── ui-kit/              控件库：独立 CMake 项目，可单独构建、测试与被其他项目使用
│   ├── include/rujian/ui/   公共头文件，只放控件的契约与类型
│   ├── src/
│   │   ├── base/            绘制、文字、DPI、主题、输入与焦点等与控件无关的基础
│   │   ├── components/<控件>/   一个控件或一族控件一个目录
│   │   └── generated/       由令牌与图标生成的代码，不手写、不手改；生成结果提交进仓库，`win32:check` 检查它们与生成结果一致
│   ├── tools/               令牌、图标与字体生成器（gen-tokens、gen-icons、gen-fonts，字体用 lib/woff2.mjs 解码）、网页版对照（reference）
│   ├── third_party/         Tabler Icons、IconPark 与 Quicksand 字体的许可与清单（图标图形、标题栏应用名字体的来源）
│   ├── gallery/             控件画廊程序
│   ├── test/
│   ├── README.md
│   └── LICENSE
├── app/                 Ember 原生应用 ember-win32.exe（64 位）
│   ├── src/             contracts、logic、infra、entry、ui、platform、shared、bootstrap 八层；静态库 `ember_app`（输出 `ember_app.lib`），程序入口只有 `bootstrap/main.cpp`
│   ├── resources/       清单（`ember-win.manifest`）、版本信息（`ember-win.rc.in`）与资源声明（`ember-win.rc.in`：应用图标与嵌入的资源包 `EMBER_RESOURCES`）
│   └── test/            应用测试 `ember_app_tests`（假实现在 `test/support`）
├── probe/               平台探针 ember-probe.exe：在目标系统上检查图形、手柄、网络、声音与核心是否可用
```

- 控件库不依赖 Ember 的任何代码；应用程序依赖控件库与核心。核心保持原有位置，原生应用经 CMake 的 `add_subdirectory` 使用静态库 `ember_core`（`ember_core.lib`）。
- 控件库的组织与 rujian-ui-kit 一致：`base` 不引用控件；控件之间只经对方的公共头文件协作，只能引用依赖表里登记的控件，不得循环引用；依赖表与检查在控件库的 README 与 `test/` 里维护。
- 应用程序的分层、依赖与组装方式沿用 01 第 4、5 节的写法：具体实现只在 `bootstrap` 创建并注入，界面层只画控件与分派用户操作，业务与数据读写都在核心里。新增的目录进入 `npm run boundaries` 的检查。
- 令牌来自 `../../rujian-ui-kit`（与 06 第 1 节的组件库位置相同，环境变量 `EMBER_UI_KIT_SOURCE` 可改），生成器读取它的源文件，原生项目里不保存令牌取值的副本。

## 4. 控件库

### 4.1 绘制与文字

- 每个顶层窗口一个 Direct2D 的窗口渲染目标，字号、间距、圆角都以 CSS 像素定义，绘制时乘以窗口的缩放比例；缩放比例取自窗口当前 DPI。
- 文字用 DirectWrite，字体顺序与令牌 `--host-font-family` 一致：西文 `Segoe UI`，中文 `Microsoft YaHei`；弯引号、破折号与省略号（U+2014、U+2018 至 U+201D、U+2026）固定取宋体类字体（`SimSun`、`NSimSun`，没有时取 `Microsoft YaHei`），与组件库 `Rujian CJK Punctuation` 的规则相同。标题栏应用名用 `Rujian Quicksand`（拉丁子集，SIL OFL 1.1），组件库里是 `woff2` 文件，DirectWrite 读不了：生成器 `ui-kit/tools/gen-fonts.mjs`（用 Node 自带的 Brotli 与 `tools/lib/woff2.mjs`，按 WOFF2 规范还原 glyf、loca、hmtx 变换）把它们解码成 TrueType，字节嵌进 `src/generated/font-data.generated.cpp`，文字引擎用内存自定义字体集（`MemoryFontCollection`，DirectWrite 1.0 的字体文件与字体集加载器）加载，样式里 `TextStyle::face` 为 `Brand` 时用它（其余字符仍按正文字体分段），许可在 `third_party/quicksand`，`win32:check` 检查嵌入文件与生成结果一致。Windows 7 的 DirectWrite 没有字间距接口，`TextStyle::letterSpacing`（字号的倍数，每个字符簇后面加一份，包括最后一个）用整段排版得到的各簇位置、把每个字符簇单独画出来实现。省略号标记也取标点字体（网页版的省略号来自 `Rujian CJK Punctuation`）。Windows 7 的 DirectWrite 没有系统字体回退，按字符范围把文字拆成多段，各段指定字体族。
- 只用 Windows 7 自带版本的接口（Direct2D 1.0、DirectWrite 1.0、IMM32）；不依赖平台更新，也不依赖 DirectX 最终用户运行库。
- 动画与悬停、按下、选中、聚焦、禁用、错误、空状态的取值都来自令牌与各组件样式文件；一个状态一份取值，不在控件里写颜色数值。
- 与网页版逐像素对齐时实测得到的规则（改动绘制代码时先用 `win32:reference` 复核）：
  - 文字行高：样式没有设置行高时按 CSS 的 `normal` 处理（行高倍数传 0），字体的上升、下降、行距各自四舍五入到设备像素再相加（网页版就是这样算的，所以 100% 缩放下 11px 的字行高是 15 而不是 14.6），排版引擎由调用方设置缩放比例；有行高时按“字号 × 倍数”，字体内容区在行高里上下居中；
  - 边框宽度：`max(1, floor(宽度 × 缩放)) / 缩放`，即设备像素的整数倍且至少 1 个设备像素（125% 下 1px 的边框占 0.8 个逻辑像素）；布局也用取整后的宽度（带边框的控件用 `snapBorderWidth` 算尺寸）；
  - 盒子（有圆角与否都一样）的边缘对齐到设备像素，边框画在盒子内侧；边缘恰好落在半个像素上时往上取整（网页版的布局单位是精确的 1/64 像素，浮点误差不能让它往下取整）；
  - 轮廓线（`outline`）：线宽同边框，`outline-offset` 向零取整到设备像素，沿对齐后的边框盒描一圈，圆角是元素的圆角加偏移与线宽（偏移为负时在盒子里面，输入框的焦点环就压在边框那条带上）；元素在 `:focus-visible` 时带 `border-radius` 的（如分段单选的选项），底色与强调线也跟着圆角裁剪；
  - `inset` 阴影（无模糊）：阴影所在的内边距框先对齐像素，阴影的厚度不取整（上沿可能只盖住半个像素），内圆角的水平、垂直半径分别是外圆角半径减去相邻边的边框宽度；外阴影（`box-shadow`）不画在元素自己的框里面，模糊用按高斯积分逐层叠加的圆角矩形逼近（Direct2D 1.0 没有模糊效果）；
  - “右边与下边各有一段边框、旋转 45 度”的方块（复选框对勾、下拉框箭头与已选项的对勾）：方块的左上角、宽、高各自四舍五入到设备像素，绕取整后的方块中心旋转，边框宽度按上面的规则取整，整个图形作为一个多边形填色（元素整体带不透明度时不能重叠上色）；
  - 滑块轨道的填充是一条“两色硬边”的渐变：边缘在填充比例处，每个设备像素要么是强调色要么是轨道底色，所以用对齐像素的裁剪分两次画；滑块中心的活动范围是轨道宽度减去直径，填充边缘却按整条轨道的宽度算；
  - 文字选区的底色与选中文字的颜色取网站版在两个主题下的实测值（浏览器默认的 `::selection`），高度是行高 normal；用 Tab 键切到输入框时全选里面的文字，失去焦点后输入框的滚动位置回到开头；`type=search` 的输入框在有内容且悬停或有焦点时显示右侧的“×”，点它清空内容；
  - 这些规则里凡是“取整到设备像素”的，都依赖网页版排版时用的设备缩放比例；基线截图必须让浏览器的设备缩放比例等于目标缩放比例（见 4.4），否则边框与轮廓线会按本机系统的缩放比例算（在 150% 的电脑上 1px 的边框会变成 2/3 个逻辑像素）。
- 弹层（下拉选项、以后的菜单）显示在窗口的弹层上（`Host::showLayer`）：盖在内容之上，鼠标事件先给弹层，在弹层上按下不改变键盘焦点，在弹层之外按下或窗口大小变化时通知弹层自己关闭；弹层不超出窗口，下拉弹层默认在触发器下方 2px、放不下且上方更宽裕时翻到上方、最窄与触发器同宽、最高 240px、与窗口边缘至少留出 8px，与组件库的 `popup-placement.ts` 一致。
- 定时器与动画：宿主提供一次性定时器（`Host::startTimer`，窗口用 `SetTimer`，控件离开控件树时自动取消）与动画开关（`Host::animationsEnabled`）；离屏截图对照时关闭动画，控件直接切到目标状态，单元测试用 `Root::fireTimer` 手动触发。
- 滚动区域（`ScrollArea`，只做 Ember 用到的纵向滚动，另可用 `setHorizontalScroll` 打开横向滚动）：滚动条盖在内容上，轨道宽 10、滑块宽 6 居中、最短 20，长度与位置按 VS Code 的滚动条状态计算；鼠标移入、滚动或拖动时显示（100 毫秒渐显），鼠标移出或停止滚动 500 毫秒后开始隐藏（800 毫秒渐隐），不显示时不接收鼠标；在轨道上按下滑块先跳到指针处再接着拖；滚轮一格 50 像素（网页版实测，各缩放比例下相同），滚动位置取整到设备像素；方向键、翻页键、Home、End 在焦点控件不处理它们时滚动（输入框有焦点时不滚动），焦点移到内容里的控件时把它滚进可见范围。打开横向滚动后，内容的最小宽度（`Widget::minimumSize`）超过可见宽度时内容按最小宽度排，可见区域底边出现横向滚动条（样式、显示与隐藏同纵向的，两条都有时横向的让出右下角）；Shift+滚轮横向滚动，没有纵向滚动时滚轮也横向滚动；焦点移到比可见区域窄的控件上时横向也滚进可见范围，整行宽度的控件（树与文件列表的行）不调整横向位置。
- 容器与展示控件（阶段 3）：网页版里的普通文字元素（`p`、`h3` 等）在原生控件库里统一由内部控件 `Label` 承载（字号、字重、行高倍数、颜色，颜色令牌取 `currentColor` 时用正文文字色，没有文字时高度为 0）；`Panel` 的内容区放在 `ScrollArea` 里，没有内容时整块收起、标题行下面也不画分割线，内容之间的间距与内边距取面板令牌，`fixed` 是原生纵向堆叠的默认行为（不压缩子控件）；`Facts`、`SettingRow` 在窄窗口时上下排列，判断用的是窗口（视口）宽度而不是自己的宽度（与网页版的媒体查询一致：`Facts` 不超过 420、`SettingRow` 不超过 720，宽度由 `Host::viewportSize` 给出）；`SettingRow` 的名称说明列最宽 420、控件列最宽 280、列间距 10，空间不够时两列从零起平分、控件列先到上限，各列在行内垂直居中；`SplitView` 的分隔条宽 4、跨在左栏右边的分割线两侧，鼠标移上去停留 200 毫秒（动画关闭时立即）才显示聚焦色，拖动、方向键（每次 10 像素）与 Home、End 调整左栏宽度并限制在最小与最大宽度之间，指针是左右调整大小的箭头；主区可以隐藏（`setMainVisible`，隐藏后左栏占满整个宽度，分割线与分隔条都不出现），左栏可以设成铺满（`setSideFit`，内容按左栏高度铺满、不滚动，内容自己带滚动区域时用）；`Tabs` 整条页签栏只有一个 Tab 停靠点，方向键首尾循环切换并同时选中，选中页签的文字加粗并变宽，页签栏与内容之间留一个堆叠间距（10），切换页签时整棵树重新布局（各页签的内容高度不同，下面的内容要跟着挪），悬停底色只有上面两个圆角。
- 列表类控件（阶段 4）：`List`（只做 divided）的行是 `ListRow`（`SettingRow` 就是它），相邻两行之间留一条分割线的高度并画线，放进面板内容区时面板让贴着面板边的第一行去掉上内边距、最后一行去掉下内边距；`RowListItem` 是“前导（默认定宽 96，可指定宽度、带图标、用强调样式：强调色图标，文字仍是常规字重，图标 14 加间距 4 排在文字左边）、主文字（占满剩余）、信息列、行尾操作”排成一行，行高下限 26，文字单行、超出用省略号，鼠标移上去与按下时底色变化（行本身不响应点击）；`Toolbar` 左边是前导控件与一行说明、右边是操作，放不下时操作换到第二行，下方有一条分割线；`Tree`（扁平条目）整棵树只有一个 Tab 停靠点，上下方向键、Home、End 只移动焦点，回车与空格选中，点击在同一行内按下并松开才选中，焦点行由 `Widget::focusRect` 告诉外层的滚动区域滚进可见范围；`Tree` 另可按层级展开（条目按先序给出层级，下一项更深就是这一项的子项，每深一层右移 12，展开状态按标识保留，默认展开或收起可设；点箭头、双击、左右方向键展开与收起，左键在已收起时移到父项），条目可带图标与靠右的弱化色说明文字，右键在松开时触发回调（Shift+F10 与菜单键也会），放在滚动区域里时撑满可见高度，条目下面的空白处也能右键；`Table`（只做紧凑、平铺两个属性都开的样式）的列宽按浏览器的自动表格布局算：每列取“最小宽度”（列的最小宽度、表头、单元格最长不可拆部分中的最大者加左右内边距）与“最大宽度”（不换行的内容宽度），放得下时多出的宽度只分给设了 `grow` 的列（都没设时按最大宽度的比例分给全部列），放不下时在最小与最大之间按比例，再不够就取最小宽度；列可以设 `maxWidth` 限制最大宽度，超出的内容换行（mapper 插件表格里名称列 `grow`、匹配列上限 180）；`TableMainCell` 的主文字与说明都可换行，宽度随所在列；表头下边线与行与行之间（含详情行）的分割线各占独立的一条，行底色延伸到线的中心，行的最小高度 32 包含它两侧各半条线（所以最后一行的分割线之外的高度是 31.5），文字高度按网页版布局单位（1/64 像素）向下取整后再累加。
- 最小尺寸与并排排版（Ember 的对话框用，网页版没有）：`Widget::minimumSize()` 是控件要正常显示至少需要的尺寸（文字不被换行或挤压、控件不换行，说明这类段落文字允许换行不计入），默认没有要求（0），`Table`（各列取最小宽度）、`Facts`（按左右并排算：名称列加最宽的内容，不看窗口此刻是否算窄窗口，因为对话框刚创建时窗口还很窄）、`SettingRow`（并排模式）与 Ember 各对话框的内容重写它；`DialogFrame::minimumWindowSize()` 把正文的要求加上标题栏上按钮的宽度、正文四周的 10 与按钮区，另留半个像素的余量，对话框窗口据此回答系统的最小尺寸查询（向上取整到设备像素），宽度按内容算时打开宽度就是这个最小宽度（登记了初始宽度的对话框取它与最小宽度中大的），高度按内容算时初始高度抬到不小于它。`SettingRow::setSideBySide(true)` 是并排模式：窗口再窄也不上下排列，控件列靠行的右边、列宽取同一个 `List` 里各行控件的最大自然宽度（`List` 在度量与摆放前统一设置，保证各行控件左边对齐）、控件在列里左对齐不换行，名称与说明占满余下的宽度（说明可以折行），行的最小宽度是“名称与说明列的最小宽度（取名称的宽度与 min(说明的自然宽度, 160)中较大者，最大 420）加列间距 10 加控件列宽”；默认模式不变，仍与网页版一致。`Select` 没有给定宽度时取最宽的选项（切换选项时宽度不变，不小于 88）；`Toolbar` 的自然宽度含前导、说明、操作与它们之间的间距，宽度不少于它就不换行；`FlexBox` 的换行判断留 0.01 的容差，自然宽度刚好放下时不因浮点误差换行。链接样式的 `Button` 默认在宽度不够时折行（与网页版一致），`setWrap(false)` 关掉折行，且绘制时向右多给一点宽度、文字不被自己的区域裁切，网址这类不能断开的链接用（“关于 Ember”里的主页地址与项目地址）。
- 外壳类控件（阶段 5）：
  - 菜单（`MenuBar`、`MenuPopup`、`MenuItem`）：弹层项高 24、左右各留 4、勾选列宽 26、右侧留 26，快捷键、提示文字与子菜单箭头前再留 52，分隔线上下各留 5，弹层内边距上下各 4；菜单栏按钮高 24、左右内边距 8。弹层经 `Host::showLayer` 显示，子菜单是各自的弹层（右侧放不下改到左侧，两侧都放不下时向左滑到窗口右边缘、盖住父菜单的一部分，但父菜单左侧从父项的左边算起至少露出 40；还放不下就缩窄（不小于 120），名称与提示文字放不下的部分用省略号结尾）；键盘焦点留在菜单栏上，按键与字符由它转给最深的有高亮项的弹层；点击打开时高亮第一项、悬停切换和鼠标展开子菜单时不高亮、方向键打开时高亮第一项（上方向键为最后一项），左右方向键在顶层弹层里切换相邻的菜单，子菜单里左键或 Esc 只关子菜单，助记字母直接选中，可勾选项（非单选）选中后菜单保持打开。弹层的最小宽度取触发按钮的宽度，再宽由菜单项内容撑开（网页版定位时把弹层的最小宽度设成按钮宽度）；菜单项不多，弹层不滚动，放不下时裁掉。
  - 标题栏（`TitleBar`）：高 36（含底部 1 像素分割线），左边留 8，依次是应用图标（16；应用把可执行文件自带的图标资源（蓝色卡带图，`platform/window/app-icon` 按设备像素取最接近的一张并预乘透明度）交给 `ui/shell/app-logo` 经画布的 `drawBitmap` 画出，由 `bootstrap/application.cpp` 装到标题栏的 `logo`）、应用名（`Brand` 字体 13 号粗体、字间距 0.08em）与副名（500 字重、较淡）、菜单栏；右侧依次是操作区、折叠按钮（宽 46、占满内容区高度、相邻按钮用与底色相同的 1 像素竖线分开）和三个系统按钮；系统按钮宽 46、占满标题栏内容高度（不含底部分割线，底色与悬停色都不盖住分割线，分割线在按钮下面也是连续的，与 Electron 外壳的 `titleBarOverlay`（高 35）一致），图形是 10×10 的线条（最小化、最大化或还原、关闭），悬停与按下的颜色取系统常见样式（关闭按钮是系统的红色）。系统按钮的悬停与按下由 `FramelessFrame` 跟踪：窗口的 `WM_NCHITTEST` 调用 `TitleBar::hitTestWindow`，把 `Minimize`、`Maximize`、`Close` 转成 `HTMINBUTTON`、`HTMAXBUTTON`、`HTCLOSE`，空白处转成 `HTCAPTION`，其余是客户区；悬停状态由窗口根据非客户区鼠标消息、按下与松开由窗口捕获鼠标后的客户区消息，经 `setSystemButtonState` 告诉控件。
  - 状态栏（`StatusBar`、`StatusBarItem`）：普通高 26、大尺寸高 32（字号、图标、状态点、状态项内边距都有大尺寸的取值），顶部 1 像素分割线；状态项由状态点、图标（等级为警告、错误时配对应图标）、文字、文字后的长方形指示灯（或画在图标里的圆点灯）依次排列，部分之间留 4；左侧是可收缩的组，放不下时文字超过 16 个字符的状态项按“字符数的平方 × 原宽”分担收缩量（与 CSS flex-shrink 的算法一致）并以省略号结尾，右侧保持原宽靠右（可经 `addEndWidget` 放入通知按钮之类的别的控件）；按钮状态项的悬停、按下、选中用无底色按钮的颜色，`success` 等级的文字颜色盖过它们。状态项的等级枚举叫 `StatusItemTone`（`StatusTone` 已被 `StatusLabel` 使用）。
  - 悬停提示（`Tooltip`）：控件用 `Widget::setTooltip`（纯文字）或 `setRichTooltip`（标题行加分条说明）设置提示，空文字的提示盖住外层控件的提示；`Root` 负责时机：鼠标停在带提示的控件上 400 毫秒后弹出，已有提示显示时移到下一个控件立即弹出，点击、按键、滚轮、鼠标离开窗口、控件离开控件树时收起，点击后在鼠标离开该控件之前不再弹出；`Tooltip` 控件（经 `TooltipPresenter` 接口登记到 `Root`，由应用创建一个（主窗口与每个对话框窗口各自创建），必须先于 `Root` 销毁）负责排版与定位：纯文字内边距 4×8、最宽 320，版式提示内边距 8×10、最宽 380，宽高都不超过 80 的控件对齐控件、更大的对齐鼠标位置，默认在锴点右侧垂直居中、间距 10、放不下改到左侧，与窗口边缘至少 8，角标指向锴点中心。
  - 通知（`NotificationCenter`、`NotificationButton`）：`NotificationCenter` 是铺满窗口的弹层，只有通知与面板接收鼠标，窗口大小变化时经弹层回调重新摆放；新通知在右下角（离窗口边 10）向上堆叠、间距 6，最多 3 条（最早的先收起），停留 6 秒（错误 12 秒），历史最多 100 条；消息最多显示 3 行（面板里 4 行），超出的部分以省略号结尾，换行与连续空格按网页的排版折叠成一个空格；超过 60 个字符或含换行的消息可点击，点击后经 `setOnShowDetail` 回调由应用在“通知详情”对话框里显示全文；面板打开时收起弹出的通知并把未读清零，打开期间的新通知直接进历史；点击面板与通知按钮之外、Esc（应用的按键处理先调用 `handleEscape`）、窗口失去活动状态（`windowDeactivated`）时收起。通知的消息下面可以带一个链接（`notify` 的 `NoticeAction`：文字与点击后的动作，用链接样式的按钮，弹出的通知与面板里的历史都显示）。通知按钮是状态栏右侧的铃铛加未读数（超过 99 显示 99+）。
  - 对话框框架（`DialogFrame`）：只是独立窗口对话框里面的内容（窗口外框、缩放、阴影、模态都由系统和应用负责）：标题栏高 32（含底部分割线）、左 6 右 4、标题与按钮之间留 4，最大化与关闭是 24×24 的小方块、间隔 2，关闭悬停与按下用系统关闭按钮的红色（`setSystemButtons(true)`，Ember 的对话框用这种，换成和主窗口标题栏一样的系统按钮：最小化、最大化或还原、关闭，宽 46、占满标题栏高度、靠窗口右边紧挨着、线条图形与颜色同主窗口，图形与颜色由公共头文件 `system-glyph.hpp` 与标题栏共用，不参与 Tab 遍历；`setLogo` 在标题栏左边放 16×16 的图标；`setTitleDetail` 在标题后面接一段弱化色的说明文字，标题完整显示、说明用剩下的空间并在放不下时用省略号，磁盘镜像管理用它显示镜像目录）；正文在滚动区域里、四周留 10；按钮区上方留 6、下方与左右各留 10、按钮之间留 6、最小宽 72、靠右；标题栏空白处经 `hitTestWindow` 交给系统拖动（`HTCAPTION`）；Esc 请求关闭（请求与按钮的含义经回调交给使用方），回车在输入框或没有焦点时触发默认按钮（单行输入框没有设置回车回调时不处理回车，让它冒泡到对话框），初始焦点是对话框框架自己（不显示焦点框、不在 Tab 顺序里，`Widget::tabStop` 返回 false），不聚焦到按钮或正文里的控件上；`setContentFlushRight(true)` 在铺满正文区时去掉右边的内边距，滚动条贴到窗口右边；`setContentFlushVertical(true)` 去掉上下的内边距，正文紧挨标题栏与窗口下边（磁盘镜像管理用，分割线上下通到头，标题行自己给上边留空）。
  - 窗口框架（`AppFrame`）：只做 Ember 用到的属性：自上而下是标题栏、页面区（内容区底色）、底部面板（外壳底色、顶部 1 像素分割线、高度含这条线、不可拖动调整，高度限制在最小高度与窗口高度的 70% 之间）、状态栏（普通或大尺寸）；失去焦点时标题栏与状态栏换成失焦底色；有状态栏时通知中心让出状态栏的高度加 6 像素；没有活动栏、边栏、标签栏与右边栏。
- 单行文字输入框自己实现编辑（光标、选区、复制粘贴、撤销、词级移动、鼠标选择、输入法组合与候选窗位置），不嵌系统的输入控件，这样外观才能与令牌一致。
- 键盘：全部控件可用键盘操作，焦点环的显示规则与 05 第 2 节一致（画面区与窗口框架类元素不画焦点环）；菜单支持助记符与方向键。
- 无障碍：每个控件对外给出名称、角色、状态与值（UI 自动化提供者），见第 9 节第 8 项。

### 4.2 令牌与图标

- 生成器（`ui-kit/tools/`）读取 rujian-ui-kit 的 `ui-tokens.css`、`dark.css`、`light.css`、`ui-base.css`，解析 `var()` 引用、长度、颜色与阴影，生成 `src/generated/` 下的 C++ 常量；遇到不认识的写法直接报错，不跳过。
- 图标取自组件库使用的 Tabler 图标：生成器扫描 Ember 界面代码（`tools/kit-components.json` 的 `iconSources`）与已登记组件的源码里出现的 `icon<名称>` 标识符，取在图标数据里存在的那些（界面直接引用 18 个，加上已登记组件内部用到的，共 55 个，是“用得到”的超集）；把图标的 SVG 路径转成 Direct2D 路径几何，显示时取 24×24 画布中间的 20×20，描边宽度（`--icon-stroke-width`，屏幕像素）不随图标尺寸变化，端点与圆角为圆形，与组件库相同。系统栏按钮的三个图标（软驱、播放、暂停）另取自 IconPark：原图路径在 `third_party/iconpark/icon-data.json`（48×48 画布，只用 M、L、H、V、C、Z 的绝对写法），生成器缩放到 24×24 后和其他图标一起转成路径几何；路径里 `fill` 为 `accent` 的部分（原图里的蓝色填充）由 `Canvas::drawIcon` 的强调色参数填充，状态项按状态给色：等级为成功时填成功色（运行中的播放三角形），指示灯画在图标里时填灯的亮色或暗色（`lamp.onIconAccent`，软驱图标的方块），没有给强调色时这些部分只描边。
- 令牌变化后重新生成即可，不手改生成的文件；生成结果提交进仓库，`win32:check` 与 `test/win32-ui-kit-tools.test.ts` 都检查它们与生成结果一致；主题有浅色与深色两套，切换时整窗重绘。

### 4.4 与组件库的对照与测试

- 基线：用 Electron 自带的浏览器渲染组件库的真实组件（只作对照工具，不启动核心，不涉及应用构建），按“控件、状态、主题、缩放比例”逐项截图，作为基线（`ui-kit/tools/reference`，引用本机的组件库源码，参考页的结构与画廊示例页一一对应）；控件库的画廊程序（`rujian-ui-gallery.exe --render`）离屏渲染同一批场景。截图用调试协议的设备指标覆盖指定页面大小与缩放比例，保证截图像素严格等于“逻辑大小 × 缩放比例”（用窗口大小会被系统取整、截图被重采样），同时用 `force-device-scale-factor` 让浏览器排版用的设备缩放比例也等于目标缩放比例（不这样做，边框与轮廓线会按本机系统的缩放比例取整，截图因机器而异）；状态用真实的鼠标与键盘事件产生；参考页关闭过渡动画，只比较稳定后的状态；截图时关闭浏览器的 LCD 文字（`disable-lcd-text`），网页版的文字与原生版一样是灰度抗锯齿，样本之外的文字不会因彩边产生无关的像素差。
- 场景：`normal`（不带交互）、`hover`（鼠标移到样本中心）、`pressed`（再按下左键）、`focus`（按 Tab 键直到焦点落在样本上）；滚动区域页再加 `wheel`（鼠标移到样本上向下滚一格）、`drag`（在滑块上按下并向下拖 30 像素）；下拉框页再加 `open`（点一下展开弹层）、`openkey`（Tab 到下拉框后按“向下”键展开）、`openhover`（展开后把鼠标移到第三个选项上），菜单页（`menu`，三个单菜单的菜单栏）也用这三个场景（点一下打开时高亮第一项），悬停提示页（`tooltip`）再加 `tip`（鼠标移到样本上并等提示弹出）。弹层、提示与通知面板的区域按顺序排在所有样本之后（下拉选项；菜单弹层与各菜单项；提示；通知面板与各条历史），参与位置与外圈像素的对照（内部的文字与图标不比）；通知页（`notification`）与通知面板页（`notification-center`）在布局后发通知（画廊页的 `setup` 回调），弹出的通知就是样本；标题栏页（`title-bar`）不显示系统按钮（系统按钮的图形、悬停与按下颜色由单元测试的像素断言覆盖），对话框页（`dialog`）的样本是对话框整体（只用它标题文字所在的条形区域排除文字）、最大化与关闭按钮、正文和两个按钮，状态栏页（`status-bar`、`status-bar-large`）、窗口框架页（`app-frame`）各对照自己的样本；悬停提示页的三个按钮拉开到提示盖不住其他按钮（网页版提示背后有背景虚化，原生版没有，盖住时会透出轮廓）；子菜单的弹层不进像素对照（单元测试覆盖）。每一页的样本、要做交互场景的样本、各样本里不参与像素对照的区域（四边各自的边距，用来排除文字）都由画廊的 `--info` 给出；下拉框展开时弹层里的各个选项按顺序排在所有样本之后，也参与位置与文字外框的对照。分栏页（`split`）与页签页（`tabs`）的交互场景以分隔条、页签栏为目标；树页（`tree`）以整棵树为目标，信息行页（`row-list`）与表格页（`table`）的悬停、按下落在样本中心所在的行上，表格与工具栏样本里的文字按“左右（或上下）条带参与对照”排除；（样本里嵌着另一个样本时，Tab 次数只在被嵌的样本自己那一项计一次）；窗口宽度会改变布局的控件各有宽、窄两个页面（`facts` 与 `facts-narrow`、`setting-row` 与 `setting-row-narrow`）。
- 比较：控件位置偏差不超过 1 个逻辑像素；文字与图标之外的区域按像素比较，通道差超过 6/255 的像素不超过 4%、最大差不超过 125（圆角、焦点环与旋转箭头、对勾曲线上 Skia 与 Direct2D 的抗锯齿差别；100% 缩放下展开的箭头有约 0.5 像素的偏差）；文字与图标的外框各边偏差不超过 1 个逻辑像素（按设备像素向上取整），文字笔画的抗锯齿差异不算。这组阈值要能分辨“边框宽度错 1 个设备像素”这类差错，放宽之前先确认是拓扑差错还是抗锯齿。每个组合的网页版与原生版截图和 `report.json` 保存在 `build/ember/win32-reference`。
- 运行：`npm run win32:reference`（可加 `--scenes`、`--themes`、`--scales`、`--no-build`、`--gallery` 参数），先用 `win32:test` 构建画廊。
- 缩放比例取 100%、125%、150%、200%，主题取浅色与深色。
- 单元测试用 GoogleTest（与核心共用 `core/third_party/googletest`，路径可在控件库的 CMake 选项里改）：布局、状态转换、文字编辑、键盘操作、菜单导航。
- 画廊与测试只用离屏渲染与消息投递，不调用全局鼠标与键盘接口。

## 5. 应用程序

### 5.1 与核心的连接

- 原生应用在进程内持有 `Core`：启动参数按现有格式传入（用户数据目录、应用版本、预装插件目录（解压出来的 `bundled-plugins/`），以及命令行的 `--debug-port`、`--debug-token` 对应的 `debugPort`、`debugToken`，见 04）；请求、取消、事件与帧都用 `Core` 的回调，事件与请求结果从任意线程回到界面线程时经窗口消息投递。实现是 `infra/core-client` 的 `InProcessCoreGateway`（接口在 `contracts/core-gateway`）：`Core` 在后台线程启动，启动完成前收到的请求先排队，启动完成后按顺序发出；启动失败时排队的请求全部以错误结束；回到界面线程的投递由 `platform/threading/ui-thread` 的仅消息窗口完成；帧由核心线程写入 `LatestFrameSlot`，界面只取最新一帧。请求名与参数、结果类型的目录由 `schema-gen` 生成到 `contracts/core-gateway/generated/request-catalog.hpp`，界面与 `entry` 只经目录引用请求名。
- 请求名、参数与事件沿用 Schema；原生应用从 `schema/*.schema.json` 生成 C++ 类型使用核心已有的生成代码，不再另写请求格式。
- 画面：`FrameHandler` 在模拟线程调用，像素只在回调期间有效，所以原生外壳在回调里把帧复制进一个单槽缓冲并通知界面线程，界面线程取最新一帧绘制，旧帧直接丢弃；每帧恰好结算一次（被取走，或被更新的帧顶掉后计为丢弃），不积压。
- 声音由核心经 miniaudio 直接输出，原生外壳不处理声音。
- 调试服务、插件脚本、软驱与磁带等都在核心里，原生外壳只做界面。

### 5.2 主窗口与标题栏

- 主窗口是普通的顶层窗口，保留系统的缩放边框、最大化、停靠、贴边与系统菜单，去掉标题栏样式（`WS_CAPTION`）：带这个样式时，系统会把缩放边框的经典样式（浅蓝底、白线）画在窗口内容之上，画面子窗口盖住的地方就露出这一圈边框；用 `WM_NCCALCSIZE` 把标题栏区域并入客户区（最大化时客户区取显示器的工作区），`WM_GETMINMAXINFO` 把最大化的窗口矩形也限定为工作区（系统默认的矩形四周多出一圈缩放边框，会盖满整个显示器，系统把它当成全屏窗口而隐藏任务栏），自绘 36px 高的标题栏（图标、名称、菜单、“更新”按钮），菜单与按钮之间留约 50px 可拖动的空白。边框处理在 `platform/window/frameless-frame`（命中测试、系统按钮跟踪、窗口大小限制、阴影与边框），位置与最大化状态记在 `config/shell-state.json`（`platform/window/window-placement` 与 `infra/shell-state`）；窗口内容由 `ui/shell/main-window-view` 组装。主题跟随首选项 `appearance.theme`（`system`、`dark`、`light`）切换，`system` 时读系统的明暗设置，切换在 `entry/preferences/theme-sync`。窗口显示前先在隐藏时把界面画一遍（`HostWindow::show`），避免启动时先露出只有黑色画面区的半成品；容器摆放子控件时不先按整个窗口摆放一次，运行画面的子窗口才不会在每次重新布局（开机、断电、打开面板）时先盖到底部面板上再缩回去。
- 系统按钮（最小化、最大化或还原、关闭）也画在标题栏里，宽 46px、高与标题栏一致，图形取系统的样式（线条，不用字体图标，因为 Windows 7 没有它们的字体）；命中测试返回 `HTMINBUTTON`、`HTMAXBUTTON`、`HTCLOSE`，所以悬停提示、窗口贴边与 Windows 11 的贴靠布局仍由系统处理；按下后由 `FramelessFrame` 捕获鼠标、跟踪悬停与按下，在同一个按钮上松开才向窗口发 `SC_MINIMIZE`、`SC_MAXIMIZE`（已最大化时 `SC_RESTORE`）或 `SC_CLOSE`（去掉标题栏样式后系统不再跟踪这些按钮，Windows 7 上系统的跟踪还会画出系统样式的按钮）。
- 阴影与边框：Windows 11 及以上用 DWM 的阴影、圆角，边框色由 `DwmSetWindowAttribute` 设成界面的边框色（随主题更新，主窗口与对话框都设）；Windows 7、8、10 用自绘模式（`FramelessOptions::customFrame`）：关掉 DWM 对非客户区的绘制，阴影由 `platform/window/window-shadow` 在主窗口正后面放一个带逐像素透明度的分层窗口来显示（图像由 `shared/window/window-shadow-image` 按窗口大小算出：高斯模糊的矩形、下移 4、四周各 36 逻辑像素，激活时深、失去激活时浅），1px 边框由 `MainWindowView` 用边框色画（最大化时没有边框与阴影，全屏时也没有阴影）；开发时可用环境变量 `EMBER_WIN_FRAME=custom` 或 `system` 强制选择。
- 窗口首次显示：`HostWindow::show` 先在隐藏时画一遍（预热渲染目标与排字），显示时先用 DWM 的隐形属性（`DwmSetWindowAttribute` 的 `DWMWA_CLOAK`，Windows 8 起有，动态查找）让系统暂不合成这个窗口，立即重绘并等 `DwmFlush` 之后再取消隐形；否则系统刚显示窗口时会先合成一块白底，内容画好前对话框会闪白（mapper 插件对话框约 80 ms）。Windows 7 没有这个属性，照常显示。
- 缩放窗口：窗口改了大小后，系统把整个窗口当作没画过，到下一次呈现之间被合成就会闪出边框色（Windows 11 上是 DWM 边框色，整个窗口闪灰；子窗口所在的地方要等子窗口自己呈现，同样会闪）；`HostWindow` 在尺寸改变的第一时间（`WM_WINDOWPOSCHANGED`，在应用的消息钩子之前）先 `Resize` 渲染目标，立即用上一帧（`HostWindow` 每帧先画进一个与窗口等大的位图，再整幅呈现）把新大小画满，多出的部分是页面底色，这一步暂时去掉 `WS_CLIPCHILDREN`，连运行画面子窗口所在的地方一起画，再布局、重画；这段空档缩到最短仍不为零，偶尔（快速拖动时约百分之一的帧）还会闪出边框色，所以边框色要设成与界面协调的颜色（不设时是白色）。
- 打开着的菜单在点标题栏、系统按钮、缩放边框（这些点击不会作为客户区的鼠标消息到达控件）或窗口失去激活时关闭：`FramelessCallbacks::nonClientPressed` 与失去激活都调用 `Root::dismissLayers`。
- 缩放区在窗口边框线的外面和边框线本身（窗口里面最外一圈，宽度是 1 个逻辑像素向下取整、至少 1 个设备像素），边框线以内（含贴着边的滚动条）都是客户区：窗口自己的 `WM_NCHITTEST` 只在最外一圈返回 `HTLEFT` 等缩放结果（由 `ResizeBorder::hitTest` 算出）；窗口外面的缩放区由 `platform/window/resize-border` 的一个分层窗口提供，大小是窗口四周各多出系统缩放边框的厚度（`SM_CXSIZEFRAME` 加 `SM_CXPADDEDBORDER`，按窗口的 DPI 取），叠在窗口的正后面，以 1/255 的不透明度显示（几乎看不见但能接住鼠标），四角沿着边再延伸一倍厚度；它的命中测试返回 `HTLEFT` 到 `HTBOTTOMRIGHT`，鼠标指针由系统按命中结果换成缩放指针，按下左键时向主窗口发带方向的 `SC_SIZE`，由系统接着做缩放；窗口最大化、最小化、全屏、不可见或被禁用（模态对话框打开期间）时缩放区不接鼠标。主窗口与对话框都用 `FramelessFrame`，所以行为相同。
- 窗口大小（默认 524x500）、位置、最小尺寸（按画面的 1 倍算，经 `FramelessOptions::minimumProvider` 每次查询时重算；标题栏放不下的操作区不显示、菜单名在菜单栏边界处被截断，见 `TitleBar::arrange`、`MenuBar::paint`）、“设置→画面尺寸”（`WindowModes::resizeTo`）、窗口位置的保存与恢复规则同 05 第 2 节、第 9 节；多显示器、DPI 变化（`WM_DPICHANGED`）时整窗重新布局；Windows 7 与 8 只有系统级 DPI，按启动时的值处理。
- 主题：深色、浅色、跟随系统；跟随系统时读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` 的 `AppsUseLightTheme`，没有这一项的系统（Windows 7、8 与早期 Windows 10）按浅色处理；首选项 `appearance.theme` 变化立即生效，系统主题变化时监听 `WM_SETTINGCHANGE`。

### 5.3 对话框窗口

对话框是独立的顶层窗口，归属于主窗口（非模态的除外，见下），主题与主窗口一致，同一个对话框同时只开一个，再次打开时聚焦已有的；可缩放、最小尺寸、模态的规则以组件库的 `Dialog` 为准，标题栏与主窗口一致：左边是应用图标，右边是和主窗口同样的三个系统按钮（最小化、最大化或还原、关闭，宽 46、线条图形、关闭悬停为系统的红色）。对话框打开时的初始焦点在对话框自己上（不显示焦点框，不聚焦到某个按钮或输入框上）。对话框里的键盘事件与手柄读取挂在对话框自己的窗口上。对话框窗口有两个按键拦截选项，设置了就先于控件拿到不重复的按下（含带 Alt 的系统键），返回 true 表示按键被吞掉，这个键随后的字符与抬起消息也一并吞掉（吞掉的键按扫描码加扩展位记在集合里，所以先按下 Alt、Ctrl 再按字母的组合，每个键的抬起消息都被吞掉，系统不会把单按 Alt 当成激活系统菜单）：`onPhysicalKey` 给键位名（学习手柄的键盘绑定用），`onShortcutKey` 给虚拟键码与修饰键（首选项里设置快捷键用）；由组装根经 `DialogHost::setKeyCapture`、`setShortcutCapture` 按对话框标识设置。`DialogHost::closeAll` 在消息循环结束后、外壳销毁之前调用，对话框内容引用着外壳的模型，要先于它们销毁。对话框可以登记成非模态（`modeless`）：打开期间不禁用主窗口，窗口没有归属窗口（不总盖在主窗口上面，点主窗口时可以被盖到后面；主窗口只用来决定打开时居中的位置），打开后 `DialogHost` 在当前消息处理完之后把它带到最前面（打开它的菜单关闭时主窗口会重新取得焦点）；有自己的最小化按钮与任务栏按钮（只最小化自己，窗口加 `WS_EX_APPWINDOW`；模态对话框的最小化是最小化归属窗口）（磁盘镜像管理用）。`DialogHost::setOpenHook` 给对话框登记“打开钩子”：窗口创建并显示之后调用，参数是窗口与正文，返回的对象跟着对话框保存、关闭时先于窗口销毁（用来挂靠窗口句柄的资源）；`DialogWindow::clientPointFromScreen` 把屏幕坐标换成窗口内容坐标。

拖放（`platform/dragdrop/file-drag`）用系统的 OLE 拖放（`OleInitialize` 在窗口所在的单线程套间线程上）：`startFileDrag` 把内存里的文件作为“虚拟文件”拖出（数据对象提供 `FileGroupDescriptorW` 与 `FileContents`，内容用内存流提供，文件夹只有描述），同时带一个窗口内部用的标记（自定义格式，进程内的数字）；`FileDropTarget` 把窗口登记成拖放目标，按标记认出是本程序自己拖的还是从文件管理器拖进来的文件，拖动中按屏幕坐标向使用方询问能不能放、放下时交出路径或标记；拖出开始时核对鼠标主键仍按着。界面层不经系统拖放，经契约 `DiskImagesDragHost`（实现是 `infra/dragdrop/ole-disk-drag-host`）。

实现：`platform/window/dialog-window` 是对话框窗口（归属主窗口、打开期间主窗口不可用、居中在主窗口上，外框、阴影与最小尺寸由与主窗口相同的 `FramelessFrame` 处理（最小尺寸可以按内容算：登记表的 `fitMinWidth`、`fitMinHeight` 经 `DialogWindowOptions` 变成 `FramelessOptions::minimumProvider`，系统每次查询最小尺寸都取正文当时的 `minimumSize()`，初始大小也不小于它），销毁时先恢复主窗口，对话框在前台时再把前台交给主窗口，然后销毁窗口，避免系统把焦点交给别的程序，例如点开网页链接再回来关闭对话框时被 VS Code 一类的窗口抢到前面）；Alt+F4、系统菜单、对话框框架的关闭按钮与 Esc 都只请求关闭，窗口不自己销毁；“最小化”（按钮与系统菜单的 `SC_MINIMIZE`）把归属的主窗口最小化（对话框跟着隐藏，还原主窗口时一起回来），对话框自己不单独最小化（打开期间主窗口不可用，单独最小化会没有办法恢复）；`bootstrap/dialog-host` 是对话框的打开者（实现 `ShellDialogOpener`）：按登记表里的对话框标识取标题与大小，正文由组装根提供的工厂每次打开时新建，标题栏的应用图标也由组装根提供的工厂创建，关闭请求延后到消息处理之外再销毁，主题随主窗口。对话框框架 `DialogFrame` 的正文按内容高度排列，放不下时由框架的滚动区域滚动；左右分栏、自己负责滚动的正文（首选项、mapper 插件、关于）用 `setContentFill(true)` 铺满正文区，并用 `setContentFlushRight(true)` 让正文区右边不留内边距，正文里的滚动条贴到对话框的右边，正文自己给右边留 10 的空。

### 5.4 主进程请求的原生实现

下面 20 个请求由外壳自己处理（不进入核心），在 `app/src/entry` 里实现；路径只来自用户在系统窗口里的选择、拖入主窗口的文件或启动参数，界面层拿不到任意路径。

| 模块 | 请求 | 原生实现 |
| --- | --- | --- |
| cartridges | `open`、`recent`、`openRecent` | 系统文件选择窗口（`IFileOpenDialog`，Windows 7 可用）、最近打开清单（`config/recent-cartridges.json`，最多 10 个） |
| machines | `openRom`、`openRoms`、`openRomDirectory` | 文件选择、文件夹选择、用资源管理器打开 ROM 目录 |
| mappers | `openPackage` | 文件选择（`.emap`） |
| media | `openFloppy`、`openTape`、`openTapeRecording`、`openPrinterDirectory` | 文件选择与保存窗口，保存录音用保存窗口；用资源管理器打开核心给出的打印机图片目录（`DirectoryOpener`） |
| diskimages | `openRoot`、`pickRoot`、`importDropped`、`loadImage`、`revealImage` | 镜像目录保存在 `config/shell-state.json` 的 `diskImagesRoot`，`openRoot` 把它交给核心，`pickRoot` 用文件夹选择窗口选并保存；`importDropped` 把拖入窗口的文件（登记过的编号）的路径交给核心；`loadImage` 经 `diskimages.imagePath` 取路径后交给 `media.floppyInsert`；`revealImage` 用资源管理器显示并选中镜像文件（`DirectoryOpener::reveal`） |
| preferences | `pickDirectory` | 文件夹选择窗口 |
| system | `openLogDirectory`、`openHelp`、`updateStatus`、`checkUpdate`、`installUpdate` | 见 5.6 |

另有：文件选择窗口按用途记住上次目录（`config/last-directories.json`）；拖放文件用 `WM_DROPFILES`，登记后只把编号交给界面（见 05 第 2 节）；`mainOnly` 的 6 个核心请求（如 `cartridges.load`）只由这些处理在内部调用。主进程请求按模块放在 `entry/<模块>/`，由 `entry/main-requests` 的路由登记并校验参数，未登记的请求直接拒绝。帮助与升级的请求见 5.6。

### 5.5 画面与输入

- 画面区是主窗口里的一个子窗口，用 Direct3D 11 显示核心给出的 RGBA 帧（R、G、B、A 的内存顺序，每像素 4 字节）：每帧把像素上传到动态纹理，适应窗口用双线性采样（画面效果为“像素”时改用最近邻采样），整数倍用最近邻采样；全屏且首选项选了“拉伸铺满”时画面铺满整个子窗口（`ScreenScaling::Stretch`，由画面控件按全屏状态传入，首选项里没有这个缩放值），采样仍按画面效果；交换链用 DXGI 1.0 的位块传送模式（Windows 7 没有翻转模型），设备功能级别最低取 9_1。比例（4:3、8:7）、裁剪（显示全部 240 行）、画面框、黑底与 05 第 7 节一致（版面规则在 `shared/screen/screen-layout`）；“未开机”“已暂停”等提示与右下角的提示框（键盘独占与鼠标捕获各一个框）由控件库预先画成位图（框的底色是半透明的，没有边框），作为纹理叠在画面上；毛玻璃在叠位图之前完成：画面子窗口拿到各个提示框的矩形（`setOverlay` 的 `glass`），把它们与画面相交的区域逐个用“毛玻璃”着色器重画一遍（着色器按提示框的圆角半径，`setOverlay` 的 `glassRadius`，把圆角之外的像素丢弃；level_9_1 的像素着色器拿不到屏幕位置，由纹理坐标换算）（对画面纹理做 17 点采样的模糊，内圈半径 5 像素、外圈 10 像素，权重 4:2:1），再叠上位图，所以框里的画面是模糊的、框外清晰。先创建硬件的 Direct3D 11 设备，创建不出时（没有显卡、没有驱动、虚拟机没有 3D 加速）改用 WARP 软件设备（同样的功能级别列表、同样的预编译着色器，只换驱动类型）；两者都创建不出时，在启动时弹出“无法初始化画面渲染，当前电脑不支持”的提示并退出，不做 GDI 降级。着色器预先编译：`platform/display/screen.hlsl` 经 `npm run win32:shaders`（`tools/build/gen-screen-shaders.mjs`）用 Windows SDK 的 `fxc` 生成 `vs_4_0_level_9_1`、`ps_4_0_level_9_1`（画面与毛玻璃两个像素着色器）字节码，生成结果（`screen-shaders.generated.cpp`）提交进仓库，运行时不依赖 `d3dcompiler`。画面子窗口对鼠标透明（`HTTRANSPARENT`），鼠标输入都由主窗口里的画面控件接收；菜单、悬停提示与通知这类弹层盖到画面上时，控件库把弹层的矩形报告给应用（`Widget::layerRects`、`Root::setLayerRectsHandler`），应用用 `SetWindowRgn` 把画面子窗口对应的矩形挖掉，弹层才显示在画面之上（差异见第 10 节）。
- 键盘、鼠标与游戏手柄只采集原始事件，格式与现有的输入消息一致，交给 `Core::sendInput`。
- 键盘采集有三种方式（`KeyboardMode`）：关闭、共享、独占。画面区获得焦点且窗口在前台时才采集，焦点离开、窗口失去激活、关闭窗口时关闭；采集时向系统登记原始输入的键盘设备（目标是主窗口），直接在窗口过程里处理 `WM_INPUT`，不用全局键盘钩子，按键以“扫描码加标志”交给机器，Win 键、Ctrl+Alt+Del 与 Alt+Tab 仍由系统处理。选哪种由运行模型的 `exclusiveKeyboard` 决定（`logic/runtime/runtime-rules` 的 `exclusiveKeyboard`）：接入了 Family BASIC 键盘，或已开机的是学习机整机机型（不是经典 FC）时独占，其余共享。
  - 独占（`RIDEV_NOLEGACY`）：进程内不再产生传统键盘消息，除 F9、F10、F11、F12 外的所有物理按键都只交给机器，所以外壳快捷键（F7、F8 等）与 Alt 加字母的菜单助记键都不生效（见 05 第 5 节）；F9 到 F12 始终留给外壳：`ScreenHostAdapter` 在原始输入里认出它们（`shared/input/scan-code-table` 的 `isAlwaysShellKey`），不上报给机器，按下时（按住不放只触发一次）经 `setOnShellKey` 交给外壳的快捷键处理（`runShortcut`），所以 F9 开机与断电、F11 全屏在独占时也有效；用鼠标操作菜单与面板按钮，画面右下角的提示框会说明；主窗口里点完鼠标、关闭菜单、执行完运行操作后焦点都回到画面（菜单打开期间焦点在菜单上，采集已关闭，菜单可以用键盘操作）。
  - 共享（不带 `RIDEV_NOLEGACY`）：传统键盘消息照常产生，外壳快捷键与菜单助记键照常生效；`ScreenHostAdapter` 把 F1 到 F24、Tab、Escape 以及按着 Ctrl、Alt、Meta 时的其他键留给外壳（不上报，规则在 `shared/input/scan-code-table` 的 `isShellKey`），修饰键本身与其余键照常上报；松开事件总是上报（输入端口忽略没按下过的键），避免先按普通键、再按修饰键后普通键卡住。
- 鼠标捕获：点击画面后隐藏指针并用相对位移（`ClipCursor` 与 `WM_INPUT`），双击右键（400 毫秒内两次右键按下，第二次不送给机器）释放。
- 游戏手柄：每个画面帧读一次，Windows 7 自带的 XInput 9.1.0（动态加载，不依赖需要另装的 `xinput1_3.dll`）读 Xbox 类手柄，按“标准映射”给出按钮与轴的编号；设备标识的格式与浏览器里的 `Gamepad.id` 保持一致，手柄绑定按它认出是哪个手柄。非 XInput 的 USB 手柄（DirectInput 一类，如北通的 DInput 模式）由 `platform/input/joystick-gamepads` 用 Windows 7 自带的 winmm 手柄接口（`joyGetPosEx`，最多 12 个）读取，不做标准映射：按钮按系统报告的顺序给出原始编号（最多 32 个），轴 0 到 5 依次是 X、Y、Z、R、U、V（没有的轴恒为 0），轴 6、7 是方向帽的左右与上下；设备标识为“名称 (Vendor: 厂商号 Product: 产品号)”，位置从 4 开始，不与 XInput 的 0 到 3 重叠；系统会把 XInput 手柄也列成通用控制器，这里按硬件标识（HID 路径里带 `IG_` 的设备）跳过它们，免得同一个手柄出现两次。两种读取由 `platform/input/gamepads` 合并，画面区与手柄设置对话框各用各的实例。
- 开发期诊断：环境变量 `EMBER_WIN_DIAGNOSTICS` 指向一个文件时，应用退出时把帧计数（核心送来、画出、被新帧顶掉）与每一帧从核心发布到画出的延迟（平均、p95、最大）写成 JSON，没有设置时不记录；“画出”是帧上传并提交给 Direct3D 的时刻，不含合成器与显示器的延迟。`tools/dev/latency-win32.mjs` 用它测量（Release 版，1-len_ctr 运行 30 秒：核心送来 2293 帧，画出 2285 帧，被新帧顶掉 8 帧（0.35%），延迟平均 0.46 毫秒、p95 0.62 毫秒、最大 5.96 毫秒）。

### 5.6 帮助与升级

- 帮助文档：站点（`npm run help:build` 的构建结果）与预装插件、第三方许可全文一起由 `npm run resources:pack` 打成一个 zip，CMake 把它作为资源 `EMBER_RESOURCES` 嵌进 `ember-win32.exe`（某一类还没构建出来时跳过并提示）；外壳在本机 `127.0.0.1` 的随机端口提供只读服务，直接从内存里的资源包读页面，不解压（路径含 `..` 或编码斜杠的一律拒绝；请求头有大小与读取超时的限制，只收 GET 与 HEAD，Host 头必须是本机地址与本服务的端口，防 DNS 重绑定），用系统默认浏览器打开。Windows 7 上的默认浏览器可能不能运行站点（VitePress 需要较新的浏览器），所以首次打开时检测并提示，见第 9 节第 1 项。实现：`platform/network/local-http-server`、`shared/help/help-request`、`infra/help`（`ArchiveHelpSite`、`LocalHelpViewer`）、`platform/resources/embedded-archive`、`infra/resources/zip-archive`（经契约 `contracts/resources/resource-archive` 使用）。预装插件在首次启动或资源包指纹变化时解压到用户数据目录的 `bundled-plugins/`（`infra/plugins/bundled-plugins`）。
- 打开日志目录、ROM 目录：用资源管理器打开；路径由原生外壳决定。
- 升级：只做自动升级，不做安装程序（发布物是放在 zip 里的单个可执行文件）。清单 `latest.json` 与新程序放在仓库的 `updates/ember/windows/`，由 GitHub Pages 经自有域名 `fcdev.cn` 对外，清单带版本、文件大小、SHA-256 与 RSA 签名，签名公钥写在程序里；下载经 WinHTTP，只用 HTTPS（干净的 Windows 7 要安装 KB3140245 才有 TLS 1.2，失败时提示这一点，不回退到 HTTP）；校验通过后暂存，用户点“更新”时由暂存的新程序等旧进程退出、覆盖旧程序并重新启动。升级逻辑由 `system.updateStatus`、`system.checkUpdate`、`system.installUpdate` 三个请求与状态推送对外。模块、清单格式、发布流程与演练方法见 01 第 11 节与 06 第 11 节。
- 升级内容仍写在帮助文档的“更新记录”页，新版第一次启动时自动打开一次。

### 5.7 用户数据与单实例

- 用户数据目录：与 Mesen 一样二选一，可执行文件所在目录里有 `ember-data` 目录就用它（便携用法），否则用 `%APPDATA%\Ember`；启动参数 `--user-data-dir` 可以临时指定。首选项的“应用”分组显示当前目录（点击用资源管理器打开）与切换按钮：以 `--move-user-data=<executable|profile> --wait-pid=<旧进程号>` 启动新实例，等旧进程退出后复制（排除 `lockfile`、`run/`）、核对大小、改名并删除旧目录，目标目录已有数据时拒绝，exe 所在目录不可写时置灰（`platform/files/user-data-location`、`logic/preferences/user-data-controller`、`bootstrap/user-data-move`）。`config/` 下各文件的名称与格式见 01 第 9 节（`shell-state.json`、`recent-cartridges.json`、`last-directories.json`、`preferences.json`、手柄绑定、`roms/`、插件目录），按同样的校验规则读写；文件不存在或损坏时用默认值。
- 单实例：沿用首选项 `app.allowMultipleInstances`（见 05 第 4.5 节）；按 Chromium 的 ProcessSingleton 约定（用户数据目录下独占打开的 `lockfile`、类名 `Chrome_MessageWindow` 且标题为用户数据目录的消息窗口、`WM_COPYDATA` 传递命令行）识别同一个用户数据目录里已在运行的实例：同一个用户数据目录再启动会被拒绝，并把已有窗口提到前面；命令行与后启动进程的当前目录经 `WM_COPYDATA` 传到已有进程，已有进程按命令行里的 `.nes` 路径（相对路径按后启动进程的当前目录算）打开卡带，后启动进程在通知前把前台权限交给它（`platform/process/single-instance`、`platform/process/command-line`）。
- .nes 文件的打开方式：启动时（取到单实例之后、调试会话除外）调用 `platform/shell/file-association`，在当前用户的注册表（`HKEY_CURRENT_USER\Software\Classes`）里登记类型 `Ember.Cartridge`（显示名、图标、打开命令 `"程序路径" "%1"`），并把它加进 `.nes\OpenWithProgids`，让 Ember 出现在“打开方式”里；`.nes` 还没有默认程序时再把它设为默认，已有默认程序（含用户在系统里选定的）不改。不需要管理员权限；内容已是最新时不写注册表、不通知资源管理器；失败只写日志。
- 双击 `.nes` 文件时系统把路径直接作为命令行参数传来，启动参数解析（`shared/launch/launch-args`）认第一个扩展名是 `.nes`、又不是选项或选项的值的参数；加载流程与 `--cartridge=` 相同。

### 5.8 设备面板与调试模式

- 行为同 05 第 4.3、6 节；实现是 `media` 与 `debug` 两个模块（逻辑层 `logic/media`、`logic/debug`，契约 `contracts/media`，界面 `ui/media`），在 `bootstrap/application.cpp` 里与 `shell`、`runtime` 一起登记，登记顺序是 `shell`、`runtime`、`media`、`diskimages`、`debug`。
- 状态以核心为准：控制器在核心就绪、收到 `media.changed`、`runtime.stateChanged`、`machines.changed` 与核心重启后读取 `media.floppyStatus`、`media.printerStatus`、`media.tapeStatus`，内容没有变化时不通知；读到磁带、磁带的序号（`serial`）变了或时间轴还在分析时再读 `media.tapeTimeline`，收到 `media.tapeAnalyzed` 时立即再读，没有磁带时清空（时间轴的内容经 `MediaModel::timelineView` 单独给出，不放进被频繁比较的 `MediaView`，规则在 `logic/media/media-rules`）；软驱的读写状态与磁道、磁带的位置、打印机的状态随机器运行变化，核心不推送，所以设备面板展开期间由面板内容控件用一次性定时器每 500 毫秒让控制器重新读取一次（展开时先读一次，收起时内容卸载、定时器随之取消）。
- 系统栏：设备按钮是软驱图标，顶部的方块是读写灯（`lamp.onIconAccent`，亮时填亮绿色，灭时填暗色），任一软驱的马达在转时亮；软盘名是静态登记的 `media.floppy.0` 到 `media.floppy.3` 四个状态项（核心的软驱编号最大到 3），没有盘片的软驱返回空值不显示，有多个软驱时前面带驱动器名；右侧的“调试模式”项是 `debug.service`，点击执行命令 `preferences.open`（打开首选项对话框，见 5.9）。
- 设备面板用控件库的信息行（`RowList`、`RowListItem`）与只有图标的幽灵按钮；行里的状态文字会变化，所以信息行增加了 `setCellText`（取文字宽度的列变宽时只重排这一行）；磁带机一行的位置列用 `setCellAction` 设为可点击（里面有磁带且不在录音时才可用），点击后由面板内容控件打开 `TimelinePopup`（弹层归面板内容拥有，内容卸载时随之关闭，松开鼠标时经模型的 `seekTape` 发 `media.tapeSeek`）。载入软盘镜像、载入磁带、选择录音文件经主进程请求 `media.openFloppy`、`media.openTape`、`media.openTapeRecording`（5.4）。
- 拖放：拖入的软盘镜像（`img`、`ima`、`vfd`、`dsk`、`flp`、`do`、`po`、`nib`、`woz`）载入软驱 A，拖入的声音文件（`m4a`、`mp3`、`wav`、`aac`、`flac`、`ogg`、`opus`、`mp4`、`mka`）载入磁带机（只载入，不自动播放），`.nes` 由运行模块认领；三者都经外壳登记的文件处理项（`WM_DROPFILES` 取文件，登记成拖入文件编号再交给主进程请求）。
- 调试服务：启动参数 `--debug-port`、`--debug-token`（5.7 的用户数据目录规则同样适用）开启，核心写端点文件 `run/debug-endpoint.json`，客户端按它自动连接；已用扩展的联调测试（`vscode/test/real-emulator/`；连接、请求、事件、截图、单步、断点、监视、指令跟踪，全部通过）和 FC Dev 扩展的启动器（设置 `fcdev.emulator.path` 指向 `ember-win32.exe`：经典 FC 调试模式载入卡带、学习机方案自动在 SB-DOS 里运行 HELLO）对原生程序跑通。

### 5.9 首选项与手柄设置

- 行为同 05 第 4.5、4.6 节；实现是 `preferences` 与 `input` 两个模块（契约 `contracts/preferences`、`contracts/input`，逻辑层 `logic/preferences`、`logic/input`，界面 `ui/preferences`、`ui/input`），在 `bootstrap/application.cpp` 里与其他模块一起登记；两个模块各登记一个对话框（宽高都按内容算最小尺寸，打开时用最小宽度；首选项另登记初始高度 520，打开时高度取它与最小高度中大的，手柄设置打开时用最小高度）与打开它的命令，菜单项在“设置”菜单里依次是“首选项”（快捷键 Ctrl+,）、“手柄设置”、“机型与 ROM”、“mapper 插件”、分隔线、“画面尺寸”（子菜单）、“全屏”、“窗口始终置顶”。控制器由组装根创建，登记项与对话框内容共用同一个。
- 首选项：设置项与分组来自核心（`preferences.list`），界面不认识具体的设置项；`PreferencesController` 在核心就绪后读取、订阅 `preferences.changed` 保持取值最新、核心重启后重新读取；修改与恢复默认不在本地先改，请求成功后以核心给出的取值为准，失败时保持原样并用外壳通知给出核心的说明；整数输入框失焦或按 Enter 时校验并提交，不合法时只把输入框标红并在行里显示原因。“机型与 ROM”对话框由机型模块（`machines`）的 `RomController` 负责（机型清单、添加或替换与移除 ROM 用系统文件选择窗口、用文件管理器打开 ROM 目录，结果与错误用通知给出）。内容控件在取值变化时只更新对应行的控件（取值、恢复默认按钮、错误提示），切换分组或清单变化时才重建右侧内容；左栏是分组导航，宽度默认 140，可拖到 320。05 第 4.5 节规划的“路径”分组（用户插件目录、开发中的插件目录）还没有做，需要时再加。导航最后的“快捷键”分组不是核心登记的设置项，由页面自己提供：`PreferencesContent` 的第三个构造参数是外壳的 `KeybindingsModel`（实现在 `logic/shell/keybindings-controller`，由 `ShellController` 持有、经 `keybindings()` 交出；没有传时不显示这个分组），组装根同时给首选项对话框设置 `onShortcutKey` 拦截，把按键交给 `shortcutKeyPressed`；快捷键页只更新控件、不重建（点击中的按钮不能被销毁），对话框最小宽度计入这一页、最小高度不计入。
- 手柄设置：`GamepadSettingsController` 读取两个玩家的绑定、订阅 `input.bindingsChanged`，并记住对话框里的操作状态（当前玩家页签、每个玩家的输入来源与选中的键、正在学习的键）；纯规则（10 个键、键名与手柄按钮的显示文字、键盘键在两个玩家之间不重复、从手柄状态的变化里认出被按下的按钮或轴、绑定与核心 JSON 的互转）在 `logic/input/pad-rules`。学习键盘绑定时，对话框窗口的物理按键拦截（`DialogWindowOptions::onPhysicalKey`）先于控件拿到按键，键位名由扫描码得出（与键盘布局无关），被吞掉的键的字符与抬起消息也一并吞掉。学习手柄绑定时对话框用自己的定时器读取手柄，`infra/input/system-gamepad-reader` 读取系统里的手柄（XInput 与通用 USB 手柄，与画面区读手柄的是同一个读取实现，各用各的实例），设备标识的格式与浏览器里的 `Gamepad.id` 一致。手柄图是 `PadDiagram`，版面数值在 `ui/input/pad-layout`。
- 控件库为这两个对话框做的补充：`PadDiagram`、`DescriptionRow`（见 4.3）；`ScrollArea::setFitContent`（内容比视口矮时按内容高度）；`DialogFrame::setContentFill`；`HostWindow` 的归属窗口选项；`Widget::requestLayout`（控件内容改变高度时通知根重新布局）；文字排版测量的缓存（同一段文字在同样的宽度下不重复测量）。
- 在开发中发现并已修复：容器摆放子控件时先按整个区域摆一次、再按实际大小摆一次，嵌套 8 层时同一个控件被摆放 256 次，首选项打开明显卡顿；改为容器只用 `setBounds` 定位子控件、子控件自己摆放自己的内容（改动在 `FlexBox`、`Panel`、`List`、`SplitView`、`ScrollArea`、`SettingRow` 等）；下拉框弹层里的选项文字按弹层宽度被错误截断，改为取选项自然宽度。
- 未验证：真实的手柄学习（开发机没有手柄，只有读取端口的单元测试与键盘学习的实机检查）；通用 USB 手柄（北通 DInput 模式）的读取只有单元测试，待用户实机验证。

## 7. Windows 7 兼容策略

- 工具链：v143 的 14.44 工具集；运行库静态链接（`/MT`），所以不要求用户安装 VC 运行库、也不要求补丁 KB2999226；核心现有的 `CMAKE_MSVC_RUNTIME_LIBRARY` 已是静态。
- 目标版本：`_WIN32_WINNT=0x0601`，应用清单声明支持 Windows 7、8、8.1、10 与 11，并声明 DPI 感知（按系统支持的最高级别，运行时检测 `SetProcessDpiAwarenessContext`、`SetProcessDpiAwareness`、`SetProcessDPIAware`）。
- 系统接口：用到的比 Windows 7 新的接口一律运行时检测、没有就降级；导入表审计脚本（`win32:check`）列出可执行文件与全部静态库导入的函数，对照 Windows 7 SP1 的导出清单基线，出现不在基线里的导入就报错。基线由 Windows 7 SP1 环境导出一次后提交。
- 不依赖的东西：.NET、WebView2、DirectX 最终用户运行库、平台更新（Direct2D 1.1、DXGI 1.2）、新版 TLS；Direct3D 只用 Windows 7 SP1 自带的 11.0 基础接口与 DXGI 1.0。
- 核心里已知要核对的点：`std::filesystem`、`std::condition_variable`、miniaudio 的 WASAPI 初始化、Winsock、`FileWatcher`（`ReadDirectoryChangesW`）、子进程管道、`GetSystemTimePreciseAsFileTime`、`SetThreadDescription` 一类较新的接口；阶段 0 逐项审计，必须改核心时只改 `platform` 层并保持其他系统的行为不变。
- 验证：Windows 7 SP1 的干净系统（用户的 Hyper-V 虚拟机：没有任何补丁、没有硬件 3D）、Windows 10、Windows 11 各跑一遍；Windows 7 与 8 上读不到的系统主题按浅色。Hyper-V 里的 Windows 7 没有 WDDM 显卡，Direct3D 11 的硬件设备创建不出来，画面区在这台虚拟机上走 WARP 软件设备（探针实测：WARP 设备功能级别 10_1，纹理上传与交换链呈现都通过），有显卡的 Windows 7 上的硬件显示由用户在发布前找真实用户验证（探针在这台虚拟机上其他全部检查都通过，硬件设备一项失败的原因见报告中的诊断信息）。探针里“Direct3D 11 软件设备（WARP）”三项（设备、纹理上传、交换链呈现，失败只记提示）用来确认软件设备在目标系统上可用。
- Windows 7 SP1 的全量回归（含升级、帮助文档与用户数据目录切换在 Windows 7 上的实机运行）2026-11-20 由用户决定不做，按通过处理，出现问题再处理。

以下各项已由用户确认，按“建议”执行，其中第 8 项的备选不采用，第 9 项经探针实测 WARP 可用后，按用户的新决定改为回退到 WARP。

1. **帮助文档怎么显示。** 站点需要较新的浏览器，Windows 7 的默认浏览器可能是 IE 11。建议：随包带站点，用本机只读服务加默认浏览器打开，检测到浏览器过旧时提示用户安装较新的浏览器。备选：内置固定版本的 WebView2 运行时（体积很大）或把手册改写成原生控件显示（不能保证排版与搜索）。
2. **发布与升级。** 已改为：不做安装程序，发布物是放在 zip 里的单个可执行文件；只做自动升级：清单 `latest.json` 与程序文件放在仓库的 `updates/ember/windows/`（由 GitHub Pages 经自有域名 `fcdev.cn` 对外），清单带版本、文件大小、SHA-256 与 RSA 签名，公钥写在程序里；下载只用 HTTPS（干净的 Windows 7 要安装 KB3140245 才有 TLS 1.2，失败时提示这一点，不回退到 HTTP）。
3. **控件库的名称、形态与许可。** 建议：位置 `ember/win32/ui-kit`，库名 `rujian-ui-kit-win32`，命名空间 `rujian::ui`，用 CMake 项目（可生成 Visual Studio 解决方案，也可在 VS 里直接打开文件夹），许可证用与 rujian-ui-kit 相同的 Apache-2.0，应用程序（GPLv3）链接它没有冲突。备选：直接写 `.vcxproj`（与 CMake 二选一，不建议维护两份）。
4. **核心的小改动。** 你说核心不用动；Windows 7 兼容审计可能发现个别接口需要降级。建议：允许只在核心的 `platform` 层做运行期降级与 CMake 目标调整，不改任何功能与请求格式，其他系统的行为不变。
5. **Windows 7 测试环境。** 已确认：最低支持 Windows 7 SP1 x64，用户提供 Windows 7 SP1 虚拟机（Hyper-V，没有任何补丁、没有硬件 3D，画面走 WARP 软件设备；硬件显示由用户发布前找真实用户验证）；我在本机只能静态审计导入表并在 Windows 10、11 上运行，Windows 7 上的实际运行由用户按我提供的脚本与步骤运行并回传结果。
6. **窗口按钮的画法与菜单位置。** 菜单放在标题栏上，就必须自绘三个系统按钮的图形，行为仍全部交给系统。建议按 5.2 做；备选：保留系统标题栏，菜单放在它下面一行（不建议）。
7. **非 XInput 手柄。** 已决定：用 winmm 的通用控制器接口读取，按钮与轴给原始编号、不做标准映射（用户的北通手柄在 DInput 模式下需要识别）；实现见第 5.5 节。
8. **无障碍。** 构建入口已定为两个脚本，不再需要默认值。建议随控件一起做基础的 UI 自动化提供者（名称、角色、状态、值），让读屏软件等辅助工具能读出控件；备选：只做键盘可达，不做 UI 自动化。
9. **没有硬件 3D 的环境。** 已确认：硬件设备创建不出时回退到 WARP 软件设备（用户的 Hyper-V Win7 虚拟机上探针实测通过），两者都创建不出时弹出提示并退出；不做 GDI 降级。
10. **右键菜单与加载动画不做。** 已确认：组件库的输入框右键菜单（网页版里没有传入宿主能力，菜单里没有“粘贴”，按组件库的代码点其他项也不会执行，未在界面上实测）与 `State`、`StatusLabel` 里的像素格加载动画，模拟器用不到，原生外壳都不做：输入框上右键不弹自绘菜单，“加载中”不显示动画也不显示文字（数据来自本机核心，加载很快）；差异登记在第 10 节。

## 10. 已知差异

已知会出现的差异登记在这里，开发中逐项补充；文字笔画的抗锯齿与字重在不同的渲染引擎里有细微差别，不登记。

| 项 | 差异 | 原因 |
| --- | --- | --- |
| 右键菜单 | 网页版的输入框上右键会弹出组件库的编辑菜单，原生外壳不弹出 | 用户决定模拟器用不到（第 9 节第 10 项） |
| 加载中状态 | 网页版的“加载中”带像素格动画和文字，原生外壳什么都不显示 | 同上 |
| 弹层的背景虚化 | 网页版的下拉弹层、菜单、悬停提示、通知与通知面板背后有背景模糊（`backdrop-filter`），原生外壳没有；弹层底色是半透明的，只有弹层盖在有内容的区域上时才看得出区别（提示、通知贴着按钮或内容时能透出后面的轮廓） | Direct2D 1.0 没有模糊效果，也不能读取窗口后面的像素 |
| 外阴影的模糊 | 弹层、对话框的外阴影用逐层叠加的圆角矩形逼近高斯模糊，边缘的渐变与网页版有细微差别 | 同上 |
| 弹层盖在画面上 | 菜单、悬停提示与通知盖在运行画面上时，画面子窗口按弹层的外框矩形挖洞，弹层圆角之外的四个角露出的是窗口底色而不是画面；弹层底色的半透明与外阴影也看不到后面的画面 | 画面是独立的 Direct3D 子窗口，系统只能用矩形区域把它让出来，做不到按圆角或透明度合成 |
| 旋转箭头的边缘 | 100% 缩放下展开的下拉框箭头与网页版相差约 0.5 个像素 | 网页版对旋转元素的取整细节没有完全还原 |
| 悬停过渡 | 网页版的底色、边框颜色有 150 毫秒的过渡，原生外壳直接切换到目标状态（分隔条的 200 毫秒悬停延迟保留） | 不做逐帧过渡；对照时网页版也关闭过渡 |
| 页签下划线两端 | 选中页签的下划线有 2 像素的顶部圆角，两端各有一个像素的抗锯齿与网页版不同（100% 与 125% 缩放下网页版的渲染还多出一个淡色像素），对照时下划线只比较外框 | 两种光栅器对 2 像素高的圆角形状处理不同 |
| 滚动区域的 `bleed` | 控件库的 `ScrollArea` 仍没有 `bleed` 属性；首选项与手柄设置的滚动由对话框框架的滚动区域（滚动条在对话框正文区的右边缘）与首选项右栏自己的滚动区域承担，没有用到它 | 阶段 9 的页面不需要，以后有容器需要时再做 |
| 手柄图与说明行 | `PadDiagram`、`DescriptionRow` 是 Ember 自己的控件，没有网页版基线可以像素对照，只有单元测试与实机检查 | 它们不在组件库里 |
| 时间轴弹层与信息行的可点击列 | `TimelinePopup`、`RowListItem::setCellAction` 同样没有网页版基线，只有单元测试与实机检查；浅色主题与很窄的窗口下的外观没有目测 | 它们不在组件库里 |
| 首选项与手柄设置的验证范围 | 只在开发机（Windows 11）上做过实机检查；Windows 7 真机与真实 XInput 手柄上的学习未验证 | 没有对应的设备与环境，发布前由用户验证 |
| 纵向堆叠里面板的压缩 | 网页版里没有 `fixed` 的面板在父容器高度不够时被压缩、内容区自己滚动；原生纵向堆叠不压缩子控件，需要这种行为的页面自己给面板高度 | 阶段 3 的页面都是自然高度，用到时再给堆叠补压缩 |
| 表格表头粘顶 | 平铺表格的表头在网页版里粘在滚动区域顶部，内容滚动时表头不动；原生表格暂时跟着内容一起滚走 | 要让表头知道外层滚动区域的位置，等对话框页面（阶段 10）真正需要时再补 |
| 表格列宽的细节 | 网页版自动表格布局对中日文换行点、很长的单词的最小宽度取值与原生排版引擎可能不同，个别单元格的换行位置或列宽相差几个像素 | 两边用的排版引擎不同，对照页里没有出现，列宽出现肉眼可见的偏差时再按实例修正 |
| 菜单弹层不滚动 | 网页版的菜单弹层在高度不够时在内容区里滚动，原生弹层不滚动，放不下时裁掉超出的部分 | Ember 的菜单项都不多，用到不到再补 |
| 系统按钮的外观 | 原生标题栏自绘的最小化、最大化、关闭按钮的悬停、按下颜色取系统常见样式，与系统绘制的按钮细节可能不同（Windows 11 与 Windows 7 上系统自己的样式也不同） | 按钮的命中测试仍返回 `HTMINBUTTON` 等（悬停提示、贴靠布局由系统处理），按下后的跟踪由外壳自己做；网页版里不是组件库绘制的，没有可对照的基线 |
| 阴影与圆角 | Windows 7、8、10 上外壳自绘阴影（分层窗口）与 1px 边框，窗口四角是直角；Windows 11 用系统的阴影与圆角；阴影的深浅与范围与系统阴影有细微差别 | 去掉标题栏样式并关闭系统的非客户区绘制后，系统不再画阴影，只能自绘；自绘版本在 Windows 7 上没有真机验证（开发机是 Windows 11，用 `EMBER_WIN_FRAME=custom` 在 Windows 11 上验证了它的绘制与按钮跟踪） |
| 鼠标点击打开菜单 | 原生外壳里用鼠标点击菜单名打开菜单时不高亮任何菜单项（2026-11-20 用户决定）；键盘打开（Alt+助记字母、方向键）仍高亮第一项；组件库网页版点击打开时高亮第一项；对照回归（`win32:reference`）里菜单页“点一下打开”的 24 个场景（两个主题、四个缩放比例、三个菜单）因此与网页版基线不一致，键盘展开与悬停场景一致 | 用户要求原生外壳不要默认选中；网页版是 rujian-ui-kit 的行为，不在本仓库修改 |
| 悬停提示的角标 | 角标用一个填色三角形加两条边线画出，与网页版旋转 45 度方块的裁剪有细微的边缘差别；角标不进像素对照（它在提示区域之外） | 两种光栅器对小三角形的处理不同 |
