# Win32 原生外壳

Ember 的第二套外壳：用 C++ 与 Win32 写成，不依赖 Electron，面向 Windows 7 到 Windows 11 的 64 位系统，尤其是系统与硬件都较旧、Electron 运行不稳的电脑。Electron 外壳保留，留给以后的 macOS 版，两套外壳共用同一个 C++ 核心，两套外壳的界面与行为保持一致，见第 6 节。

本文档是设计与开发计划，已由用户确认，按本文执行；状态说明同 [01-软件架构设计.md](01-软件架构设计.md)。界面的布局、菜单、各页面内容与 [05-界面.md](05-界面.md) 完全一致，本文只写原生外壳特有的部分。

## 1. 决策

| 决策项 | 结论 | 状态 |
| --- | --- | --- |
| 外壳数量 | Electron 外壳保留，留给以后的 macOS 版；新增 Win32 原生外壳；两套都经 `Core` 类使用同一个核心，核心的功能与行为不分叉 | 已定 |
| 两套外壳的同步 | Win32 外壳完成以后，所有外壳的界面与行为修改都要在两套里同步做，否则 macOS 用户的界面会与 Windows 不一样；编译、构建与调试只针对 Win32 外壳，不再构建和调试 Electron 外壳，见第 6 节 | 已定 |
| 构建选择 | 构建与调试脚本各两个：`build-electron.ps1`、`debug-electron.ps1`（现有 `build.ps1`、`debug.ps1` 改名，留给 macOS 版与必要时使用）与 `build-win32.ps1`、`debug-win32.ps1`（日常使用），选哪个脚本就构建、启动哪一套外壳，见第 6 节 | 已定 |
| 支持的系统 | Windows 7 到 Windows 11 的 64 位系统，要能在刚装好的干净系统上直接运行；不支持 32 位系统 | 已定 |
| 对齐范围 | 外观、样式、布局、菜单位置、主题切换与全部功能都与 Electron 外壳对齐；个别无法对齐的细节登记在第 10 节“已知差异”，差距不能过大 | 已定 |
| 样式令牌 | 全部取自 rujian-ui-kit 的令牌与主题（`src/styles`），原生外壳不自定义令牌；控件的尺寸、间距、状态底色取自各组件的样式文件 | 已定 |
| 控件库 | 不能使用 Web 组件库，另做一套 Win32 控件库，做成独立的 VC 项目，只依赖 Windows 系统与令牌，别的项目也能使用；性质与 rujian-ui-kit 相同，只是运行环境不同 | 已定 |
| 开发顺序 | 先做控件库，再做应用程序 | 已定 |
| 窗口外框 | 窗口边框、缩放、最大化、停靠、贴边与系统菜单都交给 Windows；只有标题栏区域自绘（图标、名称、菜单、更新按钮与三个系统按钮），做法与 Electron 外壳相同，见 5.2 | 已定 |
| 核心 | 核心不改动功能，经 `Core` 类（`core/src/bootstrap/core.hpp`）在进程内直接链接使用，不经 Node-API、不经网络；确需兼容 Windows 7 的小改动放在核心的 `platform` 层，见 7 | 已定 |
| 控件绘制 | Direct2D 1.0 与 DirectWrite 1.0（Windows 7 自带），没有可用显卡时用它们自带的软件渲染；不用 GDI+ 画界面，见 4.1 | 已定 |
| 运行画面 | Direct3D 11，只用硬件设备：不做 GDI 降级，也不用 WARP 等软件设备；电脑没有可用的硬件 Direct3D 11 设备（没有显卡、没有驱动、虚拟机没有 3D 加速）时弹出提示并退出，不支持这类环境，见 5.5 | 已定 |
| 工具链 | MSVC v143 工具集 14.44（本机已装的 VS 2022 组件），静态链接运行库；不用 14.50 及以后的工具集，因为它们的标准库不再支持 Windows 7（见微软 STL 变更日志），见 7 | 已定 |
| 项目位置 | `ember/win32/`，下分 `ui-kit/`（控件库）与 `app/`（应用程序），见第 3 节 | 已定 |
| 用户数据 | 与 Electron 外壳共用同一个用户数据目录与同样的文件格式（首选项、手柄绑定、BIOS、插件、界面状态），两个外壳不能同时运行，见 5.7 | 已定 |
| 帮助文档 | 随包带站点，由原生外壳提供只读的本机地址并用系统默认浏览器打开，见 5.6 | 已定 |
| 升级与安装包 | 原生外壳单独的安装包与升级清单，见 5.6 | 已定 |
| 平台 | 只做 Windows；macOS 仍只由 Electron 外壳提供 | 已定 |

## 3. 目录与依赖

```text
ember/win32/
├── ui-kit/              控件库：独立 CMake 项目，可单独构建、测试与被其他项目使用
│   ├── include/rujian/ui/   公共头文件，只放控件的契约与类型
│   ├── src/
│   │   ├── base/            绘制、文字、DPI、主题、输入与焦点等与控件无关的基础
│   │   ├── components/<控件>/   一个控件或一族控件一个目录
│   │   └── generated/       由令牌与图标生成的代码，不手写、不手改；生成结果提交进仓库，`win32:check` 检查它们与生成结果一致
│   ├── tools/               令牌、图标与字体生成器（gen-tokens、gen-icons、gen-fonts，字体用 lib/woff2.mjs 解码）、网页版对照（reference）
│   ├── third_party/         Tabler Icons 与 Quicksand 字体的许可与清单（图标图形、标题栏应用名字体的来源）
│   ├── gallery/             控件画廊程序
│   ├── test/
│   ├── README.md
│   └── LICENSE
├── app/                 Ember 原生应用 ember-win.exe（64 位）
│   ├── src/             contracts、logic、infra、entry、ui、platform、shared、bootstrap 八层；静态库 `ember_app`（输出 `ember_app.lib`），程序入口只有 `bootstrap/main.cpp`
│   ├── resources/       清单（`ember-win.manifest`）、版本信息（`ember-win.rc.in`）；图标在阶段 11 加入
│   └── test/            应用测试 `ember_app_tests`（假实现在 `test/support`）
├── probe/               平台探针 ember-probe.exe：在目标系统上检查图形、手柄、网络、声音与核心是否可用
```

- 控件库不依赖 Ember 的任何代码；应用程序依赖控件库与核心。核心保持原有位置，原生应用经 CMake 的 `add_subdirectory` 使用静态库 `ember_core`（`ember_core.lib`），不改变现有的 `npm run core:build`；给 Electron 用的 Node 原生模块是 `ember_binding`（`ember_binding.node`）。
- 控件库的组织与 rujian-ui-kit 一致：`base` 不引用控件；控件之间只经对方的公共头文件协作，只能引用依赖表里登记的控件，不得循环引用；依赖表与检查在控件库的 README 与 `test/` 里维护。
- 应用程序的分层、依赖与组装方式沿用 01 第 4、5 节的写法：具体实现只在 `bootstrap` 创建并注入，界面层只画控件与分派用户操作，业务与数据读写都在核心里。新增的目录进入 `npm run boundaries` 的检查。
- 令牌来自 `../../rujian-ui-kit`（与 06 第 1 节的组件库位置相同，环境变量 `EMBER_UI_KIT_SOURCE` 可改），生成器读取它的源文件，原生项目里不保存令牌取值的副本。

## 4. 控件库

### 4.1 绘制与文字

- 每个顶层窗口一个 Direct2D 的窗口渲染目标，字号、间距、圆角都以 CSS 像素定义，绘制时乘以窗口的缩放比例；缩放比例取自窗口当前 DPI。
- 文字用 DirectWrite，字体顺序与令牌 `--host-font-family` 一致：西文 `Segoe UI`，中文 `Microsoft YaHei`；弯引号、破折号与省略号（U+2014、U+2018 至 U+201D、U+2026）固定取宋体类字体（`SimSun`、`NSimSun`，没有时取 `Microsoft YaHei`），与组件库 `Rujian CJK Punctuation` 的规则相同。标题栏应用名用 `Rujian Quicksand`（拉丁子集，SIL OFL 1.1），组件库里是 `woff2` 文件，DirectWrite 读不了：生成器 `ui-kit/tools/gen-fonts.mjs`（用 Node 自带的 Brotli 与 `tools/lib/woff2.mjs`，按 WOFF2 规范还原 glyf、loca、hmtx 变换）把它们解码成 TrueType，字节嵌进 `src/generated/font-data.generated.cpp`，文字引擎用内存自定义字体集（`MemoryFontCollection`，DirectWrite 1.0 的字体文件与字体集加载器）加载，样式里 `TextStyle::face` 为 `Brand` 时用它（其余字符仍按正文字体分段），许可在 `third_party/quicksand`，`win32:check` 检查嵌入文件与生成结果一致。Windows 7 的 DirectWrite 没有字间距接口，`TextStyle::letterSpacing`（字号的倍数，每个字符簇后面加一份，包括最后一个）用整段排版得到的各簇位置、把每个字符簇单独画出来实现。省略号标记也取标点字体（网页版的省略号来自 `Rujian CJK Punctuation`）。Windows 7 的 DirectWrite 没有系统字体回退，按字符范围把文字拆成多段，各段指定字体族。
- 只用 Windows 7 自带版本的接口（Direct2D 1.0、DirectWrite 1.0、IMM32）；不依赖平台更新，也不依赖 DirectX 最终用户运行库。
- 动画与悬停、按下、选中、聚焦、禁用、错误、空状态的取值都来自令牌与各组件样式文件；一个状态一份取值，不在控件里写颜色数值。
- 与网页版逐像素对齐时实测得到的规则（改动绘制代码时先用 `win32:reference` 复核）：
  - 文字行高：样式没有设置行高时按 CSS 的 `normal` 处理（行高倍数传 0），字体的上升、下降、行距各自四舍五入到设备像素再相加（网页版就是这样算的，所以 100% 缩放下 11px 的字行高是 15 而不是 14.6），排版引擎由调用方设置缩放比例；有行高时按“字号 × 倍数”，字体内容区在行高里上下居中；
  - 边框宽度：`max(1, floor(宽度 × 缩放)) / 缩放`，即设备像素的整数倍且至少 1 个设备像素（125% 下 1px 的边框占 0.8 个逻辑像素）；布局也用取整后的宽度（带边框的控件用 `snapBorderWidth` 算尺寸）；
  - 盒子（有圆角与否都一样）的边缘对齐到设备像素，边框画在盒子内侧；边缘恰好落在半个像素上时往上取整（网页版的布局单位是精确的 1/64 像素，浮点误差不能让它往下取整）；
  - 轮廓线（`outline`）：线宽同边框，`outline-offset` 向零取整到设备像素，沿对齐后的边框盒描一圈，圆角是元素的圆角加偏移与线宽（偏移为负时在盒子里面，输入框的焦点环就压在边框那条带上）；元素在 `:focus-visible` 时带 `border-radius` 的（如分段单选的选项），底色与强调线也跟着圆角裁剪；
  - `inset` 阴影（无模糊）：阴影所在的内边距框先对齐像素，阴影的厚度不取整（上沿可能只盖住半个像素），内圆角的水平、垂直半径分别是外圆角半径减去相邻边的边框宽度；外阴影（`box-shadow`）不画在元素自己的框里面，模糊用按高斯积分逐层叠加的圆角矩形逼近（Direct2D 1.0 没有模糊效果）；
  - “右边与下边各有一段边框、旋转 45 度”的方块（复选框对勾、下拉框箭头与已选项的对勾）：方块的左上角、宽、高各自四舍五入到设备像素，绕取整后的方块中心旋转，边框宽度按上面的规则取整，整个图形作为一个多边形填色（元素整体带不透明度时不能重叠上色）；
  - 滑块轨道的填充是一条“两色硬边”的渐变：边缘在填充比例处，每个设备像素要么是强调色要么是轨道底色，所以用对齐像素的裁剪分两次画；滑块中心的活动范围是轨道宽度减去直径，填充边缘却按整条轨道的宽度算；
  - 文字选区的底色与选中文字的颜色取网站版在两个主题下的实测值（浏览器默认的 `::selection`），高度是行高 normal；用 Tab 键切到输入框时全选里面的文字，失去焦点后输入框的滚动位置回到开头；`type=search` 的输入框在有内容且悬停或有焦点时显示右侧的“×”，点它清空内容；
  - 这些规则里凡是“取整到设备像素”的，都依赖网页版排版时用的设备缩放比例；基线截图必须让浏览器的设备缩放比例等于目标缩放比例（见 4.4），否则边框与轮廓线会按本机系统的缩放比例算（在 150% 的电脑上 1px 的边框会变成 2/3 个逻辑像素）。
- 弹层（下拉选项、以后的菜单）显示在窗口的弹层上（`Host::showLayer`）：盖在内容之上，鼠标事件先给弹层，在弹层上按下不改变键盘焦点，在弹层之外按下或窗口大小变化时通知弹层自己关闭；弹层不超出窗口，下拉弹层默认在触发器下方 2px、放不下且上方更宽裕时翻到上方、最窄与触发器同宽、最高 240px、与窗口边缘至少留出 8px，与组件库的 `popup-placement.ts` 一致。
- 定时器与动画：宿主提供一次性定时器（`Host::startTimer`，窗口用 `SetTimer`，控件离开控件树时自动取消）与动画开关（`Host::animationsEnabled`）；离屏截图对照时关闭动画，控件直接切到目标状态，单元测试用 `Root::fireTimer` 手动触发。
- 滚动区域（`ScrollArea`，只做 Ember 用到的纵向滚动）：滚动条盖在内容上，轨道宽 10、滑块宽 6 居中、最短 20，长度与位置按 VS Code 的滚动条状态计算；鼠标移入、滚动或拖动时显示（100 毫秒渐显），鼠标移出或停止滚动 500 毫秒后开始隐藏（800 毫秒渐隐），不显示时不接收鼠标；在轨道上按下滑块先跳到指针处再接着拖；滚轮一格 50 像素（网页版实测，各缩放比例下相同），滚动位置取整到设备像素；方向键、翻页键、Home、End 在焦点控件不处理它们时滚动（输入框有焦点时不滚动），焦点移到内容里的控件时把它滚进可见范围。
- 容器与展示控件（阶段 3）：网页版里的普通文字元素（`p`、`h3` 等）在原生控件库里统一由内部控件 `Label` 承载（字号、字重、行高倍数、颜色，颜色令牌取 `currentColor` 时用正文文字色，没有文字时高度为 0）；`Panel` 的内容区放在 `ScrollArea` 里，没有内容时整块收起、标题行下面也不画分割线，内容之间的间距与内边距取面板令牌，`fixed` 是原生纵向堆叠的默认行为（不压缩子控件）；`Facts`、`SettingRow` 在窄窗口时上下排列，判断用的是窗口（视口）宽度而不是自己的宽度（与网页版的媒体查询一致：`Facts` 不超过 420、`SettingRow` 不超过 720，宽度由 `Host::viewportSize` 给出）；`SettingRow` 的名称说明列最宽 420、控件列最宽 280、列间距 10，空间不够时两列从零起平分、控件列先到上限，各列在行内垂直居中；`SplitView` 的分隔条宽 4、跨在左栏右边的分割线两侧，鼠标移上去停留 200 毫秒（动画关闭时立即）才显示聚焦色，拖动、方向键（每次 10 像素）与 Home、End 调整左栏宽度并限制在最小与最大宽度之间，指针是左右调整大小的箭头；`Tabs` 整条页签栏只有一个 Tab 停靠点，方向键首尾循环切换并同时选中，选中页签的文字加粗并变宽，页签栏与内容之间留一个堆叠间距（10），悬停底色只有上面两个圆角。
- 列表类控件（阶段 4）：`List`（只做 divided）的行是 `ListRow`（`SettingRow` 就是它），相邻两行之间留一条分割线的高度并画线，放进面板内容区时面板让贴着面板边的第一行去掉上内边距、最后一行去掉下内边距；`RowListItem` 是“前导（定宽 96）、主文字（占满剩余）、信息列、行尾操作”排成一行，行高下限 26，文字单行、超出用省略号，鼠标移上去与按下时底色变化（行本身不响应点击）；`Toolbar` 左边是前导控件与一行说明、右边是操作，放不下时操作换到第二行，下方有一条分割线；`Tree`（扁平条目）整棵树只有一个 Tab 停靠点，上下方向键、Home、End 只移动焦点，回车与空格选中，点击在同一行内按下并松开才选中，焦点行由 `Widget::focusRect` 告诉外层的滚动区域滚进可见范围；`Table`（只做紧凑、平铺两个属性都开的样式）的列宽按浏览器的自动表格布局算：每列取“最小宽度”（列的最小宽度、表头、单元格最长不可拆部分中的最大者加左右内边距）与“最大宽度”（不换行的内容宽度），放得下时按最大宽度的比例分配多出的宽度，放不下时在最小与最大之间按比例，再不够就取最小宽度；表头下边线与行与行之间（含详情行）的分割线各占独立的一条，行底色延伸到线的中心，行的最小高度 32 包含它两侧各半条线（所以最后一行的分割线之外的高度是 31.5），文字高度按网页版布局单位（1/64 像素）向下取整后再累加。
- 外壳类控件（阶段 5）：
  - 菜单（`MenuBar`、`MenuPopup`、`MenuItem`）：弹层项高 24、左右各留 4、勾选列宽 26、右侧留 26，快捷键、提示文字与子菜单箭头前再留 52，分隔线上下各留 5，弹层内边距上下各 4；菜单栏按钮高 24、左右内边距 8。弹层经 `Host::showLayer` 显示，子菜单是各自的弹层（右侧放不下改到左侧）；键盘焦点留在菜单栏上，按键与字符由它转给最深的有高亮项的弹层；点击打开时高亮第一项、悬停切换和鼠标展开子菜单时不高亮、方向键打开时高亮第一项（上方向键为最后一项），左右方向键在顶层弹层里切换相邻的菜单，子菜单里左键或 Esc 只关子菜单，助记字母直接选中，可勾选项（非单选）选中后菜单保持打开。弹层的最小宽度取触发按钮的宽度，再宽由菜单项内容撑开（网页版定位时把弹层的最小宽度设成按钮宽度）；菜单项不多，弹层不滚动，放不下时裁掉。
  - 标题栏（`TitleBar`）：高 36（含底部 1 像素分割线），左边留 8，依次是应用图标（16）、应用名（`Brand` 字体 13 号粗体、字间距 0.08em）与副名（500 字重、较淡）、菜单栏；右侧依次是操作区、折叠按钮（宽 46、占满内容区高度、相邻按钮用与底色相同的 1 像素竖线分开）和三个系统按钮；系统按钮宽 46、占满标题栏全部高度，图形是 10×10 的线条（最小化、最大化或还原、关闭），悬停与按下的颜色取系统常见样式（关闭按钮是系统的红色）。系统按钮的行为全部交给系统：窗口的 `WM_NCHITTEST` 调用 `TitleBar::hitTestWindow`，把 `Minimize`、`Maximize`、`Close` 转成 `HTMINBUTTON`、`HTMAXBUTTON`、`HTCLOSE`，空白处转成 `HTCAPTION`，其余是客户区；悬停与按下状态由窗口根据非客户区鼠标消息经 `setSystemButtonState` 告诉控件。
  - 状态栏（`StatusBar`、`StatusBarItem`）：普通高 26、大尺寸高 32（字号、图标、状态点、状态项内边距都有大尺寸的取值），顶部 1 像素分割线；状态项由状态点、图标（等级为警告、错误时配对应图标）、文字、文字后的长方形指示灯（或画在图标里的圆点灯）依次排列，部分之间留 4；左侧是可收缩的组，放不下时文字超过 16 个字符的状态项按“字符数的平方 × 原宽”分担收缩量（与 CSS flex-shrink 的算法一致）并以省略号结尾，右侧保持原宽靠右（可经 `addEndWidget` 放入通知按钮之类的别的控件）；按钮状态项的悬停、按下、选中用无底色按钮的颜色，`success` 等级的文字颜色盖过它们。状态项的等级枚举叫 `StatusItemTone`（`StatusTone` 已被 `StatusLabel` 使用）。
  - 悬停提示（`Tooltip`）：控件用 `Widget::setTooltip`（纯文字）或 `setRichTooltip`（标题行加分条说明）设置提示，空文字的提示盖住外层控件的提示；`Root` 负责时机：鼠标停在带提示的控件上 400 毫秒后弹出，已有提示显示时移到下一个控件立即弹出，点击、按键、滚轮、鼠标离开窗口、控件离开控件树时收起，点击后在鼠标离开该控件之前不再弹出；`Tooltip` 控件（经 `TooltipPresenter` 接口登记到 `Root`，由应用创建一个，必须先于 `Root` 销毁）负责排版与定位：纯文字内边距 4×8、最宽 320，版式提示内边距 8×10、最宽 380，宽高都不超过 80 的控件对齐控件、更大的对齐鼠标位置，默认在锴点右侧垂直居中、间距 10、放不下改到左侧，与窗口边缘至少 8，角标指向锴点中心。
  - 通知（`NotificationCenter`、`NotificationButton`）：`NotificationCenter` 是铺满窗口的弹层，只有通知与面板接收鼠标，窗口大小变化时经弹层回调重新摆放；新通知在右下角（离窗口边 10）向上堆叠、间距 6，最多 3 条（最早的先收起），停留 6 秒（错误 12 秒），历史最多 100 条；消息最多显示 3 行（面板里 4 行），超出的部分以省略号结尾，换行与连续空格按网页的排版折叠成一个空格；超过 60 个字符或含换行的消息可点击，点击后经 `setOnShowDetail` 回调由应用在“通知详情”对话框里显示全文；面板打开时收起弹出的通知并把未读清零，打开期间的新通知直接进历史；点击面板与通知按钮之外、Esc（应用的按键处理先调用 `handleEscape`）、窗口失去活动状态（`windowDeactivated`）时收起。通知按钮是状态栏右侧的铃铛加未读数（超过 99 显示 99+）。
  - 对话框框架（`DialogFrame`）：只是独立窗口对话框里面的内容（窗口外框、缩放、阴影、模态都由系统和应用负责）：标题栏高 32（含底部分割线）、左 6 右 4、标题与按钮之间留 4，最大化与关闭是 24×24 的小方块、间隔 2，关闭悬停与按下用系统关闭按钮的红色；正文在滚动区域里、四周留 10；按钮区上方留 6、下方与左右各留 10、按钮之间留 6、最小宽 72、靠右；标题栏空白处经 `hitTestWindow` 交给系统拖动（`HTCAPTION`）；Esc 请求关闭（请求与按钮的含义经回调交给使用方），回车在输入框或没有焦点时触发默认按钮（单行输入框没有设置回车回调时不处理回车，让它冒泡到对话框），初始焦点是默认按钮、其次是正文里第一个可获得焦点的控件。
  - 窗口框架（`AppFrame`）：只做 Ember 用到的属性：自上而下是标题栏、页面区（内容区底色）、底部面板（外壳底色、顶部 1 像素分割线、高度含这条线、不可拖动调整，高度限制在最小高度与窗口高度的 70% 之间）、状态栏（普通或大尺寸）；失去焦点时标题栏与状态栏换成失焦底色；有状态栏时通知中心让出状态栏的高度加 6 像素；没有活动栏、边栏、标签栏与右边栏。
- 单行文字输入框自己实现编辑（光标、选区、复制粘贴、撤销、词级移动、鼠标选择、输入法组合与候选窗位置），不嵌系统的输入控件，这样外观才能与令牌一致。
- 键盘：全部控件可用键盘操作，焦点环的显示规则与 05 第 2 节一致（画面区与窗口框架类元素不画焦点环）；菜单支持助记符与方向键。
- 无障碍：每个控件对外给出名称、角色、状态与值（UI 自动化提供者），见第 9 节第 8 项。

### 4.2 令牌与图标

- 生成器（`ui-kit/tools/`）读取 rujian-ui-kit 的 `ui-tokens.css`、`dark.css`、`light.css`、`ui-base.css`，解析 `var()` 引用、长度、颜色与阴影，生成 `src/generated/` 下的 C++ 常量；遇到不认识的写法直接报错，不跳过。
- 图标取自组件库使用的 Tabler 图标：生成器扫描 Ember 界面代码（`tools/kit-components.json` 的 `iconSources`）与已登记组件的源码里出现的 `icon<名称>` 标识符，取在图标数据里存在的那些（界面直接引用 18 个，加上已登记组件内部用到的，共 55 个，是“用得到”的超集）；把图标的 SVG 路径转成 Direct2D 路径几何，显示时取 24×24 画布中间的 20×20，描边宽度（`--icon-stroke-width`，屏幕像素）不随图标尺寸变化，端点与圆角为圆形，与组件库相同。
- 令牌变化后重新生成即可，不手改生成的文件；生成结果提交进仓库，`win32:check` 与 `test/win32-ui-kit-tools.test.ts` 都检查它们与生成结果一致；主题有浅色与深色两套，切换时整窗重绘。

| 滚动区域 | `ScrollArea` | 轨道、滑块、悬停、拖动、渐隐 |

| 页签 | `Tabs` | 常态、悬停、选中、聚焦 |
| 列表 | `List`、`ListRow`、`RowList`、`RowListItem`、`Toolbar` | 常态、悬停、按下、分割线、贴面板边的行 |

| 没有传属性 | `Heading`、`Row`、`Stack`、`Actions`、`NotificationCenter`、`NotificationCenterButton`；`Icon` 只传 `icon` 与 `className` |

另有快捷键换算（`shortcutFromEvent`、`RESERVED_SHORTCUTS`）属于逻辑，由控件库提供与组件库同样规则的实现。

`Button` 没传 `icon` 时，组件库按按钮文字自动匹配图标（`icon-rules.ts` 的通用规则，Ember 没有登记自己的规则）；原生控件库在阶段 2 提供同样的文字到图标的规则表，图标清单里的“控件内部用到的图标”大多来自这里。参考页对不想要图标的按钮传 `icon={false}`，原生示例与它保持一致。

### 4.4 与组件库的对照与测试

- 基线：用 Electron 里的浏览器部分渲染组件库的真实组件（不启动核心，不涉及 `ember_binding` 与应用构建），按“控件、状态、主题、缩放比例”逐项截图，作为基线（`ui-kit/tools/reference`，引用本机的组件库源码，参考页的结构与画廊示例页一一对应）；控件库的画廊程序（`rujian-ui-gallery.exe --render`）离屏渲染同一批场景。截图用调试协议的设备指标覆盖指定页面大小与缩放比例，保证截图像素严格等于“逻辑大小 × 缩放比例”（用窗口大小会被系统取整、截图被重采样），同时用 `force-device-scale-factor` 让浏览器排版用的设备缩放比例也等于目标缩放比例（不这样做，边框与轮廓线会按本机系统的缩放比例取整，截图因机器而异）；状态用真实的鼠标与键盘事件产生；参考页关闭过渡动画，只比较稳定后的状态；截图时关闭浏览器的 LCD 文字（`disable-lcd-text`），网页版的文字与原生版一样是灰度抗锯齿，样本之外的文字不会因彩边产生无关的像素差。
- 场景：`normal`（不带交互）、`hover`（鼠标移到样本中心）、`pressed`（再按下左键）、`focus`（按 Tab 键直到焦点落在样本上）；滚动区域页再加 `wheel`（鼠标移到样本上向下滚一格）、`drag`（在滑块上按下并向下拖 30 像素）；下拉框页再加 `open`（点一下展开弹层）、`openkey`（Tab 到下拉框后按“向下”键展开）、`openhover`（展开后把鼠标移到第三个选项上），菜单页（`menu`，三个单菜单的菜单栏）也用这三个场景（点一下打开时高亮第一项），悬停提示页（`tooltip`）再加 `tip`（鼠标移到样本上并等提示弹出）。弹层、提示与通知面板的区域按顺序排在所有样本之后（下拉选项；菜单弹层与各菜单项；提示；通知面板与各条历史），参与位置与外圈像素的对照（内部的文字与图标不比）；通知页（`notification`）与通知面板页（`notification-center`）在布局后发通知（画廊页的 `setup` 回调），弹出的通知就是样本；标题栏页（`title-bar`）不显示系统按钮（系统按钮的图形、悬停与按下颜色由单元测试的像素断言覆盖），对话框页（`dialog`）的样本是对话框整体（只用它标题文字所在的条形区域排除文字）、最大化与关闭按钮、正文和两个按钮，状态栏页（`status-bar`、`status-bar-large`）、窗口框架页（`app-frame`）各对照自己的样本；悬停提示页的三个按钮拉开到提示盖不住其他按钮（网页版提示背后有背景虚化，原生版没有，盖住时会透出轮廓）；子菜单的弹层不进像素对照（单元测试覆盖）。每一页的样本、要做交互场景的样本、各样本里不参与像素对照的区域（四边各自的边距，用来排除文字）都由画廊的 `--info` 给出；下拉框展开时弹层里的各个选项按顺序排在所有样本之后，也参与位置与文字外框的对照。分栏页（`split`）与页签页（`tabs`）的交互场景以分隔条、页签栏为目标；树页（`tree`）以整棵树为目标，信息行页（`row-list`）与表格页（`table`）的悬停、按下落在样本中心所在的行上，表格与工具栏样本里的文字按“左右（或上下）条带参与对照”排除；（样本里嵌着另一个样本时，Tab 次数只在被嵌的样本自己那一项计一次）；窗口宽度会改变布局的控件各有宽、窄两个页面（`facts` 与 `facts-narrow`、`setting-row` 与 `setting-row-narrow`）。
- 比较：控件位置偏差不超过 1 个逻辑像素；文字与图标之外的区域按像素比较，通道差超过 6/255 的像素不超过 4%、最大差不超过 125（圆角、焦点环与旋转箭头、对勾曲线上 Skia 与 Direct2D 的抗锯齿差别；100% 缩放下展开的箭头有约 0.5 像素的偏差）；文字与图标的外框各边偏差不超过 1 个逻辑像素（按设备像素向上取整），文字笔画的抗锯齿差异不算。这组阈值要能分辨“边框宽度错 1 个设备像素”这类差错，放宽之前先确认是拓扑差错还是抗锯齿。每个组合的网页版与原生版截图和 `report.json` 保存在 `build/ember/win32-reference`。
- 运行：`npm run win32:reference`（可加 `--scenes`、`--themes`、`--scales`、`--no-build`、`--gallery` 参数），先用 `win32:test` 构建画廊。
- 缩放比例取 100%、125%、150%、200%，主题取浅色与深色。
- 单元测试用 GoogleTest（与核心共用 `core/third_party/googletest`，路径可在控件库的 CMake 选项里改）：布局、状态转换、文字编辑、键盘操作、菜单导航。
- 画廊与测试只用离屏渲染与消息投递，不调用全局鼠标与键盘接口。

## 5. 应用程序

### 5.1 与核心的连接

- 原生应用在进程内持有 `Core`：启动参数按现有格式传入（用户数据目录、应用版本、预装插件目录、预装 BIOS 目录、ffmpeg 路径，以及命令行的 `--debug-port`、`--debug-token` 对应的 `debugPort`、`debugToken`，见 04）；请求、取消、事件与帧都用 `Core` 的回调，事件与请求结果从任意线程回到界面线程时经窗口消息投递。实现是 `infra/core-client` 的 `InProcessCoreGateway`（接口在 `contracts/core-gateway`）：`Core` 在后台线程启动，启动完成前收到的请求先排队，启动完成后按顺序发出；启动失败时排队的请求全部以错误结束；回到界面线程的投递由 `platform/threading/ui-thread` 的仅消息窗口完成；帧由核心线程写入 `LatestFrameSlot`，界面只取最新一帧。请求名与参数、结果类型的目录由 `schema-gen` 生成到 `contracts/core-gateway/generated/request-catalog.hpp`，界面与 `entry` 只经目录引用请求名。
- 请求名、参数与事件沿用 Schema；原生应用从 `schema/*.schema.json` 生成 C++ 类型使用核心已有的生成代码，不再另写请求格式。
- 画面：`FrameHandler` 在模拟线程调用，像素只在回调期间有效，所以原生外壳在回调里把帧复制进一个单槽缓冲并通知界面线程，界面线程取最新一帧绘制，旧帧直接丢弃；规则与 Electron 外壳的背压一致（每帧恰好结算一次，不积压）。
- 声音由核心经 miniaudio 直接输出，原生外壳不处理声音。
- 调试服务、插件脚本、软驱与磁带等都在核心里，原生外壳只做界面。

### 5.2 主窗口与标题栏

- 主窗口是普通的顶层窗口，保留系统的边框、缩放、最大化、停靠、贴边与系统菜单；用 `WM_NCCALCSIZE` 把标题栏区域并入客户区，自绘 36px 高的标题栏（图标、名称、菜单、“更新”按钮），菜单与按钮之间留约 50px 可拖动的空白。边框处理在 `platform/window/frameless-frame`（命中测试、系统按钮区、窗口大小限制、DWM 边框着色），位置与最大化状态记在 `config/shell-state.json`（`platform/window/window-placement` 与 `infra/shell-state`）；窗口内容由 `ui/shell/main-window-view` 组装。主题跟随首选项 `appearance.theme`（`system`、`dark`、`light`）切换，`system` 时读系统的明暗设置，切换在 `entry/preferences/theme-sync`。
- 系统按钮（最小化、最大化或还原、关闭）也画在标题栏里，宽 46px、高与标题栏一致，图形取系统的样式（线条，不用字体图标，因为 Windows 7 没有它们的字体）；它们的行为全部交给系统：命中测试返回 `HTMINBUTTON`、`HTMAXBUTTON`、`HTCLOSE`，所以点击、悬停提示、窗口贴边与 Windows 11 的贴靠布局都由系统处理，与 Electron 外壳的做法相同。
- 系统关闭了窗口合成（Windows 7 的基本主题）时没有阴影，自绘 1px 边框；其余情况用 DWM 的阴影。
- 窗口大小、位置、最小尺寸（524x500）、窗口位置的保存与恢复规则同 05 第 2 节、第 9 节；多显示器、DPI 变化（`WM_DPICHANGED`）时整窗重新布局；Windows 7 与 8 只有系统级 DPI，按启动时的值处理。
- 主题：深色、浅色、跟随系统；跟随系统时读 `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` 的 `AppsUseLightTheme`，没有这一项的系统（Windows 7、8 与早期 Windows 10）按浅色处理；首选项 `appearance.theme` 变化立即生效，系统主题变化时监听 `WM_SETTINGCHANGE`。

### 5.3 对话框窗口

对话框是独立的顶层窗口，归属于主窗口，主题与主窗口一致，同一个对话框同时只开一个，再次打开时聚焦已有的；标题栏、关闭按钮、可缩放、最小尺寸、模态的规则以组件库的 `Dialog` 与 Electron 外壳的 `platform/window/dialog-window.ts` 为准。对话框里的键盘事件与手柄读取挂在对话框自己的窗口上。

### 5.4 主进程请求的原生实现

下面 15 个请求在 Electron 外壳里由主进程处理，原生外壳在 `app/src/entry` 里实现同名同参数的处理，结果的格式与错误码不变；路径只来自用户在系统窗口里的选择、拖入主窗口的文件或启动参数，界面层拿不到任意路径。

| 模块 | 请求 | 原生实现 |
| --- | --- | --- |
| cartridges | `open`、`recent`、`openRecent` | 系统文件选择窗口（`IFileOpenDialog`，Windows 7 可用）、最近打开清单（`config/recent-cartridges.json`，最多 10 个） |
| machines | `openBios`、`openBiosDirectory` | 文件选择、用资源管理器打开 BIOS 目录 |
| mappers | `openPackage` | 文件选择（`.emap`） |
| media | `openFloppy`、`openTape`、`openTapeRecording` | 文件选择与保存窗口，保存录音用保存窗口 |
| preferences | `pickDirectory` | 文件夹选择窗口 |
| system | `openLogDirectory`、`openHelp`、`updateStatus`、`checkUpdate`、`installUpdate` | 见 5.6 |

另有：文件选择窗口按用途记住上次目录（`config/last-directories.json`）；拖放文件用 `WM_DROPFILES`，登记后只把编号交给界面（见 05 第 2 节）；`mainOnly` 的 6 个核心请求（如 `cartridges.load`）只由这些处理在内部调用。主进程请求按模块放在 `entry/<模块>/`，由 `entry/main-requests` 的路由登记并校验参数，未登记的请求直接拒绝。帮助与应用更新的请求在对应阶段（帮助 10、更新 11）之前由占位实现回应：`system.openHelp` 返回“帮助不可用”的错误，更新状态固定为“不支持”。

### 5.5 画面与输入

- 画面区是主窗口里的一个子窗口，用 Direct3D 11 显示核心给出的 RGBA 帧（R、G、B、A 的内存顺序，每像素 4 字节）：每帧把像素上传到动态纹理，适应窗口用双线性采样，整数倍用最近邻采样；交换链用 DXGI 1.0 的位块传送模式（Windows 7 没有翻转模型），设备功能级别最低取 9_1。比例（4:3、8:7）、裁剪（显示全部 240 行）、画面框、黑底与 05 第 7 节、`src/ui/runtime/screen-layout.ts` 一致；“未开机”“已暂停”等提示与鼠标捕获提示由控件库预先画成位图，作为纹理叠在画面上。创建不出硬件的 Direct3D 11 设备时（没有显卡、没有驱动、虚拟机没有 3D 加速），在启动时弹出“无法初始化画面渲染，当前电脑不支持”的提示并退出；不做 GDI 降级，也不使用 WARP 软件设备（设备创建只用硬件驱动类型）。着色器预先编译：`platform/display/screen.hlsl` 经 `npm run win32:shaders`（`tools/build/gen-screen-shaders.mjs`）用 Windows SDK 的 `fxc` 生成 `vs_4_0_level_9_1`、`ps_4_0_level_9_1` 字节码，生成结果（`screen-shaders.generated.cpp`）提交进仓库，运行时不依赖 `d3dcompiler`。画面子窗口对鼠标透明（`HTTRANSPARENT`），鼠标输入都由主窗口里的画面控件接收；菜单、悬停提示与通知这类弹层盖到画面上时，控件库把弹层的矩形报告给应用（`Widget::layerRects`、`Root::setLayerRectsHandler`），应用用 `SetWindowRgn` 把画面子窗口对应的矩形挖掉，弹层才显示在画面之上（差异见第 10 节）。
- 键盘、鼠标与游戏手柄只采集原始事件，格式与现有的输入消息一致，交给 `Core::sendInput`。
- 键盘独占：画面区获得焦点期间向系统登记原始输入的键盘设备（`RIDEV_NOLEGACY`，目标是主窗口），进程内不再产生传统键盘消息，所有物理按键都只以“扫描码加标志”交给机器；做法与 `core/src/binding/keyboard-capture-win.cpp` 相同，但原生外壳不经 Node，直接在窗口过程里处理 `WM_INPUT`，不用全局键盘钩子；焦点离开、窗口失去激活、关闭窗口时释放，Win 键、Ctrl+Alt+Del 与 Alt+Tab 仍由系统处理。独占期间窗口收不到传统键盘消息，所以外壳快捷键（F7、F8、F9、F11 等）都不生效，规则与 Electron 外壳一致（见 05 第 6 节）：主窗口里点完鼠标、关闭菜单、执行完运行操作后焦点都回到画面，所以快捷键只在没有点过鼠标或焦点不在画面上时有效，其余情况用菜单与面板按钮（菜单打开期间焦点在菜单上，独占已关闭，菜单可以用键盘操作）。
- 鼠标捕获：点击画面后隐藏指针并用相对位移（`ClipCursor` 与 `WM_INPUT`），双击右键（400 毫秒内两次右键按下，第二次不送给机器）释放。
- 游戏手柄：每个画面帧读一次，Windows 7 自带的 XInput 9.1.0（动态加载，不依赖需要另装的 `xinput1_3.dll`）读 Xbox 类手柄，按“标准映射”给出按钮与轴的编号；设备标识的格式与浏览器里的 `Gamepad.id` 保持一致，以便两个外壳共用同一份手柄绑定。非 XInput 手柄（DirectInput）见第 9 节第 7 项。
- 开发期诊断：环境变量 `EMBER_WIN_DIAGNOSTICS` 指向一个文件时，应用退出时把帧计数（核心送来、画出、被新帧顶掉）与每一帧从核心发布到画出的延迟（平均、p95、最大）写成 JSON，没有设置时不记录；“画出”是帧上传并提交给 Direct3D 的时刻，不含合成器与显示器的延迟。`tools/dev/latency-win32.mjs` 用它测量（Release 版，1-len_ctr 运行 30 秒：核心送来 2293 帧，画出 2285 帧，被新帧顶掉 8 帧（0.35%），延迟平均 0.46 毫秒、p95 0.62 毫秒、最大 5.96 毫秒）。

### 5.6 帮助、升级与安装

- 帮助文档：随安装包带站点目录；原生外壳在本机 `127.0.0.1` 的随机端口提供只读服务（只服务站点目录，路径含 `..` 或编码斜杠的一律拒绝），用系统默认浏览器打开。Windows 7 上的默认浏览器可能不能运行站点（VitePress 需要较新的浏览器），所以首次打开时检测并提示，见第 9 节第 1 项。
- 打开日志目录、BIOS 目录：用资源管理器打开；路径由原生外壳决定。
- 安装包：原生外壳用独立的安装程序与便携压缩包，安装器不依赖 .NET，见第 9 节第 2 项。
- 升级：沿用 01 第 11 节的静态目录思路，新增原生外壳自己的升级目录；清单带版本、文件大小、SHA-256 与签名，签名公钥写在程序里；下载经 WinHTTP。干净的 Windows 7 默认不启用 TLS 1.2，所以下载通道的选择见第 9 节第 2 项。升级逻辑由 `system.updateStatus`、`system.checkUpdate`、`system.installUpdate` 三个请求与状态推送对外，界面与 Electron 外壳一致。
- 升级内容仍写在帮助文档的“更新记录”页，新版第一次启动时自动打开一次。

### 5.7 用户数据与单实例

- 用户数据目录、`config/` 下各文件的名称与格式与 Electron 外壳相同（`shell-state.json`、`recent-cartridges.json`、`last-directories.json`、`preferences.json`、手柄绑定、`bios/`、插件目录），原生外壳按同样的校验规则读写；文件不存在或损坏时用默认值。
- 单实例：沿用首选项 `app.allowMultipleInstances`（见 05 第 4.5 节）；两个外壳按 Chromium 的 ProcessSingleton 约定（用户数据目录下独占打开的 `lockfile`、类名 `Chrome_MessageWindow` 且标题为用户数据目录的消息窗口、`WM_COPYDATA` 传递命令行）互相识别，所以一个运行时另一个用同一个用户数据目录启动会被拒绝，并把已有窗口提到前面（命令行经 `WM_COPYDATA` 传到已有进程，目前只用来激活窗口，不加载其中的卡带）；两个方向都已用 Electron 的 `requestSingleInstanceLock` 实测互通。

### 6.1 两套外壳的同步

- Electron 外壳留给以后的 macOS 版。Win32 外壳完成以后，所有外壳的界面与行为修改（布局、菜单、页面、文案、快捷键、设置项的显示、对话框等）都要在两套里同步做，其中组件库的令牌与样式改动也要同步到 Win32 控件库，否则不同平台的界面会不一样。
- 日常的编译、构建、调试和冒烟只针对 Win32 外壳；Electron 外壳不再构建、打包和调试，同步改动的 Electron 代码只要通过现有的类型检查、lint、依赖检查与 TypeScript 测试。
- 业务逻辑仍然只在 C++ 核心里，所以需要在两套外壳里同步的只是界面层；新增请求、事件与主进程请求仍先改 Schema。
- 这条规则在 Win32 外壳完成（阶段 12 通过）后生效，完成时同步写进项目的开发指令与 01、05、06 文档。

## 7. Windows 7 兼容策略

- 工具链：v143 的 14.44 工具集；运行库静态链接（`/MT`），所以不要求用户安装 VC 运行库、也不要求补丁 KB2999226；核心现有的 `CMAKE_MSVC_RUNTIME_LIBRARY` 已是静态。
- 目标版本：`_WIN32_WINNT=0x0601`，应用清单声明支持 Windows 7、8、8.1、10 与 11，并声明 DPI 感知（按系统支持的最高级别，运行时检测 `SetProcessDpiAwarenessContext`、`SetProcessDpiAwareness`、`SetProcessDPIAware`）。
- 系统接口：用到的比 Windows 7 新的接口一律运行时检测、没有就降级；导入表审计脚本（`win32:check`）列出可执行文件与全部静态库导入的函数，对照 Windows 7 SP1 的导出清单基线，出现不在基线里的导入就报错。基线由 Windows 7 SP1 环境导出一次后提交。
- 不依赖的东西：.NET、WebView2、DirectX 最终用户运行库、平台更新（Direct2D 1.1、DXGI 1.2）、新版 TLS；Direct3D 只用 Windows 7 SP1 自带的 11.0 基础接口与 DXGI 1.0。
- 核心里已知要核对的点：`std::filesystem`、`std::condition_variable`、miniaudio 的 WASAPI 初始化、Winsock、`FileWatcher`（`ReadDirectoryChangesW`）、子进程管道、`GetSystemTimePreciseAsFileTime`、`SetThreadDescription` 一类较新的接口；阶段 0 逐项审计，必须改核心时只改 `platform` 层并保持其他系统的行为不变。
- 验证：Windows 7 SP1 的干净系统（用户的 Hyper-V 虚拟机：没有任何补丁、没有硬件 3D）、Windows 10、Windows 11 各跑一遍；Windows 7 与 8 上读不到的系统主题按浅色。Hyper-V 里的 Windows 7 没有 WDDM 显卡，Direct3D 11 的硬件设备创建不出来，所以画面区在 Windows 7 上的显示由用户在发布前找有显卡的 Windows 7 真实用户验证，开发中按通过处理（探针在这台虚拟机上其他全部检查都通过，Direct3D 一项已知失败的原因见报告中的诊断信息）。

## 9. 已确认项

以下各项已由用户确认，按“建议”执行，其中第 8 项的备选不采用，第 9 项按用户的新决定改为不用 WARP。

1. **帮助文档怎么显示。** 站点需要较新的浏览器，Windows 7 的默认浏览器可能是 IE 11。建议：随包带站点，用本机只读服务加默认浏览器打开，检测到浏览器过旧时提示用户安装较新的浏览器。备选：内置固定版本的 WebView2 运行时（体积很大）或把手册改写成原生控件显示（不能保证排版与搜索）。
2. **安装包与升级。** Squirrel 只服务 Electron 外壳。建议：安装器用 Inno Setup（不依赖 .NET，支持 Windows 7），另出便携压缩包；升级目录独立（OSS 下 `updates/ember/windows-native/`），清单带 SHA-256 与签名；干净的 Windows 7 不能用 TLS 1.2，所以优先 HTTPS，不能协商时回退到 HTTP 并强制验证签名与哈希。备选：只出便携包、升级由用户手动下载。
3. **控件库的名称、形态与许可。** 建议：位置 `ember/win32/ui-kit`，库名 `rujian-ui-kit-win32`，命名空间 `rujian::ui`，用 CMake 项目（可生成 Visual Studio 解决方案，也可在 VS 里直接打开文件夹），许可证用与 rujian-ui-kit 相同的 Apache-2.0，应用程序（GPLv3）链接它没有冲突。备选：直接写 `.vcxproj`（与 CMake 二选一，不建议维护两份）。
4. **核心的小改动。** 你说核心不用动；Windows 7 兼容审计可能发现个别接口需要降级。建议：允许只在核心的 `platform` 层做运行期降级与 CMake 目标调整，不改任何功能与请求格式，其他系统的行为不变。
5. **Windows 7 测试环境。** 已确认：最低支持 Windows 7 SP1 x64，用户提供 Windows 7 SP1 虚拟机（Hyper-V，没有任何补丁、没有硬件 3D，所以只能验证除 Direct3D 硬件设备以外的部分，画面由用户发布前找真实用户验证）；我在本机只能静态审计导入表并在 Windows 10、11 上运行，Windows 7 上的实际运行由用户按我提供的脚本与步骤运行并回传结果。
6. **窗口按钮的画法与菜单位置。** 菜单放在标题栏上，就必须自绘三个系统按钮的图形（Electron 外壳里也是自绘的），行为仍全部交给系统。建议按 5.2 做；备选：保留系统标题栏，菜单放在它下面一行（与 Electron 外壳不一致，不建议）。
7. **非 XInput 手柄。** 建议：第一版只做 XInput（Xbox 类手柄，以及多数带 XInput 模式的第三方手柄），DirectInput 手柄放到阶段 9 之后单独补；备选：同时做 DirectInput，但需要自己维护按钮与轴的标准映射。
8. **无障碍。** 构建入口已定为两个脚本，不再需要默认值。建议随控件一起做基础的 UI 自动化提供者（名称、角色、状态、值），与 Electron 外壳里的语义属性对应，让读屏软件等辅助工具能读出控件；备选：只做键盘可达，不做 UI 自动化。
9. **没有硬件 3D 的环境。** 已确认：不支持。画面用 Direct3D 11 的硬件设备，创建不出时弹出提示并退出，不用 WARP、不做 GDI 降级；没有显卡的电脑与没有 3D 加速的虚拟机都不在支持范围内。
10. **右键菜单与加载动画不做。** 已确认：组件库的输入框右键菜单（Electron 外壳里没有传入宿主能力，菜单里没有“粘贴”，按组件库的代码点其他项也不会执行，未在界面上实测）与 `State`、`StatusLabel` 里的像素格加载动画，模拟器用不到，原生外壳都不做：输入框上右键不弹自绘菜单，“加载中”不显示动画也不显示文字（数据来自本机核心，加载很快）；差异登记在第 10 节。

## 10. 已知差异

已知会出现的差异登记在这里，开发中逐项补充；文字笔画的抗锯齿与字重在不同的渲染引擎里有细微差别，不登记。

| 项 | 差异 | 原因 |
| --- | --- | --- |
| 右键菜单 | Electron 外壳的输入框上右键会弹出组件库的编辑菜单，原生外壳不弹出 | 用户决定模拟器用不到（第 9 节第 10 项） |
| 加载中状态 | Electron 外壳的“加载中”带像素格动画和文字，原生外壳什么都不显示 | 同上 |
| 弹层的背景虚化 | 网页版的下拉弹层、菜单、悬停提示、通知与通知面板背后有背景模糊（`backdrop-filter`），原生外壳没有；弹层底色是半透明的，只有弹层盖在有内容的区域上时才看得出区别（提示、通知贴着按钮或内容时能透出后面的轮廓） | Direct2D 1.0 没有模糊效果，也不能读取窗口后面的像素 |
| 外阴影的模糊 | 弹层、对话框的外阴影用逐层叠加的圆角矩形逼近高斯模糊，边缘的渐变与网页版有细微差别 | 同上 |
| 弹层盖在画面上 | 菜单、悬停提示与通知盖在运行画面上时，画面子窗口按弹层的外框矩形挖洞，弹层圆角之外的四个角露出的是窗口底色而不是画面；弹层底色的半透明与外阴影也看不到后面的画面 | 画面是独立的 Direct3D 子窗口，系统只能用矩形区域把它让出来，做不到按圆角或透明度合成 |
| 旋转箭头的边缘 | 100% 缩放下展开的下拉框箭头与网页版相差约 0.5 个像素 | 网页版对旋转元素的取整细节没有完全还原 |
| 悬停过渡 | 网页版的底色、边框颜色有 150 毫秒的过渡，原生外壳直接切换到目标状态（分隔条的 200 毫秒悬停延迟保留） | 不做逐帧过渡；对照时网页版也关闭过渡 |
| 页签下划线两端 | 选中页签的下划线有 2 像素的顶部圆角，两端各有一个像素的抗锯齿与网页版不同（100% 与 125% 缩放下网页版的渲染还多出一个淡色像素），对照时下划线只比较外框 | 两种光栅器对 2 像素高的圆角形状处理不同 |
| 滚动区域的 `bleed` | 手柄设置页等用到的 `bleed`（内容区的滚动条贴到页面边缘）还没有做 | 阶段 3 没有用到的页面，随阶段 9 的手柄设置页补上 |
| 纵向堆叠里面板的压缩 | 网页版里没有 `fixed` 的面板在父容器高度不够时被压缩、内容区自己滚动；原生纵向堆叠不压缩子控件，需要这种行为的页面自己给面板高度 | 阶段 3 的页面都是自然高度，用到时再给堆叠补压缩 |
| 表格表头粘顶 | 平铺表格的表头在网页版里粘在滚动区域顶部，内容滚动时表头不动；原生表格暂时跟着内容一起滚走 | 要让表头知道外层滚动区域的位置，等对话框页面（阶段 10）真正需要时再补 |
| 表格列宽的细节 | 网页版自动表格布局对中日文换行点、很长的单词的最小宽度取值与原生排版引擎可能不同，个别单元格的换行位置或列宽相差几个像素 | 两边用的排版引擎不同，对照页里没有出现，列宽出现肉眼可见的偏差时再按实例修正 |
| 菜单弹层不滚动 | 网页版的菜单弹层在高度不够时在内容区里滚动，原生弹层不滚动，放不下时裁掉超出的部分 | Ember 的菜单项都不多，用到不到再补 |
| 系统按钮的外观 | 原生标题栏自绘的最小化、最大化、关闭按钮的悬停、按下颜色取系统常见样式，与 Electron 外壳里系统绘制的按钮细节可能不同（Windows 11 与 Windows 7 上系统自己的样式也不同） | 按钮的行为交给系统（`HTMINBUTTON` 等），网页版里不是组件库绘制的，没有可对照的基线 |
| 悬停提示的角标 | 角标用一个填色三角形加两条边线画出，与网页版旋转 45 度方块的裁剪有细微的边缘差别；角标不进像素对照（它在提示区域之外） | 两种光栅器对小三角形的处理不同 |
