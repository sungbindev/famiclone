# 调试器程序

Ember 调试器是一个独立的原生程序（`ember-debugger.exe`），经 [04-调试服务.md](04-调试服务.md) 的调试服务连接正在运行的 Ember，提供图形化的调试窗口：看反汇编与寄存器、下断点与单步、查看与修改内存、监视表达式、查看指令跟踪。Ember 本体仍不做调试窗口（见 05）；调试器与 fcdev 扩展、脚本一样，只是调试服务的又一个客户端。

本文是设计与开发计划。状态说明同 [01-软件架构设计.md](01-软件架构设计.md)：已定、拟定、待定；拟定与待定的内容，实现前先向用户确认。

## 1. 决策

| 决策项 | 结论 | 状态 |
| --- | --- | --- |
| 形式 | 独立程序 `ember-debugger.exe`，用 C++ 与 Win32 原生开发 | 已定 |
| 与 Ember 的关系 | 只经调试服务连接（WebSocket 加 JSON-RPC 2.0，只连 `127.0.0.1`，带令牌）；不链接核心，不读 Ember 的进程内存；Ember 本体不增加调试窗口 | 已定 |
| 目标系统与工具链 | 与 Ember 相同（见 08 第 1 节）：Windows 7 SP1 到 Windows 11 的 64 位系统，MSVC v143 工具集 14.44，静态运行库，`_WIN32_WINNT=0x0601`；可执行文件也纳入 `win32:check` 的导入检查 | 拟定 |
| 界面 | 用 `win32/ui-kit` 控件库，令牌取自 rujian-ui-kit；缺少的控件先加进控件库（第 7 节），调试器里不另写通用控件 | 拟定 |
| 窗口形式 | 主窗口是“调试器”；其余工具各是独立窗口，从“调试”菜单打开，同一进程里共用一条连接与一份运行状态；不做窗口停靠 | 拟定 |
| 第一批工具 | 调试器（含寄存器面板）、内存查看器（含内存搜索）、监视窗口、跟踪记录器，见第 3 节 | 拟定 |
| 项目位置 | `ember/win32/debugger/`，与 `win32/app` 并列，分层与依赖规则同外壳，见第 4 节 | 拟定 |
| 连接方式 | 启动时按端点文件自动连接；没有可连的 Ember 时可以由调试器启动一个；也可以手动输入地址与令牌，见 3.5 | 拟定 |
| 协议类型 | 请求与结果的 C++ 类型由 `schema/` 生成到调试器自己的 `generated` 目录，不手写 JSON 字段名 | 拟定 |
| 反汇编 | 在调试器里完成（输入是停下时读到的 CPU 空间快照），助记符与操作数的写法与核心的 `inspector.disassemble` 一致 | 拟定 |
| 窗口与断点的保存 | 见第 9 节第 3 项 | 待定 |
| 分发与升级 | 见第 9 节第 1 项 | 待定 |

## 3. 第一批工具

快捷键沿用常见调试器的习惯，拟定如下，实现前随本文一起确认。

### 3.1 调试器窗口

```text
┌ 标题栏：文件  调试  运行  帮助 ─────────────────────────────┐
│ 工具栏：继续/暂停  单步  步过  步出  单步扫描线  单步帧  复位   │
├───────────────────────────────┬────────────────────────┤
│ 反汇编                         │ 寄存器（CPU 与各模块）   │
│                               ├────────────────────────┤
│                               │ 断点                     │
├───────────────────────────────┼────────────────────────┤
│ 调用栈  栈内存                 │ 监视                     │
├───────────────────────────────┴────────────────────────┤
│ 状态栏：连接  机型  运行状态  帧  周期  当前行所在的区域       │
└──────────────────────────────────────────────────────┘
```

- 运行控制：继续与暂停（F5）、单步（F11，一条指令）、步过（F10）、步出（Shift+F11）、单步扫描线与单步帧（`runtime.step` 的 `scanline`、`frame` 单位）、软复位与硬复位（`runtime.reset`）。运行中只有“暂停”与复位可用；断电或没有主机时全部置灰。
- 反汇编：每行依次是断点槽、地址、字节、指令文本（带有效地址与取值的注释，如 `LDA $0180 = 33`）。停下时自动滚到当前 PC 并高亮；可以滚到任意地址，地址框接受表达式（`$C000`、`pc`、`[$FFFC]`）；点击断点槽切换执行断点；右键菜单有“运行到此行”（临时执行断点加继续）、“把 PC 设到此行”（`inspector.setState` 改 `pc`）、“添加断点”（执行、读、写）、“在内存查看器中打开”。向上滚动时从目标地址之前的几个候选起点试着反汇编，取能恰好在目标地址对齐的一个；都对不齐时按单字节数据行显示。
- 寄存器面板：CPU 的 `a`、`x`、`y`、`sp`、`pc`、`status`（`NV-BDIZC` 各位可以点击翻转）、周期数，点击数值直接改（`inspector.setState`，在指令之间生效）；其他模块（`ppu`、`mapper`、`paging`、`mmc3`、`board`，随机型而不同）按 `inspector.getState` 给出的字段原样列出，每个模块一组，只读的灰显。
- 断点面板：列出断点（类型、地址或范围、条件、命中次数），可以新增、删除、启用与禁用、编辑条件。启用开关与条件都由核心保存与求值（`inspector.updateBreakpoint`、`addBreakpoint` 的 `condition`，条件写法见 04 第 4.5 节），条件不成立的命中核心不会停下，也不累计次数。
- 调用栈与栈内存：调用栈来自核心的 `inspector.callStack`，每帧显示调用处、目标地址与返回地址，双击跳到对应反汇编；栈内存显示 `$0100-$01FF`，SP 所在的字节高亮。
- 监视面板：与监视窗口是同一份监视项（3.3）。
- 状态栏：当前选中行的地址经 `inspector.resolve` 解析，显示它所在的区域与偏移（如 `cart.prg + $1A40`、`board.ram + $0200`、`register`），分页与 bank 切换的机型靠它看出代码在 ROM 里的真实位置。
- 刷新：每次停下（命中断点、单步、暂停、授权运行结束）刷新全部面板；运行中不刷新反汇编、寄存器与调用栈，面板灰显并写明“运行中”。

### 3.2 内存查看器

- 空间：下拉框列出 `inspector.listSpaces` 的全部空间（`cpu`、`ppu`、`board.*`、`chip.*`、`cart.*`，随机型与卡带而不同），默认 `cpu`；每行 16 字节，左边地址，中间十六进制，右边字符；每行字节数可以选 8、16、32。
- 编辑：选中字节后直接输入十六进制，经 `inspector.writeMemory` 写入；只读空间（卡带的 ROM、BIOS）灰显；`cpu` 与 `ppu` 空间的写与 CPU 写一样有副作用，状态栏提示。
- 变化高亮：与上一次刷新的内容比较，变化的字节标色，几次刷新后渐退。
- 跳转与定位：地址框接受表达式；选中字节时状态栏显示 `inspector.resolve` 的结果；右键可以在选中地址上添加读断点或写断点、添加到监视。
- 搜索：精确值（字节序列、文字、16 位小端数值）搜索，以及“与上次比较”的搜索（等于、不等于、变大、变小、变了、没变）；范围是当前空间；结果列表按地址排列，双击跳转，搜索时一次读出整个空间（单次请求最多 1 MB，更大的空间分段读）。
- 刷新：停下时刷新；运行中按设置里的频率刷新可见的范围（默认每秒 10 次）；上一次读取没有返回时不发下一次。

### 3.3 监视窗口

- 每行一个表达式，显示取值，值变化时标色；可以新增、删除、编辑；整份监视清单保存起来（第 9 节第 3 项）。
- 表达式：数值（`$C000`、`0xC000`、十进制）、寄存器与状态名（`a`、`x`、`y`、`sp`、`pc`、`p`，以及 `ppu.scanline` 这样的 `<模块>.<状态项>` 路径）、内存读取（`[地址]` 读一个字节，`{地址}` 读 16 位小端数值，地址前可以加空间名，如 `[ppu:$3F00]`）、运算符 `+ - * / % & | ^ ~ << >> == != < <= > >= && || !` 与括号。取值显示格式可以按行选十六进制、十进制、二进制。
- 求值只读：所需的内存与状态在每次刷新时按表达式批量读取；不使用 `inspector.watch`（它只能监视状态项，不能读内存）。
- 可编辑：寄存器与 `[地址]` 形式的监视项可以直接改值，写回走 `inspector.setState` 与 `inspector.writeMemory`；其余只读。
- 表达式求值器在调试器的 `logic` 层，监视项与地址框共用它；写法是核心断点条件（04 第 4.5 节）的超集，增加 `<模块>.<状态项>` 路径与空间名。

### 3.4 跟踪记录器

- 控制：开始与停止，类型选择指令（`instruction`）、寄存器访问（`io`）或中断（`irq`），最大行数（1 到 1000000，默认 100000），指令类可以勾选“每个地址只记第一次”。开始经 `inspector.traceStart`，停止经 `inspector.traceStop`。
- 显示：停止后读 `traceStop` 返回的文件（路径在调试输出目录里，调试服务只监听本机，调试器与 Ember 在同一台电脑上，直接只读打开），放进虚拟列表，指令类按列着色（地址、字节、指令、寄存器、周期）。
- 过滤与定位：按文字过滤（只显示包含它的行）；选中一行可以跳到反汇编里对应的地址；可以复制选中的行或另存为文本文件。
- 限制：同时进行的记录最多 8 项（协议限制）；记录属于当前主机，装入新卡带后作废，调试器提示并清空已停止但未显示的记录。

### 3.5 连接、设置与启动

- 自动连接：启动时读端点文件 `run/debug-endpoint.json`（位置规则同 04 第 8 节：用户数据目录下，`ember-data` 目录优先，否则 `%APPDATA%\Ember`）并确认写它的进程还在；也认环境变量 `EMBER_DEBUG_URL`、`EMBER_DEBUG_TOKEN`、`EMBER_DEBUG_ENDPOINT`、`EMBER_USER_DATA`，以及命令行参数 `--endpoint=<文件>`、`--url=<地址>`、`--token=<令牌>`、`--user-data-dir=<目录>`。
- 连不上时弹出“连接”对话框：手动输入地址与令牌，或“启动 Ember”（先选 `Ember.exe` 的位置，记住；用 `--debug-port=<空闲端口>` 与 `--debug-token=<随机令牌>` 启动，只在自己启动的进程退出时结束它，不按进程名结束）。Ember 默认只能运行一个实例：用户已经开着一个没有开启调试服务的 Ember 时，对话框提示“先在 Ember 的首选项里开启调试服务，或关闭它后由调试器启动”。
- 握手：`debug.hello`（`client` 为 `ember-debugger`，`protocol` 为 1）；`protocol` 或 `coreVersion` 不认识时拒绝连接并说明。
- 订阅的事件：`runtime.stateChanged`、`runtime.breakpointHit`、`runtime.error`、`debug.eventsDropped`；收到 `debug.eventsDropped` 就重新读取 `runtime.status` 与断点命中状态。
- 断线：状态栏显示“已断开”，各窗口灰显，每秒重连一次；Ember 重启后令牌可能变了，重连前重新读端点文件。
- 设置对话框：Ember 的位置、刷新频率、字号、是否保存窗口布局；经 `win32/ui-kit` 的 `SettingRow` 等控件排布。

## 4. 程序结构

```text
ember/win32/debugger/
├── CMakeLists.txt        目标 ember-debugger，链接控件库；网络部分直接编译核心的 platform/network 两个源文件
├── resources/            清单、版本信息、图标
├── src/                  contracts、logic、infra、ui、platform、shared、bootstrap 七层；入口只有 bootstrap/main.cpp
│   └── generated/        由 Schema 生成的协议类型，不手写、不手改
└── test/
```

- 分层与依赖规则同 `win32/app/src`（见 01 第 5 节与 06 第 4 节）：`contracts` 只引用 `shared`；`logic` 引用 `contracts`、`shared`；`infra` 引用 `contracts`、`shared`、`platform`；`ui` 只引用 `contracts`；`platform` 引用 `shared`；具体实现只在 `bootstrap` 创建并注入；新增目录进入 `npm run boundaries` 的检查（目录只能是这七层，前四层的文件放在 `<层>/<模块>/` 下）。
- 模块（各层目录同名）：

| 模块 | 职责 |
| --- | --- |
| `session` | 连接与会话：端点发现、握手、请求与响应的对应、事件分发、断线重连、启动 Ember；对外是异步接口，回调回到界面线程 |
| `cpu-debug` | 运行控制、步过与步出、断点（含条件与启用状态）、反汇编、寄存器、调用栈 |
| `expression` | 表达式的解析与求值（监视项与地址框共用） |
| `watch` | 监视清单与取值刷新 |
| `memory` | 内存空间、读写、变化比较、搜索 |
| `trace` | 跟踪记录的启停、文件读取、过滤 |
| `workspace` | 设置、窗口布局、断点与监视清单的保存 |
| `shell` | 主窗口、菜单、状态栏、工具窗口的打开与关闭、连接对话框 |

- 模块之间只经对方契约层的抽象协作：`cpu-debug`、`watch`、`memory`、`trace` 都经 `session` 的契约发请求，监视与地址框经 `expression` 的契约求值。
- 网络：`infra/session` 用核心 `platform/network` 的 `TcpSocket` 与 `websocket`（握手校验用其中的 `acceptKey`，帧用 `encodeFrame` 加掩码发送）；网络读写在一个工作线程里阻塞进行，收到的消息经窗口消息投递到界面线程，请求完成时在界面线程调用回调，界面不被阻塞。
- 线程：界面线程只做绘制与交互；工作线程只做网络；文件读取（跟踪文件、端点文件）在界面线程之外的任务线程里完成。
- 协议类型：`npm run schema` 增加一路输出，把 `inspector`、`runtime`、`debug` 等模块里调试器用到的请求、结果与事件生成为调试器的 `generated` 头文件（带 JSON 序列化），Schema 仍是唯一定义。

## 5. 调试服务的用法

| 操作 | 请求 |
| --- | --- |
| 握手与订阅 | `debug.hello`、`debug.subscribe` |
| 运行状态 | `runtime.status`；事件 `runtime.stateChanged`、`runtime.breakpointHit`、`runtime.error` |
| 继续、暂停、复位 | `runtime.resume`、`runtime.pause`、`runtime.reset` |
| 单步 | `runtime.step`（`instruction`、`scanline`、`frame`） |
| 一次取全部状态 | `inspector.snapshot`（各模块状态、断点、监视项，同一时刻读出） |
| 内存 | `inspector.listSpaces`、`readMemory`（二进制帧）、`writeMemory`、`resolve` |
| 修改寄存器 | `inspector.setState` |
| 断点 | `inspector.addBreakpoint`（含 `condition`）、`listBreakpoints`、`updateBreakpoint`（启用与条件）、`removeBreakpoint`、`clearBreakpoints` |
| 调用栈 | `inspector.callStack` |
| 跟踪 | `inspector.traceStart`（可选 `ring`）、`traceRead`、`traceStop` |

- 停下时的刷新：一次 `inspector.snapshot` 加一次读取 `cpu` 空间的 `$0000-$FFFF`（64 KB，二进制帧，本机回环），反汇编、栈内存、监视里 `cpu` 空间的取值都从这份快照得到，不再逐项请求；反汇编里芯片寄存器类地址的取值与核心一样显示 `00`。
- 步过：当前指令是 `JSR` 时，在下一条指令的地址加一个临时执行断点后继续运行，任何原因停下都删除临时断点；其他指令等同单步。步出：取 `inspector.callStack` 栈顶的返回地址加临时执行断点后继续，命中时检查 SP 已经回到调用之前，没有（递归）就再继续。临时断点命中时若同时命中用户的断点，以用户的断点为准。
- 断点同步：调试器的断点列表是准的。核心换主机（装入卡带、整机机型开机、取出）时会清空断点，收到 `runtime.stateChanged` 且原因为 `load` 或 `eject` 后，调试器把断点（含启用状态与条件）重新下发。
- 请求的时延：同一连接上的请求按到达顺序逐个处理，机器自由运行时每个检查请求要等到下一个帧边界才执行（暂停时立即执行）。所以运行中的自动刷新每次只发一批、上一批没返回不发下一批；运行控制与事件不受影响。
- 带条件的断点由核心求值，命中很频繁（如每帧甚至每扫描线执行的地址）也不用往返调试器。

## 6. 模拟器的改动

下表的 8 项核心改动已经全部做完（2026-11-24），调试器的三批工具都不需要再改核心。协议的写法见 [04-调试服务.md](04-调试服务.md) 第 4.5 节。

| 序号 | 改动 | 改在哪里 | 状态 |
| --- | --- | --- | --- |
| 1 | 调用栈：请求 `inspector.callStack` | CPU 核在 JSR、RTS、RTI 与复位后通知调用观察者；各 6502 机型共用的 `CpuDebugKit` 用 `CallTracker` 维护调用栈（按栈指针弹出过期帧） | 已实现 |
| 2 | WebSocket 客户端一侧：帧解码器可以解码服务端发来的不带掩码的帧，增加客户端握手请求与响应校验 | `core/src/platform/network/websocket.*`；不改协议，不改服务端的行为 | 已实现 |
| 3 | 各机型的 PPU 状态补 `control`、`mask`、`status` | 各机型 `readState` 的 `ppu` 分支；`Ppu2c02` 增加同名的只读访问 | 已实现 |
| 4 | 颜色表：请求 `inspector.getPalette`，按机型当前的 PPU 与 `$2001` 的强调、灰度位返回 64 个颜色的 RGBA | `Ppu2c02` 与 `PpuUm6576` 的 `colorTable()`，机型的 `MachineDebugger::colorTable()` | 已实现 |
| 5 | 条件断点：断点带表达式条件、启用开关，请求 `inspector.updateBreakpoint` | `logic/hardware/debug/expression.*`（解析与求值）、`BreakpointTable` | 已实现 |
| 6 | 事件记录：请求 `inspector.eventsStart`、`eventsStop`、`eventsGet`，记寄存器读写与中断，带帧、扫描线与点 | `EventLog`、`ProbeHub`、`CpuDebugKit`；`Ppu2c02::positionAt` 与 `PpuUm6576::position` 给出位置 | 已实现 |
| 7 | 子程序周期统计：请求 `inspector.profilerStart`、`profilerStop`、`profilerGet` | `CallTracker` | 已实现 |
| 8 | 跟踪的实时读取：`traceStart` 的 `ring` 与请求 `inspector.traceRead` | `RecorderTable` | 已实现 |

Ember 的界面与外壳、其余协议都没有改。
